# 附錄引用

**為何要提**：主文精要呈現，完整或細緻之內容才詳見附錄。主文不提，讀者與審查委員就不知道附錄存在，即使知道也不知道怎麼用。

範圍、編號與引用形式依專案參數第 18 項。下文之「附錄 X」為示意。規則強度標示見 SKILL.md 第 2 節，未標者按預設處理；數值（字數）為經驗值。

## 1. 基本規則

- **每份附錄皆於表格以外之內文提及**，並說明讀者於其中可查得什麼；附錄要點表不代替內文之提及。
- **提及前先打開該附錄**，依其實質內容與用途定位，不憑名稱想像。
- **編號與名稱不手寫**：由程式取自資料夾名或共用資料，產製時檢查存在；資料夾增減或改編號時重產即核對。
- **只提確實交付之文件**：委託單位臨時要求而不在交付清單之額外報告、簡報，不列附錄也不寫「另提供」；收件人對不上就會認為亂寫。
- **舊期別之附錄編號不沿用**：編號改變時重新對應；無系統對應者補於正文適切處。

## 2. 落點（預設）

| 落點 | 提及什麼 |
|---|---|
| 背景與目的 | 專案之範圍與管控方式之文件 |
| 整體架構之文件脈絡段 | 專案實際有之文件，依其脈絡（如需求、規劃、規格、測試、操作）依序帶出；次要文件一句收束 |
| 各系統一節之末 | 該系統確有之操作手冊、測試等文件（有分冊者提分冊）；規格書有專章者一併提出 |
| 維護 | 建置與移機之文件 |
| 資訊安全 | 掃描、版控與安全性設計之文件 |
| 測試 | 測試計畫、測試結果與效能測試之文件 |
| 系統文件 | 其他文件與附錄內容要點表 |

落點隨專案之章節調整，原則是：技術與功能之敘述段不夾帶文件之指路，附錄集中於交代文件之段落或一節之收束段。專案沒有的文件類別不提，不虛構。

## 3. 各系統一節之附錄段（預設）

**該系統有專屬文件者，預設放最末，自成一段，以系統名起首**：此段通常接在多張圖之後、下一個系統標題之前，讀者沒看到系統名會被下一個標題帶跑。節末沒有圖而可自然併入末段者，併入該段（如接在「此外，」段之末）亦屬合理，依專案之寫法。該系統沒有專屬文件者不硬補；專案已定於上層一次引用者從專案。

```
○○系統之甲、乙與丙等完整操作，詳見附錄 X-1「○○系統之使用者操作手冊」，其測試項目與結果載於附錄 Y-1「○○系統之測試報告」。（有專章者）○○之程式規格載於附錄 Z「系統程式規格書」。
```

- **列舉接「等」**：所列只是部分者加「等」或補齊，以該分冊之章節為全集對照；所列已是全集才可不加。
- **避免落單**（判準依〈文句與段落診斷〉第 5 節，不以句數）：自成一段者寫足各文件可查得之內容，通常 2 句以上；該系統同時有操作與測試文件者成對帶出，平行陳述，不寫「則載於」。
- 接於引圖句之後者另立一段（引圖句須為段落最後成分）。
- 不在各系統重複全系統層級之文件。

## 4. 依實質內容定位

- **輕重緩急**：主要文件依脈絡帶出；操作與測試文件皆有者成對（提操作手冊即帶出測試報告）；次要文件只依其自身之用途寫一句，不細述其欄位，分句扣除名稱不超過約 20 字（經驗值）。
- **用詞不得引起誤解**：文件之描述用詞會被照字面讀（如「連線方式」會被讀為網路設定）。
- **不寫成為點交或驗收而作**：
  - 改前：驗收時請依附錄 X 逐項核對
  - 改後：若須查覽各分館之功能概述，可詳閱附錄 X
- **附錄之內部用語不搬入**。
- **不寫文件之由來**：不寫取自另一份文件或由程式產生；寫文件本身之內容與用處。
- **不宣告順序**：不寫「依需求、規劃、設計、測試至驗收之程序」，以敘述串連。

## 5. 附錄內容要點表

- 欄位：附錄、文件名稱、內容要點。內容要點寫內容與用途。
- **不寫會隨重產變動之數字**（掃描之檢出數、案例數、提交筆數），以免附錄重產後與正文不一致；專案數、系統數取自共用資料。
- 全份表格宜少，此表常是唯一之表。

## 6. 可機械檢查者

可於產製時檢查，不符即中止（皆以專案實際有之文件為準）：每份附錄於表格以外至少提及 1 次、提及之編號存在、有分冊之系統提出其分冊、同段依脈絡排序、次要附錄未細述、操作與測試皆有者成對。見〈落地到專案〉第 4 節。

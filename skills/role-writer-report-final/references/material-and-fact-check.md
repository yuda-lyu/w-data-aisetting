# 素材提取與事實核對

**任務**：把開發紀錄變成可入文之事實。順序不可顛倒：先提取與歸類，再核對，最後才精煉成文句。

**分工**：事實核對之通用方法（證據優先順序、現行執行路徑、提交訊息只是線索、「原為 X 改為 Y」兩端有據、期間查日期、全稱與數量列舉成員、目的與效益、判定值）在 skill[role-writer-validate] 之 Step 3「證據門檻」，核對派工之提示詞範本在其參考檔《文句與因果審閱》§7，本檔不重複，只列成果類報告之素材來源、歸類與寫法。

## 1. 素材來源

| 報告 | 素材 | 用法 |
|---|---|---|
| 分年 | 前一期報告產製之後，各程式專案之版本控制提交紀錄 | 主要素材，逐筆歸類 |
| 分年 | 前一期報告之文字與圖 | 只用於判斷差異，不抄文字 |
| 全期（預設） | 歷年報告、最近一期報告、各系統功能要點、操作手冊 | 先做提取檔，分為初衷與規劃、逐系統之歷年進展、各年度小結、舊年度用語清單 |
| 皆有 | 手冊、規格、程式碼、設定檔、共用資料檔 | 核對事實 |

舊年度報告可能為舊產線與舊用語：只取事實與架構方向，用語依現行規範改寫（專案參數第 27 項）。

**新建、無前期報告或無操作手冊者**：期間起點取專案起點（如首筆提交），報告寫「成果」而非「相對前期之差異」；核對來源改取規格、說明文件與程式。全期取法：`git -C <版本庫> log --reverse --format="%ad %h %s" --date=short`。

## 2. 提取提交紀錄

- **期間**：前一期報告實際產製之後至今，日期以該報告之產製紀錄為準，不憑印象。
- **輸出**：依程式專案分組、依日期由舊至新，一行一筆（日期、提交代號、提交訊息）。探索之輸出放暫存夾，不覆寫專案內已被其他文件引用之紀錄檔。
- **統計只記於原則文件**：提交筆數屬提取方法，不入正文（專案參數第 17 項）。
- **提交訊息用於定位與歸類，實際範圍以差異為準**：提交多為批次進行，一筆常含多項修改；訊息只是線索，判定一項改動之實際範圍須比對前一期末之程式與現行程式（依據之門檻見 skill[role-writer-validate] Step 3）；差異供核對，不據以逐檔列舉：

```bash
git -C <版本庫> log --since=<起日> --format="%ad %h %s" --date=short
git -C <版本庫> log -S "<關鍵字>" --oneline
git -C <版本庫> show <前一期末提交>:package.json
```

**若版本庫曾重建或移轉**：現行版本庫之首筆提交可能就含全部程式碼，前一期末之提交不存在。此時以首筆提交與現行版本比對差異，舊紀錄取自專案另存之檔。

## 3. 差異之來源：不只專案程式碼

系統開發案之差異也在所用之套件。只看專案提交訊息會漏掉，或寫成空泛之「大幅更新相依套件」。

1. **定出兩端版本**：前一期末與現行各程式專案所用之套件版本；現行讀 `node_modules/<套件>/package.json`，前一期末讀 Git 歷史之 `package.json`，或以發布日期反查。
2. **自有套件逐一比對**：以 `npm pack <套件>@<舊版> --pack-destination <暫存夾>` 取得舊版（依專案之 registry 設定），與現行版比對檔案增刪；另看該套件之提交紀錄。新增之檔案與提交訊息最能看出功能與安全性之差異。現行安裝版之後才發布者不算本期成果。
3. **非自有套件**：比對主要版本之變動（執行環境、前端引擎、表格與介面組件庫之更換或移除），寫其對系統之影響，不逐一列套件與版號。
4. **排除本部署未啟用之功能**：套件是中立的，其功能不一定用於本案；查各專案之設定檔確認有啟用才寫。手冊或測試涵蓋了也不代表要列入成果。（本點指套件之功能；屬交付範圍而暫不啟用者與選項型能力，依〈內容邊界與防禦性寫作〉第 3 節。）
5. **歸類與寫法**：依第 4 節歸類。「更新相依套件」可寫，但不得只寫這句當作該系統之成果。

## 4. 逐筆歸類

每筆歸入一類（涉及多類者依主要內容）。類別與落點依專案之章節調整，原則不變：每筆都要有去處，包括「不寫」。

| 類別 | 判準 | 落點 |
|---|---|---|
| 新進度 | 前一期未有之功能、系統、頁面、資料類型或工具 | 各系統一節之主體；判定為亮點者配圖 |
| 維護、更新與優化 | 套件更新、環境升級、重構、效能與穩定性、日誌 | 該系統一節之「此外，」段；跨系統共通者集中於維護一節 |
| 資訊安全 | 弱點之套件更新、可疑輸入之偵測、密碼規則、前端保護、掃描 | 資訊安全一節 |
| 測試與資料產製 | 端對端測試、單元測試、示範與測試資料之產製 | 測試一節 |
| 文件 | 各報告與手冊 | 系統文件一節 |
| 不寫 | 版本庫之移轉、報告產線之內部調整、規格與設定檔、尚未上線之修正、人名與單位之內部實況 | 不入報告 |

## 5. 成果類報告之核對要點

- **核對對象依序為手冊、流程規格、程式碼與設定、共用資料檔**：只寫查得、已上線、能演示者。逐句之證據門檻與帳冊依 skill[role-writer-validate] Step 3，本節不另立門檻。
- **無部署之套件或函式庫**（對 Step 3 之適用變通，其餘門檻照用）：「現行執行路徑」理解為已交付（或已發布）之版本其入口走得到該行；「已上線、本部署啟用」理解為已交付版本預設可用或說明文件載明之選項，並有測試或可實跑之示例。尚未發布之成果，以報告所涵蓋之基準版本為準，於回報列為「需你決定」。
- **無法確認是否為本期新增者寫現況**：「○○系統現已提供…」陳述能力，不宣稱為本期新增。
- **前一期之敘述作對照**：前一期寫「開發中」「已規劃將提供」者，本期已提供即屬新進度；前一期已有者（文字或圖上看得到）不寫成新進度，判斷時以圖為證，不憑記憶。
- **效果亦須為本期才有**（通則）：寫「改為…，使…」之前，改動與效果分開驗：先開前期末之程式或畫面，確認該效果前期是否已有；已有者只當背景，不接在「使」之後。「原為 X，改為 Y」兩端有據只證明機制有變，不證明效果是新的。效果寫使用者看得到之差異（換了什麼、多了什麼），機制只作補充；程式註解已寫明改動緣由者以之為準，不另行推論。例：舊版之到期提醒本來就依到期日排序，不寫「重構提醒清單，使其依到期日排序」，寫實際之差異「提醒清單改為可依分館篩選」。由段落濃縮為前言、開場、對照表與小結時，留下的須是差異本身，不是段落裡最好懂之句。歷年累積之功能寫「已分年積累」，不當成本期成果。why：只驗機制兩端，會把過往工項當成本期成果。
- **寫結果前先問：只用本系統自己之數據算得出嗎？** 算不出者，於首次寫到該成果處交代缺的那份資料由誰提供、在計算中擔任什麼角色，架構圖與規格類附錄之外部來源亦列入（改前「新增計算西區分館之預約等候天數」；改後「借閱紀錄只能算出各書之平均借期，須再以各分館之開館時數換算，故依各分館提供之開館時數表，新增計算西區分館之預約等候天數」）。外部提供之量與系統所需之量不同時分別寫明，並交代系統之換算（「外部書目庫提供 10 碼書號，系統換算為 13 碼後比對」），不寫籠統之上位詞。資料經委託單位及其授權之單位提供者兩者皆寫。來源歸屬有爭議者依專案參數第 13 項。why：只寫系統做了什麼，讀成系統自己之數據即可算出，等於攬下他方之貢獻、也藏住依存；素材只取自提交訊息與功能要點時最易漏。
- **功能之全集依程式之條件**：觸發條件與適用範圍依程式寫全，不以測試案例所走之路徑或規格之簡化語寫窄。本條管觸發條件與適用範圍之寫全；可選用之能力列不列，依〈內容邊界與防禦性寫作〉第 3 節之判斷次序，不以程式之全集補寫委託單位不知之能力。
- **裁定者之記憶也要查**：裁定者記得某功能是本期新增，查前期報告不一定如此；查得不符時據實回報，不照寫也不逕改。

## 6. 防漏：不憑記憶挑選

- 以提交訊息之「重構、新增、轉分頁、擴充、改版」逐筆列出本期之使用者畫面改動，逐筆判定為亮點（配圖）、文字陳述或不寫，判定結果登記於亮點清單或「考慮過而未選」。
- 裁定者點名漏列一項時之做法依 skill[role-writer-validate] §7（先歸類再同類掃描，不只補被點名者）；本節之逐筆判定即其 L3 反向覆蓋在成果類之做法（軸為本期之使用者畫面改動）。
- 全期總報告（單案依據）：先就各系統列出主要目的與主要功能（依功能要點與手冊），再自主要功能中挑亮點，不沿用分年報告之細部改版（〈亮點與配圖〉第 2 節）。
- 列舉系統之功能時對照其功能要點逐項取材，主要功能不得漏列。
- **工項清單是盤查之軸，不是事實來源**：委託之規劃書或工作項目清單（期初擬定，與最後交付常不同）用於判定本期之工作性質與盤查有無漏寫：逐項對現行程式判定已做、部分、未做或與規劃不同；已做而報告未寫者補寫，不據清單之字面寫成果。**驗收對應表**（委託單位或裁定者要求時才附）：列工項與報告章節之對應並稍加描述，工項名稱照原文逐字，章節號由程式帶出，內容只寫正文已寫之事實；部分或未做之工項不在表內自行說明，列入回報由裁定者決定如何呈現；正文仍依實際成果之系統分節（一工項常橫跨多個系統，依工項分節會重複）。

## 7. 精煉為報告文字

- **提交訊息不照錄**：開發端之簡記（字首、英文縮寫、暱稱）一律改寫；照錄只限版控記錄類附錄之提交紀錄表。
- **附錄之內部用語不搬入**：附錄自行定義之用語改為讀者一看即懂之說法；技術名詞首次出現時以一句說明其作用（「以瀏覽器自動化工具模擬使用者之操作」）。
- **承接語只承接，不夾帶新事實**。
- **自貶詞去除**（預設）：「初步」「概略」「粗略」不寫。

| 提交訊息（虛構示意） | 類別 | 報告之寫法 |
|---|---|---|
| 館藏清單改用新版表格組件、篩選列可收合 | 新進度 | 將原本之表格組件更換為新版組件，因其只繪製可視範圍內之列，可縮短大量館藏之載入時間；篩選條件列可收合，騰出清單顯示空間（效益須有機制為據，見 skill[role-writer-validate] Step 3） |
| 建構新增、編輯、刪除功能（多個系統） | 新進度 | 於首個系統一節以其畫面詳述，其餘寫「其機制同○○系統」並只寫特有者 |
| 新增後台編輯功能 | 新進度 | 寫實際能編輯什麼（功能取自手冊之操作項目），不沿用提交訊息之字面 |
| 執行環境升版至長期支援版 | 維護 | 為使系統穩定運作、提高效能並修補已知之漏洞，將執行環境更新至其長期支援版（Long-Term Support, LTS）之第 N 版（目的寫此類動作真正要達成之事，不以版本之名稱倒推，見〈文句與段落診斷〉第 4 節；所列目的以版本說明或更新紀錄查得者為限） |
| 移除對舊組件庫之依賴 | 維護 | 移除舊有之介面組件庫 |
| 圖示字型改隨專案安裝、不走外部載入 | 維護 | 前端所用之圖示字型改由隨同專案安裝之套件引入，不依賴外部之內容傳遞網路 |
| 正式版不輸出除錯用對照檔 | 資訊安全 | 正式版本之前端程式移除原始碼對照檔，避免前端之原始碼外露 |
| 初步建立自動化操作測試 | 測試 | 併入端對端測試之敘述，「初步」不寫 |
| 調整建置設定、整理程式註解 | 不寫 | 開發端內部作業 |

上表之提交訊息與寫法皆為虛構示意，不得當成任何專案之事實。

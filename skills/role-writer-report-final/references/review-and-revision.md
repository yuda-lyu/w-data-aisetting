# 盤查與修訂

**分工**：通用之檢測與修正流程都在 skill[role-writer-validate]，本技能**不重複**，避免兩處分叉。本檔只留成果類報告專屬之通讀面向、修改原則與修訂紀律。

## 1. 與 skill[role-writer-validate] 之對照（不重複之項）

| 事項 | 在 skill[role-writer-validate] 之位置 |
|---|---|
| 三層偵測（lint → 候選掃描 → 逐段通讀）與三段式審閱（機械候選 → 未參與撰寫者逐句審閱 → 作者核實） | Step 3b；《文句與因果審閱》§1、§2、§4 |
| 候選掃描之形式判準（含換詞連用）與掃描程式之取捨 | 《文句與因果審閱》§3、§10 |
| 通讀問題表（名詞所指、事實與機制、主語與分句、指代、因果、列舉、概括句、重複、缺字與歧義、跨文件同步、承諾與範圍） | 《文句與因果審閱》§8 |
| 主張溯源之證據門檻、因果逐句五問、判定值 | Step 3 |
| 派工範本（逐句審閱、逐字校對、事實核對） | 《文句與因果審閱》§5、§6、§7 |
| 被指正後之做法：歸類、同類判準、同形不等於同類、全文掃描同類、修正管線、第一段寫歸類與同類掃描結果 | §7 |
| 批次改原稿之修補先驗後寫 | 《文句與因果審閱》§11 |
| 給共用位置（技能、範本、共用規範）之文字所做之他案試讀 | 《文句與因果審閱》§9 |
| 回報之覆蓋聲明、審閱範圍與未讀範圍 | §8；《文句與因果審閱》§4「回報要寫」 |

成果類走 skill[role-writer-validate] 決策表之「成果／進度報告」列。三層依序、範圍不自限、同類掃描之範圍與放行區之處理，一併依其 §7 第 3 步，本檔不另存一份。

## 2. 成果類通讀時每段另問之事

與《文句與因果審閱》§8 之問題表併用，下列只補該表沒有之成果類面向：

| 面向 | 問法 |
|---|---|
| 稱謂 | 委託單位與自稱依專案參數嗎？全稱只在首次定義？ |
| 層級名稱 | 「本系統」指整體嗎？各系統一節指整體時寫了全名嗎？ |
| 輕重 | 次要者是否寫得比主要者長、排得比主要者前？ |
| 邊界 | 有無缺陷自陳、承諾、保證、指責、內部實況、開發端之事？（〈內容邊界與防禦性寫作〉） |
| 標點與格式 | 分號、冒號、數字與量詞、格式名、「」之用法（〈格式、標點與用字〉） |
| 圖 | 紅框、圖名、測試字樣、段圖交錯、引圖句是否為段落最後成分；圖內文字亦為正文（同類掃描範圍依 skill[role-writer-validate] §7）；改後重繪該報告之圖並以版本控制確認只有該圖變動 |

通讀之對象與方法（讀產出之報告，不讀產製程式）依《文句與因果審閱》§3、§8；分冊文字來自其他來源者，以搜尋盤查來源並改來源。

## 3. 修改原則

「改來源不改產物」「撰寫要點之範例隨正文同改」「同類掃描涵蓋全部輸出」「新裁定可機械判定者入 lint」等通則依 skill[role-writer-validate] §7 之修正管線；成果類報告另有下列各點：

1. **共用資料之改動**：成果類報告之 md 與 docx 是純產物，來源含正文之產製程式、共用資料與分冊之上游（規格、手冊內容檔）。改共用資料前查會跟著變之報告，改後全部重產。
2. **規格與產品不符回規格**，再重產下游；畫面文字有錯者改產品與下游，不在報告端改寫。
3. **定稿句與既有裁定之例外不動**：查出之疑義列入回報待裁示，不自行改。可能有意見之定稿句，先提案再改。
4. **事實改了要回頭查因果**：改掉一個功能敘述，引用它之小結與開場也要重讀。

## 4. 修訂紀律

- **治語彙不拆結構**：裁定針對語彙（禁詞、稱謂）時，只替換語彙，不順手重構篇章。動手前先看前版，分析結構與語彙孰對孰錯，只動錯的部分。曾經委託單位審閱之結構是資產。
- **裁定者之指示是方向，不是成稿**：除明示逐字定稿者外，不原樣抄入，也不把方向性例句當句型套遍全部報告。給的範式先判斷屬於骨幹哪一節。
- **關鍵段落不一次成稿即交**：逐句分析 → 脈絡分析 → 至少 3 組候選 → 依五維度評比（〈文句與段落診斷〉第 2 節）。
- **修句要整句重讀**：改一個分句常使相鄰分句承接改變；連帶讀前後句。
- **不藉機夾帶**：改用字時不順帶改事實，改事實時另行核對。
- **裁定者直接改寫之版本**：比對差異，提煉原則（〈文句與段落診斷〉第 8 節），確認有無問題，只順必要之處並列出。
- **既有寫法不等於正確**：舊報告與原則文件之早期例句可能已被後續裁定取代，同一事項以較新之裁定為準。

## 5. 被指正時之補充（成果類）

通用流程依 skill[role-writer-validate] §7。成果類另加兩點：

1. **確認裁定者之改法有無問題**，不順處提出順句建議（〈文句與段落診斷〉第 8 節）。
2. **沉澱**：新裁定依〈落地到專案〉第 7 節寫入要點與 lint。

## 6. 回報內容（成果類補充）

通用內容（覆蓋聲明、逐句通讀與只以搜尋盤查之範圍、未讀完者明寫、候選與 lint 統計）依 skill[role-writer-validate] §8。成果類另列：

- 同步到哪些報告與文件。
- 定稿句與既有裁定之疑義，列入待裁示，附選項與建議；已裁定者不再問。
- 改了幾處、不改幾處與理由、依本技能哪些原則。

## 7. 交付前勾選（成果類專屬）

通用項（主張溯源、因果、文句、覆蓋聲明）依 skill[role-writer-validate] §8 之勾選與覆蓋聲明；本節只補成果類專屬項。全部打勾才可寫「完成」，否則寫「部分完成：做了 X，未做 Y」。本清單為摘要，各項之正本在所指之參考檔，兩處不一致時以參考檔為準。

**定位與敘事**

- [ ] 專案參數已查明；未裁定者依保守寫法並列入回報
- [ ] 語氣為確定語氣；無規劃類字眼；分年寫差異、全期寫全程；前期已有者未寫成新進度
- [ ] 無要點小標、無「標目＋長文」；條列皆為短項且其下無圖
- [ ] 上層開場只寫概要；共通功能與維護各只寫一次；一功能只在一段完整說明
- [ ] 引言以逗號接續；段首無「在○○上，」「○○方面，」與須回看前段之詞

**邊界**

- [ ] 無缺陷自陳、保證、承諾、展望與指責；無內部實況與人名
- [ ] 無開發端之擴充設計、產線由來、版本庫移轉、自有套件名（依專案參數第 26 項）
- [ ] 測試無案例數與結果；會被當成標準之數字已依專案參數第 17 項處理
- [ ] 「提供」「交付」之物皆載於交付文件

**亮點與圖**

- [ ] 亮點皆配圖；差異皆有文字；每張圖以原尺寸看過（紅框、圖名、測試字樣、可辨讀）
- [ ] 無前一期畫面；無臨時截圖；展示資料之標示依專案參數第 14 項
- [ ] 無段圖交錯；引圖句為段落最後成分；圖名末字為「圖」且不重複
- [ ] 自繪圖之方向與寬高比已量；圖內文字依同一份用字盤查

**附錄、小結與產製**

- [ ] 每份附錄於內文提及並說明可查得什麼；未虛構不存在之附錄
- [ ] 小結以系統為主語之因果句；末段點出核心與貢獻，未逐一重述亮點
- [ ] 定稿句一字未動；同步之他份報告已同改
- [ ] docx 已依 skill[role-writer-report-convert-to-docx] 第 7 節驗證

## 8. 反模式對照（成果類專屬）

通用反模式見 skill[role-writer-validate] §9。

| 反模式 | 為何錯 | 正確作法 |
|---|---|---|
| 把他案之裁定當本案規則 | 前提可能不成立 | 先問事實前提，查專案參數 |
| 例句照抄進報告 | 例句是示意，內容與專案不符 | 取其病理與句構，內容自專案查得 |
| 依小標順序逐項寫 | 明顯套版 | 大段敘述，順序隨系統而變 |
| 引言後接本來就有之功能 | 因果不實 | 基本功能寫基本運作段 |
| 把資料寫成主語 | 像資料自己會動 | 寫人或系統做動作，資料作受詞 |
| 小結逐一重述亮點 | 沒有高度 | 點出核心、好處，以長期特性收束 |
| 成果章放防禦句 | 模糊焦點，反被指推責 | 放測試附錄；主文至多一句中性指向 |
| 把裁定者告知之實況寫進去 | 那是給你判斷用的 | 改寫為正途之程序 |
| 放舊畫面作新舊對照 | 讓讀者看見舊版問題 | 只放當期畫面，差異以文字 |
| 臨時截圖補亮點 | 未經審定 | 依序補規格、標準圖、手冊 |
| 流程圖過寬就改 LR | 入報告後字過小 | 依分群收斂或拆圖 |
| 手改報告 md 或 docx | 下次重產即消失 | 改來源後重產 |
| 為語彙裁定重構篇章 | 破壞已審之結構 | 只替換語彙 |
| 方向性例句套遍全部報告 | 句型全同，又成套版 | 提煉傾向，用語有變化 |
| 中途丟一堆待確認給裁定者 | 未調研就交出判斷責任 | 查清楚，真判不了者完工一次回報，附選項與建議 |

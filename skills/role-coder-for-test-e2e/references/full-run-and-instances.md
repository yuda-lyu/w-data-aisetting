# 全量執行與多開：單趟收集（首選）／重產趟（次選）→ 審差異 → 採用／比對趟；埠位移之臨時實例

本篇是 SKILL.md §7.11（全量執行）與 §1.5（實例內單鏈、跨實例並行）的深入層。適用：一次跑完一個或數個專案之全部 e2e 流程——為報告取全量數字、套件或 Chromium 升版後之全面回歸、改共用層後之全面確認。單一流程之開發、追加案例、已知範圍之變更仍走 SKILL §7.6 之定點流程，不套本篇。**版本前提**：首選之單趟收集、重產趟之可設上限（`E2E_BASELINE_KEEP_SAME`／`E2E_BASELINE_KEEP_MAXDIFF`）與埠位移（`E2E_PORT_OFFSET`）皆需 w-package-tools-e2e ≥ 1.0.11（規格見其 README §2.8～§2.10）；未升版之專案依各處標示之專案層作法（退路）。

## 0. 名詞

| 名詞 | 意思 |
|---|---|
| 全量執行 | 本輪涉及之各專案（主系統與支援專案）之全部 e2e 流程各跑一次，取得可對帳之數字 |
| 收集趟 | 首選。全部流程以比對模式（mocha）加 `E2E_COLLECT=1` 執行：不符照存三聯組、續拍至案例末才拋彙整錯誤，不寫標準圖（≥ 1.0.11；§3 第 2A 步） |
| 重產趟 | 次選。全部流程以產製入口（直跑 `--baseline`／mocha `E2E_REGEN=1`，contract C13）之有變更才改寫模式執行（≥ 1.0.11：`E2E_BASELINE_KEEP_SAME=1`＋`E2E_BASELINE_KEEP_MAXDIFF`；< 1.0.11：套件 `--write-mode changed`），差異上限見 §3 第 2B 步；與「改 launch 旗標＝全量重產」（受影響範圍為全部之定點重產，SKILL §7.9 ①）不同 |

| 比對趟 | 次選路徑之第 4B 步：全部流程以比對模式（mocha）執行；**報告之數字只來自比對模式之執行**（首選路徑為收集趟與採用後之重跑，§3 第 4A 步） |
| 本輪副本 | 收集趟或重產趟之前各專案 `test/pics` 之完整複製；審查與還原（含否決之還原）一律以它為準，不以版控 HEAD 為準（專案常有未提交之標準圖） |
| 差異上限 | 產製端「有變更才改寫」之保留門檻（contract C13）。≥ 1.0.11 為 `E2E_BASELINE_KEEP_MAXDIFF`（`E2E_BASELINE_KEEP_SAME=1` 時才讀）：未設＝比對端容差（`maxDiffPixels`，預設 100）；`0`＝只保留 RGBA 逐像素相同者（pixelmatch 計數 0 而 RGBA 不同者——低於 threshold 之均勻色差、被忽略之反鋸齒像素——照寫，原因 `rgbaDiff(diff=0px)`）；`N`＝pixelmatch（`includeAA:false`，threshold 同比對端，同一套覆蓋）計數 ≤ N 保留。< 1.0.11 之 `--write-mode changed` 以比對容差為界、不可設，上限 0 須專案自寫開關，要連計數 0 而 RGBA 不同者一併審時用隔離輸出（§3 第 2B 步） |
| 案例清單 | 收集模式於每個有證據之目錄寫入之 `<案例鍵>__<時間戳>__collect.json`（`{ caseKey, outcome:'mismatch'｜'failed', error, cwd, records }`），供審查與採用工具辨識所屬案例、結局與正式標準圖路徑（≥ 1.0.11） |
| 實例 | 一組專屬之服務程序（前端、後端）、埠、資料庫目錄、可寫之實體檔夾、`test/_tmp/` 與 `./testPending/`；正式專案本身是一個實例（正式實例），以埠位移複製出者為臨時實例（§5） |

## 1. 為什麼不以一般比對趟起手

以一般比對趟起手時，凡套件升版、用語改動造成之標準圖過舊，都要「跑失敗 → 查因 → 逐案例重產 → 審 → 重跑該流程」，每輪都要人工介入；比對失敗即拋錯之案例，其後各張沒有比對也沒有失敗證據（§4），補齊還要再重產一趟。**首選以收集趟起手**：一趟比對（`E2E_COLLECT=1`）就得到每案每張之不符證據與候選標準圖（續拍至案例末），標準圖在採用前不動；人工只在審差異介入一次；省掉重產趟那一整趟全量執行，採用者之通過由採用本身決定。**收集趟之取捨**：只收超過容差、尺寸不同與缺標準圖者，容差內之有效改變（例如一個字）不收集也不失敗，與一般比對趟相同。**次選以重產趟起手**（共用層 < 1.0.11，或流程既未經 `runBaselineCase` 亦未包收集器）：一趟就得到每案每張之當次截圖，只寫出有變更者（`KEEP_MAXDIFF=0` 時連容差內之改變與計數 0 而 RGBA 不同者一併寫出）；人工只在審差異介入一次；比對趟驗證的是審過之標準圖，數字可對帳。

與既有鐵則之關係：重產趟之寫出、收集趟之證據都**不等於採用**——審差異後還原者不計為重產，未 `--accept` 者不計為採用；採用（`--accept` 或保留寫出）須經審差異，並於回報中逐張列出供使用者事後檢視（可否決，否決即還原）。授權見 §2。

## 2. 授權：分三種情境，不混用

| 情境 | 誰授權 | 授權涵蓋 | 仍須 |
|---|---|---|---|
| 定點重產（既有之單案例重產；UI 變更、helper 改動、追加案例等已知範圍） | 使用者，逐次 | 指名之流程、案例、語系 | 只產受影響者（`--names`／`--langs` 截圖前 gate）；審圖認可後才比對（SKILL §7.9） |
| 全量趟（單趟收集或重產趟） | 該專案之主責 agent（或主控）**自行發動，不必逐次請示**——重產趟之寫出、收集趟之證據都不等於採用 | 本輪全部流程之收集（不寫標準圖）或寫出（重產趟，有變更才寫） | 開跑前備份本輪副本；採用（收集趟 `--accept`、重產趟保留寫出）須經審差異（逐張分類；CHANGED 以改前改後並排圖目視裁定），審差異後還原或不採用者不計；審差異完成即 `--accept` 或跑比對趟；回報中**逐張列出採用之變更**供使用者事後檢視，使用者可否決，否決即自本輪副本還原並重跑該流程之比對 |
| 只取數字之全套（例：凍結碼上之最末全套、提示詞寫明「既有標準圖 0 張改變」） | — | 只跑比對趟，不重產 | 比對失敗依 pixel-mismatch-diagnosis 查因並回報，不在本輪重產 |

## 3. 步驟（順序不可調）

**第 0 步：開跑前核對**

1. 快照不含之實體檔依清單核對（contract C4 (c)）；缺檔即中止，自備份複製回來後重核，不帶著缺檔開跑——缺檔之症狀分散在不同流程且不直指根因，事後難以歸因。
2. 列出本機之 `baseline|mocha|後端` 程序，以監聽埠與命令列之路徑辨識各屬哪個實例；非自己啟動者先回報（SKILL §9.1），在它結束前不在該實例啟動任何鏈。
3. 定本輪名稱（如 `fullrun-<日期>`）；本輪之副本、log、審差異產物、臨時實例都放 `./tmp/<本輪>/`（隔離輸出放各專案 `test/_tmp/<本輪>-out/`），每條鏈之 log 檔名本輪未用過（SKILL §7.6 第 2 步）。`./tmp/<本輪>/` 在全部鏈結束、臨時實例移除之前不得清理（§5.2 第 1 點）。
4. 大量寫檔前確認磁碟剩餘空間（副本、截圖、臨時實例各佔一份）。
5. 列出預期清單：各專案 × 流程 × 語系 × 案例（取自各流程之 cases 宣告）；第 2、4 步據以核對沒有「未執行」。

**第 1 步：備份**

- 確認沒有任何鏈在跑（含其他實例——它們以連結共用標準圖夾）。
- 各專案 `test/pics` 複製到**全新**之 `./tmp/<本輪>/pics-before/<專案>/`（目標夾事先不存在）。Windows：`robocopy <專案>\test\pics <副本夾> /E /MT:32 /NFL /NDL /NJH /NJS /R:0 /W:0`——**離開碼 0～7 皆正常，≥ 8 才是失敗**；不用 `/MIR`。POSIX：`cp -a`。
- 核對：相對路徑清單相同且逐檔雜湊相同（檔數與總位元組只是快篩）；逐檔雜湊存為 `pics-before.sha256`，第 5 步據以核對。
- **開發用資料庫**：e2e 所用之資料庫目錄即開發用者（每案把快照複製進同一目錄），先停開發服務，連同其實體檔一併備份並核對後才開跑——否則第 5 步無從還原。
- 副本保留到本輪回報交付、採用之變更經認可之後才清。

**第 2A 步：收集趟（首選；w-package-tools-e2e ≥ 1.0.11）**

- **前提**：各流程經 `runBaselineCase` 比對端（`collect` 預設依 `E2E_COLLECT==='1'`）；不經 `runBaselineCase`、於 `it` 內逐階段呼叫 `assertBaselineMatch` 者，以 `createBaselineCollector({ caseKey }).run(async () => { … })` 包住案例本體（未設 `E2E_COLLECT` 時照常首張不符即拋，可常駐包著）。範圍外即使設了 `E2E_COLLECT=1` 仍照常立即拋錯，故未包者該案仍是首張不符即中止——改走 2B，或先包上再收集。
- **開跑**：於前一趟結束後記下開始時間 T；設 `E2E_COLLECT=1` 與 `E2E_STRICT_CAPTURE=1`（未 settle 即為截圖失敗、不被收集，免把不穩定之圖採用為標準圖），以逐檔隔離 runner（SKILL §9.2）跑全部流程；不設 `--baseline`／`E2E_REGEN`（兩者互斥，併用即拋錯）。
- **產出**：不符（超過容差、尺寸不同）照存三聯組 `./testPending/<標籤>__<時間戳>__{capture,baseline,diff}.png`；缺標準圖者存 `<標籤>__<時間戳>__capture.png`（候選標準圖）；案例末拋固定格式之彙整錯誤（首行 `截圖與標準圖不一致 ×<不符張數>/<比對張數> [<案例鍵>]: <標籤>(<狀態>), …`，狀態 `<N>px`／`尺寸不同`／`缺標準圖`／`比對錯誤`，解析式見套件 README §2.8），並寫案例清單（見 §0）。
- **取捨**：收集只收超過容差者，容差內之改變不收集也不失敗，標準圖維持過舊——要連容差內、計數 0 而 RGBA 不同者一併審的流程改走 2B（`KEEP_MAXDIFF=0`）。
- **逐案例記錄狀態**：通過／彙整錯誤（不符張數與各張狀態）／另因錯誤失敗（語意斷言、不變式、逾時等照常立即失敗，以該錯誤為準，案例清單 `outcome:'failed'`，**證據不可採用**）／pending（已知缺陷；已收集不符時不 pending，改拋彙整錯誤，回歸不被掩蓋）／未執行。mocha 比對模式下一案失敗不會中止其餘 `it`；以第 0 步之預期清單核對，「未執行」須為 0。
- 狀態表、log 與彙整錯誤存入 `./tmp/<本輪>/collect/`；長鏈依 SKILL §11.1；多開依 §5。

**第 2B 步：重產趟（次選；共用層 < 1.0.11，或流程既未經 `runBaselineCase` 亦未包收集器者）**

- 全部流程以產製入口之有變更才改寫模式執行（直跑型 `--baseline`；mocha REGEN 型 `E2E_REGEN=1`）。**≥ 1.0.11**：設 `E2E_BASELINE_KEEP_SAME=1` 加 `E2E_BASELINE_KEEP_MAXDIFF=0`，只保留 RGBA 逐像素相同者，其餘（計數 > 0，及計數 0 而 RGBA 不同者）皆寫出交審——容差內之差異也可能是有效內容之改變，例如一個字；只有審差異分辨得出。比對端覆蓋一律給 `runBaselineCase` 之 `compareBuf`（兩端共用同一函數，判定才看得到覆蓋）；暫時狀態圖（提示訊息滑入中、載入中轉圈、進度條）以 `transient` 宣告（既有者不改寫）；配自訂 `match` 時須明給 `maxDiffPixels`（或 `keepMaxDiff`／`KEEP_MAXDIFF`），否則於開瀏覽器前拋錯；啟用時 `--write-mode changed` 之容差判定由其取代（日誌原因 `changed→keepSame; …`），`--names`、`--write-mode all|missing` 先決、決定要寫者再經本判定。**< 1.0.11**：直跑型 `--baseline --write-mode changed`（以比對容差為界、不可設）加專案自寫之上限 0 開關，mocha REGEN 型以專案映射登錄之對應開關；無此開關者用下述隔離輸出。
- **差異上限之取捨與建議值**：建議值 **0**（≥ 1.0.11 即 `E2E_BASELINE_KEEP_MAXDIFF=0`）。代價是審差異之量增加——每張 NOISE 都要以差異圖裁切目視證明不落在內容變化上才能還原，不能證明者列 CHANGED 候審。改以比對容差（`maxDiffPixels`，預設 100）為上限則不必審 NOISE，但容差內之有效改變（一字之改之像素數依字型與字級而異，可能落在容差內）既不寫出、比對趟之 `[baseline-headroom]` 也只告警逾容差一半者，會完全看不到；介於 0 與容差之間之值沒有可證成之分界，不建議。NOISE 量大時（例：Chromium 或字型升版造成大面積細微差異）先依 pixel-mismatch-diagnosis 找共因（旗標、字型、版本）處理，不以調高上限掩蓋；目視可用差異外接矩形之裁切圖分批（一頁多張）進行以減輕負擔。
- **隔離輸出**（共用層 < 1.0.11 之退路——上限不可設；專案自寫之開關已支援上限 0 者照用，否則用本條。≥ 1.0.11 以 `KEEP_MAXDIFF=0` 即涵蓋計數 0 而 RGBA 不同者，不必為此用本條）：改以 `--write-mode all` 加 `E2E_BASELINE_OUT_DIR=test/_tmp/<本輪>-out` 執行，正式 `test/pics` 不動；第 3 步以 `compareImageDirs` 比對隔離輸出與正式標準圖，採用者才複製進 `test/pics`（第 1 步之備份照做，作核對基準）。`E2E_BASELINE_OUT_DIR` 不改寫參考片段（`_ref` 類）之自舉路徑，開跑前先確認參考片段皆已存在（contract §0.5〈遷移協定〉）。**不要以比對容差為上限替代**：容差內之改變既不寫出，比對趟之 `[baseline-headroom]` 也只告警逾容差一半者，小於一半之有效改變（一個字）會完全看不到。
- 一律 `strict` settle（SKILL §7.9）；產製端與比對端同一案例管線（SKILL §7.10）。
- **逐案例記錄狀態**：寫出（各張圖鍵）／保留（`[keep]`）／失敗（語意斷言或不變式；管線「任一斷言失敗一張不寫」，該案標準圖維持原樣）／pending（knownDefect）／未執行。失敗**只記錄、不在本趟補救**，交比對趟再判。產製入口遇一案失敗即中止整個流程者（contract C13 直跑骨架之迴圈直接 `await`），該流程其後之案例為「未執行」：以 `--names` 指定其餘案例續跑，直到每案皆有狀態；`finalize()` 之孤兒檢查另跑一次並記錄（其拋錯不代表案例失敗）。以第 0 步之預期清單核對，「未執行」須為 0。
- 狀態表、各流程之 `[write]`／`[keep]` 輸出與孤兒報告存入 `./tmp/<本輪>/regen/`。案例是否跑過以這些紀錄判定，不以圖檔 mtime 判定（保留之圖 mtime 不變）。
- 長鏈依 SKILL §11.1（明給 `timeout`；超過 115 分鐘 detached 執行並分段等待）；多開依 §5：臨時實例於第 1 步之後建立，通過 §5.2 第 7 點之等價驗證後才分配流程。

**第 3 步：審差異**

**首選路徑**：`node node_modules/w-package-tools-e2e/tools/reviewPending.mjs --since <T> --crops ./tmp/<本輪>/crops --json ./tmp/<本輪>/review.json`（套件 `reviewPendingShots`）讀 `./testPending` 各標籤最新一組證據並分類，只讀、不改寫標準圖；工具類別與下表之對應：SAME→SAME（罕見）、NOISE→NOISE（證據只在超過比對端容差時產生，故僅在 `--max-diff` 大於專案之比對容差時才會出現）、CHANGED 與 SIZE→CHANGED、MISSING（缺標準圖，capture 即候選標準圖）→NEW；另列所屬案例與結局，`failed` 者標「不可採用」。證據只含超過容差之張數，故 DRIFT 不會出現。

以本輪副本（隔離輸出時為正式標準圖）為基準逐張分類。工具以比對端同參數之 pixelmatch（`includeAA:false`、`threshold:0.1`、同一套覆蓋），另報位元組與 RGBA 是否相同及差異外接矩形；套件 `compareImageDirs` 可用。**內容類別**與**孤兒狀態**分兩欄記：

| 內容類別 | 判準 | 處置 |
|---|---|---|
| SAME | 位元組或 RGBA 相同（含有變更才改寫而未寫出者） | 不動 |
| DRIFT | 計數 0 而 RGBA 不同（≥ 1.0.11 設 `KEEP_MAXDIFF=0` 之重產趟照寫，原因 `rgbaDiff(diff=0px)`；< 1.0.11 只在隔離輸出時看得到；收集趟不收集） | 不寫回（已寫出者自本輪副本還原）；成因明確且已登錄漂移點者歸等價（SKILL §7.9），整片均勻之色差另查成因 |
| NOISE | 計數 ≤ 比對容差（`maxDiffPixels`），且以差異圖裁切目視證明差異不落在文字、圖示或元件之內容變化上 | 自本輪副本還原（隔離輸出時不複製）。計數逾容差一半者另依 SKILL §7.7〈餘裕〉查因。**不能證明是雜訊者不歸此類**，列 CHANGED 候審 |
| CHANGED | 計數逾容差、尺寸不同，或容差內而不能證明為雜訊 | 裁出「改前｜改後｜差異」並排圖逐張目視裁定：①改動之元件或文字（套件升版改了欄位、hover 色、用語）→ **採用**；②只落在不可固定之值 → 還原，並補遮蔽（SKILL §7.9 首條、unfixable-values-masking §4），同畫面同性質之值一併；③壞畫面 → 還原，先判成因：產品缺陷走已知缺陷協定（SKILL §7.5，不凍結），時序或環境造成者以定點重產該案例後再審 |
| NEW | 副本沒有、本趟寫出（收集趟：工具之 MISSING，缺標準圖） | 依 SKILL §7.6 第 3～4 步無框掃描並逐張目視；新增案例之圖須有對應 spec 視覺項 |
| MISSING | 副本有、本趟後檔案不存在（收集趟不寫不刪，不會發生；與工具之 MISSING〔缺標準圖〕不同義） | 查明原因；無正當理由即自副本還原 |

| 孤兒狀態 | 判準 | 處置 |
|---|---|---|
| 有宣告 | 有案例宣告此圖鍵 | — |
| 孤兒 | `finalize()`／`findOrphanBaselines` 列出（無案例宣告；檔案內容可為 SAME） | 對應案例已於 spec 廢止或改名 → 列入刪除清單、刪檔並回報；否則補宣告 |

- 每張寫出之圖一列：內容類別、差異矩形、對應之畫面元素、裁定與依據；**表不留空格**——空格表示還沒審，不是「沒問題」。
- **還原一律自本輪副本複製回來**，並以雜湊核對還原後與副本相同（版控取回會漏掉未提交之標準圖）。收集趟路徑中，「還原」＝不 `--accept`（正式標準圖未動，無須複製），其餘處置同。
- **審差異完成即進第 4A／4B 步**（全量趟之採用不等使用者事前認可，SKILL §7.9 ②）。採用清單（CHANGED 採用＋NEW 採用）與刪除清單**逐張列入回報**供使用者事後檢視，形式同圖文對照之審圖報告（dispatch-and-review-workflow §6）：每張附圖鍵、類別、變動原因，CHANGED 附改前改後並排圖，NEW 標「改前不存在」只附新圖；已有下游手冊者同輪更新。使用者否決者自本輪副本還原（雜湊核對），並重跑該流程之比對、回報兩次結果。
- 對帳（分項記，不合併）：重產趟寫出數＝NOISE＋CHANGED＋NEW（設 `KEEP_MAXDIFF=0` 者另加 DRIFT；隔離輸出時另加 SAME 與 DRIFT）；採用數＝CHANGED 採用＋NEW 採用；還原數＝寫出數－採用數（隔離輸出時為未複製數）；刪除數＝刪除清單；MISSING 逐張列。收集趟：不符標籤數（彙整錯誤之不符張數合計，同一標籤重跑者取最新一組）＝CHANGED＋NEW＋SAME＋NOISE；採用數＝`--accept` 標籤數；不採用數＝不符標籤數－採用數。數字對不起來即有圖未審、`--since` 取錯，或被兩條鏈寫過。

**第 4A 步：採用（首選）**

- 審畢後 `node node_modules/w-package-tools-e2e/tools/reviewPending.mjs --since <T> --accept <標籤,...> --dry-run` 先驗證，無誤去掉 `--dry-run` 再跑（API：`acceptPendingShots({ labels, since, dryRun, root })`）。`--accept` 即「採用」：把各標籤最新 capture 複製為正式標準圖，同樣須先審差異、逐張列入回報（授權見 §2）。
- 工具**先全部驗證才複製**，拒收：所屬案例 `failed`、案例清單衝突、證據過期（正式標準圖已與證據中之副本不同，或缺標準圖之證據而正式圖已出現）、capture 非可解碼 PNG、多個標籤指向同一正式標準圖（junction、符號連結、硬連結、大小寫別名皆視為同一）、無案例清單之證據（預設拒收；舊證據僅 API 明給 `legacy:true` 加 `pathOf`，CLI 不提供）、無證據；任一標籤不合格即全部不採用，離開碼 1。
- 比對端覆蓋後之證據：採用時覆蓋區內容取自舊標準圖（覆蓋區本不參與比對）；覆蓋區須為真實內容者（如新增之不可固定之值區）改以產製模式（定點重產）產該張。
- 採用後只重跑「另因錯誤失敗」之案例（修好後以一般比對或再收集一次）；純像素不符而採用者，其通過由採用本身決定（capture 即新標準圖），不必整趟重跑；回報要列其通過時，以 `runIsolatedE2e` 之 `targets`（檔＋`--grep`）只對採用之案例跑一次比對（不設 `E2E_COLLECT`），grep 對不到案例即失敗（自動 `--fail-zero`）。
- **報告之數字只來自比對模式之執行**（收集趟與重跑）：通過、失敗、pending（已知缺陷）、耗時；收集趟之彙整錯誤案例另列「標準圖不符：採用 n／不採用 m」，不與通過合併；採用者經上點重跑後計入通過。

**第 4B 步：比對趟（次選）**

- 逐檔隔離 runner（SKILL §9.2）跑全部流程；結果以 `<專案>-<流程>-<趟次>-<執行序號>` 命名各寫一檔（如 mocha JSON），兩條鏈、兩個專案之同名流程、同一流程之重跑都不寫同一檔；多開時見 §5.4。合併前以第 0 步之預期清單核對每個流程之結果檔都在。
- **報告之數字只來自比對趟**：通過、失敗、pending（已知缺陷）、耗時；重產趟之失敗不計入報告數字，只在對帳表出現。
- 比對趟之失敗依 pixel-mismatch-diagnosis 或回 spec 查因；若修正需要再重產，屬定點重產（§2 第一列），重產並經審後重跑該流程之比對，回報兩次結果。

**第 5 步：收尾（順序不可調）**

1. 停止本輪自己啟動之測試服務與臨時實例之服務，以 PID 與埠回驗已結束（舊行程仍持有資料庫時不可還原）。
2. 自第 1 步之備份還原開發用資料庫與實體檔，核對後重啟開發服務；以新行程確實在監聽該埠驗證（舊 PID 已消失、出現新監聽 PID、無綁定失敗），不以健康檢查回 200 判定。
3. 實體檔清單再核對一次（第 0 步之 1）。
4. 各專案 `test/pics` 以逐檔雜湊對 `pics-before.sha256` 核對：與副本不同者恰為採用清單（新內容）、NEW 採用（新增）與刪除清單（已不存在），其餘須與副本相同。`git status --porcelain -- test/pics` 只作輔助——開跑前已為 `M` 之檔再被改動，狀態仍是 `M`，看不出來。
5. 移除臨時實例（§5.5）；各實例之 `./testPending/` 先搬回正式專案（收集證據於移除實例前採用完畢，或搬回後以 `--root <正式專案根>` 採用，§5.4）。
6. 本輪副本保留至使用者完成事後檢視（否決之還原要用它）；必須先清 `./tmp/` 時，把採用與刪除清單所涉之改前圖連同清單移到專案內之證據夾（如 `spec/evidence/`）再清。**實例放在 `./tmp/` 下時，結案清理 `./tmp/` 前必須先拆除其中之連結並回驗**（§5.5 第 3～5 點），否則依全域之清理作法（如 robocopy 鏡像空目錄）會穿過連結刪到原專案。

**回報附對帳表與採用清單**：對帳表為各流程之預期案例數、重產趟各狀態數（首選路徑為收集趟各狀態數：通過／彙整錯誤／另因錯誤失敗／pending／未執行）、SAME／DRIFT／NOISE／CHANGED（採用／還原）／NEW／MISSING、孤兒與刪除數、比對趟通過／失敗／pending（首選路徑為採用後重跑結果）；採用清單逐張列出（第 3 步）供使用者事後檢視。人工介入只在審差異一次。

## 4. 比對失敗即拋錯之後果與對策

- 比對端遇第一張不符即拋錯者——流程中逐階段比對（截圖後當場比），或管線逐張比對而不續比——該案例其後各張沒有比對、也沒有 fail-dump；流程中比對者連截圖都沒有拍到。
- 因此未啟用收集時，`./testPending/` 之 capture **不是臨時標準圖**：不可整案複製進 `test/pics`——它只有第一張，且繞過了產製管線之語意斷言、覆蓋與 strict settle（SKILL §7.7「只經同一案例管線」）。補齊靠收集趟（≥ 1.0.11）、重產趟或定點重產。
- **收集模式**（w-package-tools-e2e ≥ 1.0.11，`E2E_COLLECT=1`）：不符記錄並續比，案例末才拋彙整錯誤，單趟即得完整差異（§3 第 2A 步）。收集證據之 capture 經同一案例管線（語意斷言先過，失敗之案例標 `failed`），仍不得手動複製進 `test/pics`，採用只經 `--accept`（驗證後才複製）。共用層 < 1.0.11、或流程既未經 `runBaselineCase` 亦未包 `createBaselineCollector` 者，依前條以重產趟補足。

## 5. 多開：埠位移之臨時實例

### 5.1 何時可多開、何時不得

- **同一實例內單鏈**：重產、mocha、探測共用該實例之後端與資料庫，同一時間只能一條（SKILL §7.6 第 2 步）。**跨實例可並行**：各實例之埠、後端、資料庫、可寫實體檔夾互不共用，單鏈鐵則之理由（互殺後端、互洗資料）不成立。
- **不得放到臨時實例之流程（只能在正式實例跑）**：①畫面或語意斷言之期望值含主機或埠者（分享連結、網址控制、API 網址、單一登入之轉址欄、參考文獻之瀏覽網址等）——在臨時實例跑，寫出之標準圖帶錯誤之埠；判準：該流程任一張標準圖或任一期望值含主機或埠。②依賴以固定網址登錄於外部服務者（外部回呼網址等）同理。
- **共用外部資源之流程**（同一真實收件匣、外部 API 額度）跨實例並行前，確認彼此不會讀到對方之信件或耗盡額度；不能確認就排在同一實例。
- **未通過首次等價驗證之實例**（§5.2 第 7 點）不得寫正式標準圖。
- **同一趟內同一流程只分配給一個實例**（標準圖夾以連結共用，兩個實例跑同一流程會寫同一檔）。
- 實例數依機器資源，先以兩個實例試跑並觀察 CPU、記憶體與逾時，再增加。

### 5.2 建立要點（以 Windows 實測；POSIX 對應寫法附後）

1. **位置**：`./tmp/<本輪>/inst<N>/<專案>/`，每個實例一個編號 N。臨時實例是一個完整之專案根，其資料庫、`test/_tmp/`、`./testPending/` 都在其中；`./tmp/` 雖是 AI 暫存區（SKILL §9.2 因其隨時可能被清而禁止測試使用），**實例存續期間 `./tmp/<本輪>/` 一律不得清理**，只在 §5.5 移除實例後才清——以此排除該風險。
2. **來源樹複製**：複製前先以 §5.5 第 3 點之方式（不跟進連結）列出來源樹內既有之連結，逐一決定排除或改為實體複製，複製後實例內之連結只容許第 3 點之兩項。排除 `node_modules`、`.git`、`test/pics`、`./testPending/`、`test/_tmp/`、`./tmp/`、資料庫目錄、可寫之實體檔夾（第 5 點另處理）、大型文件與產物夾；排除清單寫進映射表。Windows：`robocopy <專案> <實例> /E /XJD /XD <排除夾…> /NFL /NDL /NJH /NJS /R:0 /W:0`（離開碼 0～7 正常）——**來源樹內若已有連結，不加 `/XJD` 時 robocopy 會跟進連結把目標內容整份複製進來**；`/XD` 給名稱（`tmp`）會排除**任何層級**之同名夾，給完整路徑（`<專案>\tmp`）才只排除該一夾，原始碼內有同名子夾者（如 `src/…/tmp`）用完整路徑（以上皆 2026-10-28 實測）。POSIX：`rsync -a --exclude=…`（既有連結會原樣保留，故依本點開頭先處理）。
3. **以目錄連結指回正式專案者只限兩項**：`node_modules`（版本必與正式相同）與 `test/pics`（重產趟寫出直接落在正式標準圖夾，配合 §5.1 之流程互斥）。Windows 以 junction：Git Bash 寫 `cmd //c "mklink /J <連結> <目標>"`（`//c` 是 Git Bash 避免路徑轉換之寫法），PowerShell／cmd 寫 `cmd /c mklink /J "<連結>" "<目標>"`，路徑含空格者加引號；或 node `fs.symlinkSync(target, link, 'junction')`；POSIX `ln -s`。**可寫之狀態不連結**：資料庫、上傳與附件夾、`test/_tmp/`、`./testPending/`——連結會讓實例之寫入落進正式專案。以模組自身位置定位寫檔之套件（以 `import.meta.url` 決定輸出位置者）會寫進正式之 `node_modules`、由各實例共用，若其狀態會被並行寫入（如瀏覽器使用者資料夾），先確認可並行。
4. **埠整體位移**：所有服務埠加同一位移（+100×N 之類，位移後仍 ≥ 8000 且不與他專案相撞）。**≥ 1.0.11 一律用 `E2E_PORT_OFFSET`（非負整數；未設、空或 `0` 不位移），不改任何原始碼、不做文字取代**：該鏈之行程環境設 `E2E_PORT_OFFSET=<位移>`（其 mocha 與 spawn 之服務沿用 `process.env`）；專案 setup 須以基準埠宣告——`createServiceManager` 之 `services[].port` 寫基準埠，服務以 spawn 收到之 `port`（實際埠）啟動（命令列參數或環境變數，不在服務端寫死）；`baseUrl`／`apiBaseUrl`、設定檔內之埠（以 `createTempSettings` 之 overrides 寫入）、dev server 之 proxy 目標、`killPortListeners` 之對象一律經 `resolveE2ePort(基準埠)`（`probeHttp`、`killPortListeners`、`listenerPids` 不另位移，呼叫端組好實際埠再給）；格式錯誤或結果超過 65535 即拋錯，不靜默沿用基準埠。未依此宣告之專案先補 setup（contract C2〈埠與路徑可位移〉）。**< 1.0.11（或專案 setup 尚未依上述宣告）之退路**：專案已提供自讀位移量者（contract C2）只給位移量；沒有者以文字取代，**只改白名單路徑**（專案根之設定檔與程式碼、測試目錄），不碰資料目錄（資料內之數值會被誤改），取代後在白名單內搜尋舊埠字樣確認已無殘留、在白名單外確認未被改動。（以下兩點兩種作法皆適用）dev server 另插入埠設定時**不指定 host 為 `localhost`**（可能只綁 `::1`，setup 以 `127.0.0.1` 探測會判為未就緒，SKILL §9.3），沿用原專案之 host 行為。**多專案**（主系統呼叫支援專案之服務）：同一編號實例內之各專案一起建立、用同一位移（`E2E_PORT_OFFSET` 一個值；支援專案之 setup 亦須依上述宣告組埠）；列出每個實例內各專案之服務、端點與可寫資料之對應表，並以探測請求或服務日誌驗證實例內之跨專案呼叫都指向同一編號實例（不是正式實例之支援服務），未驗證不得並行。
5. **資料庫與實體檔**：資料庫自基礎快照建立，**不從正式實例執行中之資料庫目錄複製**（正式鏈每案重置資料庫，複製途中檔案被刪除重建即失敗或得到不一致狀態）；需以種子腳本重建者，一律以**實例根為 cwd** 執行（在正式專案根執行會改寫正式之資料與實體檔，contract C4 (c)）。快照所引用之實體檔依清單複製到實例並核對。
6. **就緒**：自實例根啟動服務（隱藏視窗），以位移後之埠探測健康；以監聽該埠之 PID 之命令列確認是本實例之行程，不是正式實例或他實例。
7. **首次等價驗證**：每個專案挑一條正式實例也能跑之流程，以同一版程式與資料，分別在正式實例與臨時實例以產製模式執行並以 `E2E_BASELINE_OUT_DIR` 寫到兩個隔離目錄（不動正式標準圖；`E2E_BASELINE_OUT_DIR` 不改寫參考片段（`_ref` 類）之自舉路徑，而臨時實例之 `test/pics` 連回正式，故參考片段須事先皆已存在），以 `compareImageDirs` 比較**兩次當前輸出**，須全為 SAME、已登錄之 DRIFT 或 NOISE。不與既有正式標準圖比——升版後它本就可能過舊。不符即查實例環境（埠殘留、資料不同、跨專案呼叫指錯實例），不得以該實例產正式標準圖。

### 5.3 流程分配

- 開跑前寫好分配表：每條流程 → 一個實例（含「須留正式」之理由），存於 `./tmp/<本輪>/`；派工模式下寫進計畫檔（dispatch-and-review-workflow §3）。
- 同一實例之多條流程串成一條序列鏈；各實例之鏈並行。每條鏈各自之 log、執行資訊（起訖、離開碼）、結果檔分開寫。
- 重產趟與比對趟可用不同分配，但每一趟都要滿足 §5.1。

### 5.4 結果分檔與合併

- 比對趟之結果以 `<專案>-<流程>-<趟次>-<執行序號>` 命名各寫一檔；執行資訊各鏈分寫，全部鏈結束後才合併為本輪總表，合併前以預期清單（§3 第 0 步第 5 點）核對結果檔齊全。
- 各實例之 `./testPending/` 失敗證據搬回正式專案之 `./testPending/`（檔名帶 ms 時間戳，撞名加序號，不覆蓋；SKILL §7.7）——它們在實例目錄內，移除實例時會一起消失。收集趟之證據連同案例清單（`*__collect.json`）一併搬回；案例清單記有比對時之工作目錄（實例根），搬回後採用給 `--root <正式專案根>`；實例之 `test/pics` 為連結者，在實例根下採用亦寫回正式標準圖夾，但須在移除實例之前（§3 第 5 步）。

### 5.5 移除實例：尚有連結時絕不可遞迴刪除

連結指向正式專案之 `node_modules` 與 `test/pics`。**2026-10-28 於 Windows 11 以假資料實測**：①以 robocopy 鏡像空目錄（`/MIR`，加 `/XJ` 或 `/XJD` 亦同）清除含 junction 之目錄，**會穿過 junction 把目標內容整份刪除**——這正是大量刪檔慣用之作法；②`dir /AL /S /B <實例根>` **會穿過 junction**，把正式 `node_modules` 內部之巢狀連結也列出來——依此清單逐一 `rmdir`，可能拆到正式專案內部之連結；③Git Bash `rm -rf` 與 node `fs.rmSync(…, { recursive: true })` 在同一測試只移除連結本身，但行為依工具與版本而異（PowerShell `Remove-Item -Recurse` 未實測），不可依賴。故一律：

1. 停止實例之服務（樹狀終止），以埠與 PID 回驗已結束。
2. 搬回 `./testPending/` 與需保留之 log（§5.4）。
3. **以不跟進連結之方式列出實例根下之全部連結**：node 遞迴 `fs.readdirSync`，每項以 `fs.lstatSync(p).isSymbolicLink()` 判定（Windows 之 junction 亦回 true），是連結即記錄且**不往下走**（2026-10-28 同一實測只列出實例自己的連結）；POSIX `find <實例根> -type l`（預設不跟進連結）。**不用 `dir /AL /S`**。枚舉失敗（權限、路徑過長）不得視為「沒有連結」。
4. 核對清單：每個連結之所有上層目錄都在實例根內且本身不是連結；清單應恰為建立時之連結（§5.2 第 3 點），多出者先查來源。逐一只拆連結：目錄連結（junction）Git Bash `cmd //c "rmdir <連結>"`、PowerShell／cmd `cmd /c rmdir "<連結>"`（皆不加 `/S`）；檔案連結 `cmd /c del "<連結>"`；POSIX `rm <連結>`（結尾不加 `/`）或 `unlink`。
5. **回驗**：再以第 3 點之方式列一次，須為空；正式專案完好——`node_modules` 內代表性套件存在、`test/pics` 逐檔雜湊與預期相同（§3 第 5 步第 4 點之核對）。
6. 回驗通過、實例內已無連結，才刪除實例目錄本身（檔案多時可依全域規範之大量刪檔作法，robocopy 與刪除分兩道指令）並確認已不存在。

**實例放在 `./tmp/` 下時，結案清理 `./tmp/`（或 `./tmp/<本輪>/`）前必須先依第 3～5 點拆除其中之連結並回驗**，否則依全域之清理作法（`rm -rf tmp/`、robocopy 鏡像空目錄）會穿過連結刪到原專案——上述實測 robocopy 會穿過、Git Bash `rm -rf` 未穿過，但不可依賴；連結清單不為空就不清。

## 6. 導入驗證（專案首次採用本流程時）

1. 對一個流程數多（如 20 條以上）之專案依 §3 跑一輪：重產趟寫出數、審差異各類數、比對趟通過數三者可對帳（首選路徑為收集趟不符數、審差異各類數、採用數與採用後重跑結果三者可對帳）；人工介入只有審差異一次。
2. 建兩個臨時實例跑互斥之流程子集；實例之輸出與正式實例等價（§5.2 第 7 點：同一流程在兩邊產到隔離目錄，比較兩次當前輸出）；依 §5.5 移除後，正式專案之 `node_modules` 與 `test/pics` 完整。
3. 全量執行前後各核對一次實體檔清單；刻意在專案根執行一次會改寫實體檔之種子腳本（於可還原之副本上），下一次核對應即攔下。

結果寫進專案規則帳本之 e2e 映射節（project-mapping-template〈全量執行與臨時實例〉）。

## 7. 常見失敗與對策

| 失敗 | 後果 | 對策 |
|---|---|---|
| 以一般比對趟起手、失敗後逐案例補救 | 多輪人工介入；中止之案例其後各張無證據 | §3 收集趟（或重產趟）先行 |
| 把 `./testPending/` 之 capture 手動複製為標準圖 | 未收集時只有第一張；繞過語意斷言與覆蓋；收集時繞過 `failed`、過期、衝突之驗證 | §4：以收集趟經 `--accept` 採用，或重產趟補齊 |
| 審差異以版控 HEAD 為基準 | 未提交之標準圖被當成新增或被錯誤還原 | 一律對本輪副本 |
| NOISE 一律還原、不看差異位置 | 一字之改等容差內之有效內容被丟掉 | 以差異圖證明為雜訊才還原；不能證明者列 CHANGED 候審 |
| 重產趟以比對容差為上限 | 容差內之有效改變不寫出、`[baseline-headroom]` 也不告警 | 上限 0（`E2E_BASELINE_KEEP_MAXDIFF=0`）；共用層 < 1.0.11 時用隔離輸出（§3 第 2B 步） |
| 產製入口一案失敗即中止，其後案例當成已跑 | 標準圖仍是舊檔、比對趟才發現 | 逐案例記狀態，以預期清單核對「未執行」為 0，以 `--names` 續跑 |
| 只落在不可固定之值之 CHANGED 只還原不補遮蔽 | 下次全量又寫出同一批 | 還原＋補遮蔽（SKILL §7.9） |
| 產製端無「有變更才改寫」 | 重產趟改寫全部標準圖，`git diff --stat` 失去判斷力 | contract C13 必備（≥ 1.0.11 用 `E2E_BASELINE_KEEP_SAME=1`）；未補前用隔離輸出 |
| 收尾先還原資料庫、後停服務；或開跑前沒備份開發資料庫 | 舊行程仍持有資料庫；開發資料無從還原 | §3 第 1 步備份、第 5 步先停服務再還原 |
| 首次等價驗證拿實例輸出比正式標準圖 | 升版後正式標準圖本就過舊，正確之實例被判不等價 | 兩邊各產到隔離目錄，比較兩次當前輸出 |
| 結案依全域作法清理 `./tmp/`，其下仍有實例之連結 | 穿過連結刪到原專案 | §5.5 末段：先拆連結並回驗，清單為空才清 |
| 以 `dir /AL /S` 列出連結後逐一拆除 | 穿過 junction 列出正式 `node_modules` 內部之連結，拆到正式專案 | §5.5 第 3 點：以不跟進連結之方式列出 |
| 在快照所依之專案根執行種子腳本 | 實體檔被換掉，下載、重複提示、比對結果散在各流程出錯 | 實例內一律以實例根為 cwd；第 0 步與第 5 步核對清單 |
| 畫面含主機與埠之流程放到臨時實例 | 標準圖帶錯誤之埠 | §5.1 留正式實例 |
| 自正式實例執行中之資料庫目錄複製 | 複製失敗或狀態不一致 | 自基礎快照建立 |
| dev server 指定 `localhost` | 只綁 `::1`，探測判為未就緒 | 不指定，沿用原專案 host 行為 |
| 以遞迴刪除或 robocopy 鏡像清除含連結之實例 | 穿過連結刪掉正式專案之 `node_modules` 與標準圖 | §5.5：先拆連結並回驗 |
| 兩個實例跑同一流程 | 同一標準圖被兩條鏈寫入 | §5.1 每趟每流程一個實例 |
| 把收集趟當成能抓到容差內之改變 | 容差內之有效改變（一個字）不收集也不失敗，標準圖維持過舊 | 要審此類之流程改走重產趟並設 `KEEP_MAXDIFF=0`（§3 第 2A 步取捨） |
| 審查或採用不給 `--since`，或前一趟未結束即取 T | 前幾趟殘留之舊證據被列為待審甚至被採用 | T 於前一趟結束後取；審查與採用皆給同一 `--since <T>` |
| 以文字取代整樹改埠（≥ 1.0.11） | 誤改資料目錄內之數值；漏改或多改 | `E2E_PORT_OFFSET`＋`resolveE2ePort`（§5.2 第 4 點） |

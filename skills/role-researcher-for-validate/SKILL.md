# 網路調研之通用驗證：摘要不是證據

## 0. 一分鐘看懂

**什麼時候用**：要把網路上查到之內容變成結論、建議或文件依據時。查得愈順、摘要愈漂亮，愈要照本技能走：搜尋結果之摘要與部分抓取工具之輸出是改寫過之摘要，會把不同方法、不同版本合併成一句通順之話。

**要交出什麼**（放 `./tmp/<案名>/`）：

| 檔 | 內容 |
|---|---|
| `research-sources.md` | 來源帳冊：每個來源之網址、等級、版本或取用日期、讀了哪些段、逐字摘錄（附頁碼或行號）；另列查詢紀錄（日期、查詢字串、是否為反向查詢） |
| `research-claims.md` | 主張帳冊：每條結論對到哪些來源摘錄、判定值；推薦之作法另記已知缺陷、後繼改良與驗證結果（腳本與 log 路徑）（Step 6、7） |
| `refsrc/` | 下載之原文（原始碼 raw 檔、PDF 與其抽出之文字），供 Grep 定位與複驗 |
| `review/` | 獨立複審之報告與你之核對紀錄（Step 8，有做才有） |
| 回覆 | 結論、證據等級、未讀原文者、未驗證者（Step 9） |

任務結束時 `./tmp/` 依全域設定清除；帳冊要留給第三者複驗者，移到使用者指定之位置（專案 docs 目錄，或隨回報附上）並說明。

**什麼叫完成**：每條結論都標明證據等級，其中寫成「一手已證」者對到一手來源之逐字摘錄，非一手者不得寫成已證；全稱主張列出成員；推薦之作法已驗證或標明未驗證；回報寫明證據等級、未讀原文者與未驗證者。

## 1. 三條鐵則

1. **摘要是線索，原文才是證據**。搜尋結果之摘要、抓取工具以模型回答提示詞之輸出、AI 概述、轉載、他套件內附之副本，都只能用來決定「去讀哪一份原文」。網址連得上（HTTP 200）只證明網址存在，不證明內容如所述（連結存活之檢查見 skill[role-coder-for-test] §6、skill[role-writer-validate] L0a，它們只管存在這一層）。
2. **全稱與歸類要逐一核對**。「各家皆…」「都採用…」要列出查過之成員與各自之原文；某文獻屬於哪一類方法，由該文獻自己之原文確認，不由他文之引用列表或摘要推斷；名稱或描述相近之不同方法、不同版本不得合併。
3. **推薦要經驗證，否則明寫未驗證**。調研結論若是「建議採用 X」，X 須實作或實跑驗證（計算類依 skill[role-researcher-for-calculation]）；做不到就寫「未驗證」，不寫成建議。

## 2. 來源分級

| 等級 | 例 | 可否當證據 |
|---|---|---|
| 一手 | 論文或技術報告原文（含作者自存版）、官方文件之對應版本、原始碼之上游 repo（標明分支、標籤或提交）、標準或規範原文 | 可，附逐字摘錄與版本 |
| 二手 | 教科書、綜述論文、維護良好之百科條目 | 可作背景；關鍵主張仍回一手核對 |
| 線索 | 搜尋摘要、抓取工具之模型摘要、AI 概述、論壇與部落格、轉載、他套件內附之副本或舊版鏡像 | 不可；只用來找一手來源 |

**版本與內附副本**：內附（vendored）指某專案把另一個專案之原始碼複製進自己之程式樹。這種副本可能落後上游，上游可能已大改（含修正你正要引用之缺陷），故列為線索。回答「某作法現在怎麼做」以上游現行版為準；回答「某已發布版本做了什麼」，以該版本之發布包或對應標籤之原始碼為一手來源（記版本）；兩者不同時兩者都記，並寫明你採用哪一個、為何。

## 3. 步驟

### Step 1 定題

寫下：要回答之問題（一句）、判斷「較好」之準則（精度、穩健、速度、相容、法規）、範圍（領域、版本、語言）。沒有準則就無法比較，只會收集。

### Step 2 取線索

- 至少三組查詢字串，含**反向查詢**：「X 缺點」「X inaccurate」「X known issues」「X deprecated」「X vs Y」「alternative to X」。只查正向會只看到推銷 X 之來源。
- 記下查詢字串與日期（絕對日期）。
- **隱私**：查詢字串與抓取之網址不得含使用者之專案名稱、路徑、資料內容、人名、內網位址或帳號；只用公開之技術詞彙。

### Step 3 取原文

- 論文：取 PDF 並抽成文字（PDF 處理依 skill[role-operator-pdf]），存 `refsrc/`，以 Grep 定位段落。抽出之文字常使公式與圖內數字錯亂或殘缺，關鍵公式與圖表之數字回 PDF 頁面（可轉圖）核對；摘錄之頁碼同時記文獻印刷頁碼與 PDF 頁序。
- 原始碼：取上游 repo 之 raw 檔（記下分支、標籤或提交與取用日期），不用他人內附之複本；要查某已發布版本之行為時，取該版本之發布包或對應標籤（見 §2）。
- 網頁文章：用 skill[fetch-web] 取純文字。它以 Readability 抽出文章主體，側欄、警語框、表格可能被丟掉；要讀之段落不在抽出之文字內時，改取原始 HTML 核對。
- **先弄清楚抓取工具回的是原文還是模型作答**：有些工具抓取頁面後，由小模型依你給的提示詞作答（例：Claude Code 內建之 WebFetch，其工具說明原文為 “Fetches a URL, converts the page to markdown, and answers `prompt` against it using a small fast model.”；fetch-web 則回 Readability 抽出之純文字）。模型作答型工具之輸出是改寫過之摘要，視同線索；要引用時要求逐字引文，並回到下載之原文用 Grep 核對，核對不到之句子視為線索。
- 原文網址失效時，以標題、作者、報告編號另找存放處，核對確為同一份後才用，並在帳冊記替代來源。
- 讀不到原文（付費牆、失效）者，該來源降為線索，並在回報中列為「未讀原文」。

### Step 4 來源帳冊（`research-sources.md`）

| # | 網址 | 等級 | 版本／提交／取用日期 | 讀的範圍 | 逐字摘錄（頁碼或行號） |
|---|---|---|---|---|---|

「讀的範圍」寫通讀或節錄哪幾段；只節錄者，結論不得超出所讀段落。

### Step 5 主張帳冊（`research-claims.md`）

每條要寫進結論之句子一列：主張、來源編號與摘錄、判定值（已證／部分屬實／查無依據／來源互相矛盾）。

- 全稱主張：列出成員，逐一附原文；有例外者改寫為「多數」並列出例外。
- 歸類主張（「A 屬於 B 類」「A 與 C 是同一種方法」）：附該文獻自己之原文。
- 數字：附原文之數字與單位，不用摘要轉述之數字。

### Step 6 找反例與後繼改良

對每個要推薦之作法：

1. 查它之**已知缺陷**：官方文件之警語（「inaccurate」「not robust」「deprecated」「known limitation」）優先讀；作者自述之限制段落必讀；上游原始碼之註解常自陳缺陷與其處置，也要讀。
2. 查**後繼改良**：之後誰引用它並提出改良；改良者常會說明前者錯在哪。
3. 查**版本差異**：上游現行版與你讀到之版本是否相同。

找到缺陷而仍推薦者，寫明缺陷與為何仍採用。

### Step 7 驗證推薦

- 推薦之作法須實作或實跑：計算類依 skill[role-researcher-for-calculation]；程式改動之完成判準依 skill[role-coder-for-validate]。
- 驗證只用了「順利之資料」者不算；要含該作法已知會失效之情形（Step 6 查到之缺陷）。
- 做不到驗證者，結論寫「調研建議（未驗證）」。

### Step 8 獨立複審（結論會用於決策、對外提出或改動共用程式時）

- 派給未參與調研者。派工、權限、逾時依 skill[dispatch-claude]、skill[dispatch-codex]、skill[dispatch-opencode]、skill[dispatch-antigravity]（能力下限見各技能之〈權限：先定能力下限，再往下收斂〉，dispatch-codex 為〈沙箱與網路：先定能力下限，再往下收斂〉）。那些技能所列複審之能力下限是讀檔、寫報告、唯讀查證，未涵蓋上網；要複審者自行上網，須另行放行搜尋與抓取工具，並以最小探測（抓取一個已知網頁並逐字引用其第 N 行）確認，不假設；確認不了就不派獨立調研，改派它審你的帳冊。複審者上網時，查詢之隱私限制同 Step 2。
- **先獨立、後查核**（兩階段，是調研複審之刻意安排：避免複審者被你的結論錨定）：第一階段之提示詞、工作目錄與開放目錄都不含你的帳冊與結論，只給問題與準則，由複審者自行調研並下結論。第二階段才給出你的主張清單，並比照各 dispatch-* 〈派什麼、怎麼驗收〉之順序（該節以輸入空間表為例，這裡把表換成帳冊）：先挑戰帳冊之完整性（缺來源、缺成員、摘錄與原文不符者附出處），最後才評方案。
- 收回後，對其推翻或新增之關鍵主張（影響結論者優先），自己打開原文或重跑其腳本核對，核對過才採用；未核對者不採用。

### Step 9 回報

第一段寫與先前說法之差異（含自己先前說錯之處）；其後依序：結論（每條附證據等級：一手已證／二手／未讀原文／未驗證）、未解決或需裁定之事（含未讀原文者、未驗證者）、來源清單（只列親自開過原文者；他人查得者註明出處）。

## 4. 典型錯誤形狀

- **把改良前後之方法合併**：依搜尋摘要寫「各實作皆以 A 法計算」並推薦 A；實際只有一家用 A，其餘皆用改良之 B，而 A 之已知缺陷正是 B 要解決的。提出 B 之論文又被誤歸為另一類方法。所引之 A 實作是他套件內附之舊版，上游已加上防護並在註解自陳 A 之缺陷。這些都是獨立複審打開原文才發現。
- **把抓取工具之摘要當原文**：工具輸出寫得像引文，實為模型依提示詞整理之摘要；據以寫入 issue 之「原文」與原始碼不符。
- **以可連當已驗**：參考文獻逐一驗 HTTP 200 即標「已驗證」，內容並未讀過。
- **只查正向**：查「X 之作法」得到之來源都在介紹 X，沒查「X 之缺陷」，推薦了已被取代之作法。

## 5. 完成前勾選

- [ ] 問題、準則、範圍已寫下（Step 1）
- [ ] 查詢含反向查詢；查詢字串不含專案或個人資訊；查詢紀錄已記入帳冊（Step 2）
- [ ] 每條結論標明證據等級；寫成「一手已證」者對到一手來源之逐字摘錄，並記版本或取用日期（Step 3～5）
- [ ] 抓取工具之摘要已回原文核對，核對不到者降為線索（Step 3）
- [ ] 全稱主張列出成員；歸類主張附該文獻原文；不同方法或版本未合併（Step 5）
- [ ] 推薦之作法已查已知缺陷與後繼改良，記入主張帳冊（Step 6）
- [ ] 推薦之作法已驗證，驗證結果記入主張帳冊，或標明未驗證（Step 7）
- [ ] 需要時已做獨立複審，且已親自核對其關鍵推翻項（Step 8）
- [ ] 回報第一段寫與先前說法之差異（含自己先前說錯之處），並附證據等級、未讀原文者、未驗證者（Step 9）

## 6. 與其他技能之分工

| 技能 | 分工 |
|---|---|
| fetch-web | 抓取網頁文章內容之方法；本技能管抓到之內容能否當證據 |
| role-operator-pdf | PDF 抽文字、轉圖 |
| role-researcher-for-calculation | 數值、幾何、統計與領域計算方法之調研：定義、算法、實作三層、對抗案例、參考解、領域適用性 |
| role-writer-validate | 報告之主張溯源；報告引用外部文獻時，其證據依本技能之一手來源與摘錄（其 L0a 只驗連結存在）。報告內各主張之判定值依該技能 Step 3；本技能之判定值只用於調研帳冊 |
| role-coder-for-test | 測試與樣本數據中之連結、引用須真實可連（§6）；本技能管內容是否支持主張 |
| role-coder-for-validate | 依調研結果改程式時之完成判準 |
| dispatch-* | 獨立複審之派工、權限與逾時 |

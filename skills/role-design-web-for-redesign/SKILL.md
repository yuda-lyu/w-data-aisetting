# 既有系統 UI 重新設計紀律

**觸發詞**(出現任一,一律當[整體重做]處理,不可降級成[調樣式]):「重新設計」「重做」「redesign」「要有設計過 / 設計感」,以及任何對美感 / 版面 / 比例 / 對齊 / 留白 / 風格的不滿.

**定位**:本技能管[改造既有 production 系統之 UI]——量測既有版面、盤點不可變資產、遷就既有組件庫與設計語言.從零產出獨立靜態 Web 產物(landing page / 簡報 / 儀表板原型)不適用本技能,改用 role-design-web-for-prototype 系技能;其中純美學通識(避開 AI 味、icon 選用優先序、placeholder 哲學)可另參 role-design-web-for-prototype 之[設計原則]節.production 系統多為被使用的工作畫面(監測、後台、儀表板、設定、清單),其數據展示、KPI、圖表、表格、零值與狀態、手機收合之細則見 skill[role-design-web-for-prototype] 之 `references/app-screens.md`;其預設禁令遇既有系統之設計語言(如既有深色玻璃主題)時,依該技能之[品牌破例]以既有系統為準.

**受眾分級(動工前先判定)**:依 skill[role-design-web-for-prototype]〈受眾分級〉判定本系統屬甲(政府機關對民眾公開網站)、乙(其他對外公開網站)、丙(科研數據呈現)或丁(單位內部使用系統),寫進設計方向說明;分級不明就問使用者.**無障礙只在甲、以及乙經使用者或客戶要求時必做**——下文第 17、19、21 條標[需做無障礙時]之項目,其餘分級不做;可讀性基本功(字夠大、灰字讀得清、手機按得到、有互動回饋)所有分級都做.production 系統多屬丙或丁.

**流程總覽**:進入後交付前必做,且**一次做完**(不逐點等使用者挑錯),依序五段:

| 段 | 條目 | 產出 |
|---|---|---|
| A. 動工前:盤點與基準 | 1–8 | 改前截圖與量測、API/設計語言/不可變資產/綁定關係/必保行為/技術棧清單 |
| B. 設計:方向與整體 | 9–15 | ≥2 方向與取捨、各區之展示手法 |
| C. RWD | 16–18 | 各區塊窄版設計、內容實寬計算、nowrap 清單 |
| D. 實作紀律 | 19–20 | 狀態齊全、樣式與動效守系統 |
| E. 驗收:改後證明 | 21–22 | 改前改後並排、寬度譜量測、功能回歸、評審、一次交付 |

## A. 動工前:盤點與基準

1. **改前基準**——動手前先把現況截下來並量好,這是改後對照的唯一基準:以第 18 條⑤之寬度譜(另加 1440)截取現況各狀態(resting / hover / 展開收合)存 `./tmp/<案名>/before/`,並把將要改動之區塊的關鍵數字(各區高度佔可視高之比例、間距、對齊線、各區實寬)記成一張表.沒有改前基準,改後的[變好了]就無從證明.
2. **讀完該元件 / 組件完整 API 與所有 prop 預設值**——陰影 / 邊框類預設常為 `true`,沒讀就會踩到(殷鑑:`WButtonChip` 的 `shadow` 預設 true,沒看到就多了不搭的投影).
3. **量測實際版面數字**——尺寸 / 間距 / 對齊 / 比例,用 `getBoundingClientRect`(可經 w-screenctl `/chrome/evaluate`;1.0.27 起須以 `--evaluate` 啟動並帶 Bearer token,啟動與呼叫範例見 skill[role-coder-for-test-e2e] §11.3)取真值,找根因並用數字佐證,不憑肉眼猜.
4. **盤點周邊設計語言**——色票 / 圓角 / 間距節奏 / 既有同類元件樣式,沿用求一致.
5. **盤點不可變資產與上游產物**:後端預產圖檔(底色/尺寸/內含標題)、API 產物格式、字型等——先實際抓一份樣本打開看,設計必須遷就,不可憑假設選色系(殷鑑:曾有監測頁後端產圖為白底,首輪重設計卻做深色系全滅).
6. **梳理資訊架構綁定關係**:動筆前把[選單-內容-附屬功能(搜尋/清單)]的歸屬與觸發鏈寫成清單(誰綁誰、點了切到哪、預設停在哪);版型可變、操作語意不可變,要變須先報備並經使用者同意(殷鑑:曾有地震事件搜尋樹綁定於地震事件選單,首輪設計拆成常駐側欄/水平帶被退).
7. **列出必須保住的行為**:改版範圍內每條路由、每個表單(送出/驗證/錯誤)、每個選單與切換、每個連結、鍵盤操作(Tab 順序、Enter/Esc)、資料綁定與自動刷新——逐項寫成清單,第 21 條逐一點過驗收.重新設計改的是呈現,不是行為;清單外的行為一旦壞掉,整輪設計都不算數.
8. **技術棧不遷移**:先讀清楚框架、樣式方法(Tailwind 先確認 v3 或 v4 再動設定、CSS modules、styled-components、SFC scoped 等)與組件庫;不遷移框架或樣式庫;新增任何套件前先查專案依賴檔,不憑印象 import.自有套件(`wsemi`、`w-*`)之組件不支援所需設計時,不在專案端改寫組件或繞道,依全域規範 §5 之自有套件通報流程處理.

## B. 設計:方向與整體

9. **提 ≥2 個設計方向,擇一並說取捨**,不直接微調現況.
10. **從整體決定**層級 / 比例 / 對齊 / 留白 / 動態,而非逐一 prop.
11. **換位置≠重新設計,沿用原展示語言≠重新設計**:把既有元素搬個位置(功能列上移/下移)、沿用原系統的高亮語言(如左緣 border 高亮)、沿用原本的區塊切分,都只是[配合原本的設計].重新設計的界線:**操作功能與流程(語意層)記好不可變,其餘版面/區塊切分/展示手法/視覺語言全部重新想**;交付前逐區自問[這一區的呈現手法是重新設計的,還是搬來的?]搬來的比例過高＝沒設計(殷鑑:曾有一輪選單高亮沿用左 border、功能列只是換位置被退).
12. **資訊權重與關聯性決定擺位**:每個元素先問[它屬於哪個資訊群?與誰一起被閱讀?]附屬資訊須緊鄰其所屬群組——如測站告示圖屬測站資訊,應與站名相鄰成[圖配文],不可因[右上角剛好有空間]把它放到設定/使用者資訊慣用區.版面慣性(右上=設定,右側=次要)會誤導擺位,以資訊關聯性優先(殷鑑:曾有告示圖被擺到右側像設定鈕被退).同性質元素同區歸位:摘要卡(如最新事件)與 meta 群同排;狀態文字(如刷新倒數)歸入導覽/工具帶置右,不散落各處(殷鑑:曾被要求併區).
13. **資訊匯總≠設計:數據區塊必須有展示設計**:把 label+粗體數字丟進區塊只是[把資訊匯總過來放],不是設計(殷鑑:曾有監測通道 panel 僅文字+粗體數字被評[這哪叫設計]).動工前**上網調研業界數據展示實例**並說明參考來源,再為每類數據依[它回答什麼問題]選展示形式(細則見 skill[role-design-web-for-prototype] `references/app-screens.md` §5–§6):
    - **形式**:隨時間變化 → 一條線(直線段、3–5 條淡格線、不畫資料點);每期多少 → 直角長條;佔比 → 細環或 100% 堆疊條(最多五份);離目標多遠／用量 → 兩端標示、填色為真實比例的進度條;排名 → 排序過的橫條清單;狀態 → 淡底配同色相深字的膠囊(每列一個).
    - **KPI 以字的層級表現**:標籤在上(灰、一般大小寫)、數值大一級(約 1.7 倍)、回答畫面主問題的那個數字最大;變化量用文字寫出比較窗口(「與前 30 天比」),**顏色表示好壞而非升降**(延遲、錯誤率上升是壞消息),零或無法比較的變化用灰色.
    - **說明放在答案旁**:關鍵事件在圖上註記原因(1px 標記＋12px 標籤),參考線(門檻、目標)用 1px 虛線並在末端標示;主要資料元素帶畫面唯一的色相.
    - **不做**:每個 KPI 放迷你走勢線、彩色圓圈 icon 或淡色磚——趨勢放在自己的圖裡.
    與 skill[role-coder-for-ui] §3 相輔:該節管型別錯配,本條管[型別對了但零視覺設計].
14. **icon 語彙是重新設計的一部分**:調研參考範本時同步萃取其 icon 用法;meta chips/導覽項/分類標籤等資訊元素應配可辨識之 icon(inline SVG,非 emoji,語意對應:座標=定位針,波形=地震…).查了一堆參考卻交出純文字 chips＝調研成果沒帶回設計(殷鑑:曾有座標/鑽孔/地震事件 chips 純文字,被質問[查了這麼多資料 icon 都沒有?不可能吧]).樣式:全畫面一套、統一描邊粗細之線框、14–20px、放在標籤前,依文字色或灰色;不放在彩色圓圈或方塊裡,不為每個類別配不同顏色(顏色若要用,放在數字上;見 app-screens.md §9.4).
15. **資料驅動元素須生成式設計＋邊界處理**:數量由資料決定的元素(感測器 n 支,欄位 n 個)必須實證資料結構後以資料生成,並處理 n 變化之邊界(標籤/按鈕防重疊,最小與最大 n 之版面);寫死示例數量＝沒抓到業務結構(殷鑑:曾有水壓計每站 1~3 支,前 4 輪一直畫成 1 支;深度導航被要求支援多水壓計+防重疊).

## C. RWD

16. **RWD 是交付的一部分,且是逐區塊的設計而非只做抽屜顯隱**:各斷點行為(顯隱鈕、抽屜浮動/收合、控制列摺疊)須設計且可實測;缺 RWD 之設計視為未完成(殷鑑:曾有首輪 5 版全數未設計顯隱抽屜被退).**每個區塊都要問[窄版時它變成什麼樣?]**,禁止放任 flex-wrap 自動往下疊交差:①資訊磁貼/按鈕帶→窄版改單列橫向捲動或壓縮款式,header 不得吃掉過半可視高(比例原則:內容展示區永遠是主角);②工具列/選單列→縮 padding 與字級,右端狀態元素(倒數/計數)須 `flex:0 0 auto` 保證可見,不可被擠出;③內容區 padding 須與版面連動——窄版空間已少,水平 padding 要縮小讓內容(圖/表)展示最大化,寫死大 padding=沒設計;④交付前以窄版實寬截圖逐區檢查高度比例與可見性(殷鑑:曾有監測頁頁首磁貼窄版直落疊半屏.倒數被擠出.padding 不連動,被評[隨便亂設計亂排就交差]).
17. **側欄/導航面板之 RWD 一律沿用系統既有抽屜慣例**:新設計的任何側欄(導航,清單,面板)比照主系統抽屜模式——寬版可收合(如 30px 軌條+顯隱鈕),窄版浮動覆蓋+遮罩+顯隱鈕;每加一個側欄都自問[窄版怎麼辦?](殷鑑:曾有深度導航首版窄版直接 display:none 被要求改抽屜).互動導航點擊須有回饋動畫(如平滑捲動),不可瞬跳.收合後仍須可用:
    - 顯隱鈕用真正的 `<button>`;窄版(觸控)顯隱鈕要好按(約 44px).
    - 收合後仍顯示的軌條與顯隱鈕,不可放在 `hidden` 或 `inert` 的祖先元素裡(`inert` 會連滑鼠點擊一起停用,軌條就點不到了).
    - 收合時被藏起的展開內容不可再被點到或互動(`hidden`、`display:none` 或 `inert`).
    - 只剩 icon 的軌條:hover 時顯示 tooltip;目前所在項目維持高亮.
    - **需做無障礙時**另加:顯隱鈕有無障礙名稱(`aria-label`)與 `aria-expanded`,鍵盤可操作且 focus 可見;被藏起的內容同時移出 Tab 順序——**只加 `aria-hidden="true"` 不會把子孫移出 Tab 順序**,過場動畫期間仍須渲染時自行管理 tabindex;只剩 icon 的軌條把標籤文字留在 DOM(視覺隱藏),鍵盤 focus 時也顯示 tooltip;觸控目標 44×44 為合規門檻.
18. **RWD 五鐵則——斷點是手段,內容實寬才是事實**(殷鑑:曾有監測頁選單列/磁貼帶一日連退四輪,每輪都是打補丁而非整體設計):
    ① **先算後排**:動工前逐項計算內容帶實際總寬(字數×字寬+icon+padding+gap,rem 記得乘 root 字級);內容實寬(如 1060px)大於你設的斷點(660px)時,中間全是災區——優先採與寬度無關之通用結構(固定區+`flex:1; min-width:0`+內部橫捲),讓版面自適應而非猜斷點.且[固定區+flex:1]結構須以**可變文字之最長情境**檢核(站名/地址長短組合):固定區實寬佔比過大時,flex 區會被擠成窄縫還在縫裡開捲軸——剩餘寬低於合理下限即改上下斷行成列,兩者各得全寬(殷鑑:曾有頁首窄版識別區吃掉大半寬,磁貼帶剩窄縫被批[重要資訊只能用超窄區塊呈現]).
    ② **nowrap 全數列管**:每個 `white-space:nowrap` 都是溢出炸彈,會把整版推移裁切且無捲軸可救;動工前列 nowrap 清單,逐個給[空間不足時的讓位策略]——標籤縮短/次要字隱藏/換行——並於捲動容器加 `overflow-x:hidden` 保險.
    ③ **狀態元素永不犧牲**:倒數/計數等狀態元素 `flex:0 0 auto`,被裁到剩[9 分]的倒數＝沒有倒數;空間不足時由主功能群讓位,而讓位手段首選**標籤縮短**(語意不變+tooltip 全名),**禁用[群組內捲動+藏捲軸]於選單類**——內部剪裁會造成[被旁邊元素遮蔽]的假象,比溢出更像壞掉.
    ④ **讓位是設計不是位移**:把元素移位/疊上去/剪一半都不是 RWD;每次調整後自問[各元素在此寬度下是否完整可見.互不遮蔽.比例合理?]
    ⑤ **驗證掃寬度譜**:至少 320/360/430/660±20/768/1024 逐寬量測斷言(單列性,右端元素完整可見且不與鄰元素重疊,`scrollWidth≤clientWidth`);只驗單一寬度＝沒驗(殷鑑:只測 430 一點,331/731 全漏).

## D. 實作紀律

19. **互動狀態逐一盤點**:改版範圍內每個可互動元素都要有完整狀態,並沿用第 4 條盤點的色票——
    - hover(放在 `@media (hover: hover)` 後面,免觸控點一下就卡住)、active/按下(輕微 `scale(0.97–0.98)` 或位移 1px)、disabled(仍須清楚可讀,並說明為何停用;30% 不透明度之類讀不清的停用＝缺陷).**需做無障礙時**另加 `:focus-visible`(鍵盤可見的焦點框,不可移除)與完整鍵盤操作.
    - 導覽標示目前所在頁;連到 `#` 的死連結不可留——接上真實目的地,或明確呈現為停用.
    - loading:以最終版面為底、每個數值換成同尺寸的平塗灰條(列高不變),不用閃光漸層,資料抵達時版面不位移;已在畫面上的資料重新整理時保留舊值、更新時間戳記.
    - empty:保留區塊外框與標題,加一句說明與下一步動作,不是整塊空白.
    - error:在失敗的那一塊裡說明什麼失敗、最後一次正常是何時,附重試;不用全畫面橫幅,不用 `window.alert`(見 skill[role-coder-for-ui] §2).系統訊息直說事實與下一步(「無法儲存變更,請重試」),不用「哎呀!」、成功訊息不加驚嘆號.
    細則見 app-screens.md §11.
20. **樣式與動效守既有系統**:新樣式寫進專案既有的樣式方法,不另起一套;顏色、間距、圓角只取第 4 條盤點的 token;z-index 沿用專案既有的層級值,不自創 `9999`;全屏區塊用 `min-height: 100dvh` 而非 `height: 100vh`(行動瀏覽器網址列伸縮會讓 vh 跳動);動畫只動 `transform` 與 `opacity`,不動 `top`/`left`/`width`/`height`.

## E. 驗收:改後證明

21. **改後證明,逐項對照第 1、7 條**:
    - **截圖**:以第 18 條⑤之寬度譜(另加 1440)截取改後各狀態(resting / hover / 展開收合 / loading / empty / error;需做無障礙時加 focus),存 `./tmp/<案名>/after/`;截圖用 Read 讀進對話前,先以 `file <圖檔>` 確認是 PNG(內容不是合法圖片時讀進來會讓整個 session 永久壞掉).
    - **改前改後並排**:每個寬度把 before 與 after 並排比對;第 1 條記下的數字改後複量,前後並列寫進回報(例:「430px 下頁首佔可視高 52% → 18%」).
    - **功能回歸**:第 7 條清單逐項實際點過——路由、表單送出與錯誤、選單切換、搜尋、原有的鍵盤操作、自動刷新——全部仍正常才算完成.
    - **無障礙檢測(需做無障礙時)**:skill[role-design-web-for-prototype]〈受眾分級〉之無障礙項目逐項驗證,並以 axe-core／Lighthouse 或該案指定工具檢測.
    - **截圖評審**:以 skill[role-design-web-for-prototype] `references/critique.md` §3 工作畫面七問(被閱讀的頁面用 §2)評審改後截圖,寫下前三個問題並修正,最多三輪.
22. **一次交付完整設計 + 理由**:兩個以上方向的取捨、最終設計、改前改後並排與數字對照、功能回歸結果、仍未解決的問題,一次交出,不逐點等使用者挑錯.

## 間距與對齊原則

- **間距對稱**:水平與垂直留白不必完全相等,但比例差距不可過大;尤其值小時(如 5px vs 14px)差幾 px 觀感差異就很大,須拉近比例(值大時差幾 px 才不明顯).
- **同列共用底緣**:同一列的卡片底緣對齊;卡片群內的按鈕或動作釘在各卡底部,不論上方內容長短都排成一條水平線;內容平衡不了時讓短卡內容靠上、把動作或總計釘在卡底,不要把卡框拉長蓋住一片空白.
- **並排元素的共用部分對齊**:並排的卡片、欄、面板,其標題、說明、數值、清單起點落在同一條 Y 線上;基線錯落看起來就是壞掉.
- **一個間距值,算式要閉合**:同一區塊水平與垂直用同一個 gutter;並排區塊的寬度加總寫成算式確認閉合(例:3×372 + 2×17 = 1152),不讓卡片停在離容器右緣差一截的地方.
- **視覺校正**:數學置中不等於看起來置中——文字旁的 icon、圓內的播放鍵、按鈕內文字常需 1–2px 校正,以截圖確認.

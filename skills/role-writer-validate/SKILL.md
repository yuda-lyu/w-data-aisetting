# 報告／文章撰寫自檢規範：只相信能驗證的

> 請照章節順序執行，每一步都要留下指定的產物檔；不要跳步，不要用「我已確認」「看起來沒問題」取代產物。步驟可以合併，但產物與回報格式不可省略。專案或派工另有規定（證據存放位置、回覆格式、執行慣例、提示詞模板）時，位置與格式依其規定；產物、統計與覆蓋聲明照樣要有。

## 0. 一分鐘看懂：什麼時候用、要交出什麼、什麼叫完成

**什麼時候用**：你寫了（或正在改、正在審）一份描述系統、程式、資料或需求的文字——報告、技術文件、分析文章、審計結論、交付說明——而且它會被人拿去做決定。宣告完成之前、被指出錯誤之後、審別人的報告之前，都要走一遍本技能。

**要交出什麼**（全部放在 `./tmp/`，或使用者指定的專案 docs 目錄）：

| # | 檔案 | 內容 | 對應層 |
|---|---|---|---|
| 1 | `validate-plan.md` | 這份報告屬哪一類、做哪些層、不做哪些層與理由 | §5 決策表 |
| 2 | `validate-entities.md` | 實體帳冊：報告提到的每個名字是否真的存在 | L0a |
| 3 | `validate-requirements.md` | 需求對齊矩陣：每條需求對到哪一節 | L0b |
| 4 | `validate-claims.md` | 主張帳冊：每句事實描述的證據與判定值；含執行紀錄 | L1、L2 |
| 5 | `validate-wording.md` | 文句與因果審閱帳冊：候選、審閱者回報、作者核實結果（做 L1b 時才有） | L1b |
| 6 | `validate-coverage.md` | 盤點對照表：該寫到的東西有沒有寫到 | L3 |
| 7 | `validate-rules.md` | 交使用者或專家逐條確認的規則清單（做 L4 時才有） | L4 |
| 8 | 回覆末尾 | 覆蓋聲明（§8 模板） | 全部 |

**什麼叫完成**（三件同時成立才可以寫「完成」）：

1. 決策表要求的層全部做完，而且每份產物沒有空白格。
2. 每一個發現都已處置：修報告、修系統、改成推測語氣、或刪除。
3. 回覆附覆蓋聲明；沒做的層寫明原因。

## 1. 名詞定義

| 名詞 | 意思 | 例子 |
|---|---|---|
| 實體 | 報告中可以用工具查「存不存在」的名字 | 檔案路徑、函式名、選項或旗標、設定鍵、API 端點、i18n 鍵、資料表或欄位名、套件名與版本、URL、報告編號、法規條號 |
| 主張 | 報告中一句可以被問「有什麼證據」的事實描述 | 「轉接器預設沙箱是 workspace-write」「每日約 1,200 筆」「設定未完成時所有命令會被擋」 |
| 證據 | 能讓第三者自行複驗的來源 | `檔案:行號`、測試名稱、執行 log、spec 段落編號、已驗證可連的外部文獻 |
| 可執行者 | 報告中可以真的跑一次的東西 | 指令、範例程式、API 呼叫、統計數字的產生步驟、截圖 |
| 需求條目 | 需求文件、招標需求、spec、使用者原話中，可以獨立回答「有沒有回應」的一條 | 「須支援上市與上櫃」「每日 17:00 前完成」 |
| 盤點項 | 從系統或需求反向列出的「應該被寫到的東西」 | 所有 opt 鍵、所有錯誤路徑、所有步驟、所有枚舉值、所有同類的兄弟元素 |
| 兄弟元素 | 同一類別裡的其他成員 | 報告寫了「節點」的刪除行為，「邊」「把手」「畫布」就是兄弟元素 |
| 產物 | 一份別人可以逐格檢查的表或紀錄檔 | §0 列的檔案 |
| 現行執行路徑 | 從入口（排程、路由、畫面、指令）走得到的程式；被註解、未接上之備案、預設關閉者不算 | 入口只呼叫 A 版；B 版檔案存在但無人呼叫 |
| 候選 | 工具依形式特徵列出的待判讀位置，不是結論；0 筆也不代表乾淨 | 同段連用兩個「此外」 |
| 未參與撰寫者 | 沒看過作者的結論與草稿過程的新 context（另一個 agent 或人），只拿到報告與判準 | 新開的子代理 |

## 2. 本技能要抓的四種錯

| 模式 | 定義 | 在報告上的症狀 | 靠哪一步抓 |
|---|---|---|---|
| 漏列（the miss） | 該寫的沒寫；寫出來的每一句都對，但不完整 | 需求 12 條只回應 10 條；選項表少列旗標；只寫成功路徑沒寫錯誤路徑；只寫一種語系或平台；寫了節點沒寫邊 | Step 2 需求對齊、Step 5 反向覆蓋 |
| 捏造（the hallucination） | 看起來合理，但不存在或不為真 | 不存在的 `檔案:行號`、函式名、旗標、設定鍵、版本號、URL、報告編號、法規條號；讀程式碼推論出來的行為卻寫成「實測」；數字沒跑過就寫；拿 google 搜尋頁當參考連結 | Step 1 實體存在、Step 3 主張溯源、Step 4 實跑 |
| 誤解（the misinterpretation） | 需求略含糊，盡力做了仍做錯 | 要「彙整」卻寫成「逐條翻譯」；要驗收文件卻寫成技術筆記；讀者或語體錯；使用者問的是一整個類別，你只回答投訴的那一句；spec 有歧義，自己挑一種解釋沒有說 | Step 0 讀懂任務、Step 6 專家確認 |
| 因果不實（the unsupported cause） | 關係是作者補的：拆開每個事實各自為真，但「為、故、使、以免」所接的目的、原因或效益，機制看不出 | 虛構例：「搜尋改為分頁載入，以降低伺服器負載」（分頁載入是真的，降低負載是補的目的）；通則換對象（「快取可加快查詢」為真，套到不經快取的查詢就不成立） | Step 3 證據門檻與因果五問、Step 3b |

前三種錯有一個共同根因：**context rot**——對話越長，模型對中段內容的記憶越差，長報告的末段最容易與前段矛盾、或漏掉前段承諾的事。因果不實的成因不同（研判）：提交紀錄只記做了什麼、不記為什麼，作者為了讓句子有因果，會補一個看似合理的目的，且這類句子通順、lint 全過。所以：報告超過約 300 行時，先分段自檢，最後再做一次整篇一致性掃描（同一個實體在各段的描述是否一致；前段寫「見第 5 節」，第 5 節是否真的有那件事）。一致性用 grep 對照，不靠記憶。

## 3. 三條鐵則

驗證有三個角色：**人**、**AI**、**確定性工具**（grep、curl、測試、腳本）。任何一方單獨都做不到規模化，三者要輪流上場。每兩個角色的配對各有一個典型失敗，翻成三條鐵則：

**鐵則一：被抓到一處錯，不可以只改那一句。**（人＋AI 的失敗：「你說得對」——人抓到一個錯，AI 只修那一個，不找為什麼會錯。）
做法：先把這個錯歸類成漏列、捏造、誤解或因果不實的哪一種；寫下「同類判準」（例如「所有沒附產生腳本的數字」，要寫到病理，不是字面）；依判準逐段掃描全文找同類；全部修掉；再重跑受影響的層。詳見 §7。

**鐵則二：格式工具通過，不代表內容正確。**（AI＋工具的失敗：「我徹底辜負了你」——markdown 渲染正常、連結全部 200、拼字檢查通過，內容卻是錯的，綠燈直接交付。）
做法：把「工具通過」只當作 L0 的結果；內容是否正確，只能靠 L1 到 L4（溯源、文句與因果審閱、實跑、反向覆蓋、專家確認）。回報時不可以用「連結都通」「格式沒問題」暗示內容正確；lint PASS、掃描 0 筆、審閱通過也一樣。

**鐵則三：會重複做的手工檢查，要寫成腳本。**（人＋工具的失敗：「這也要自動化？」——30 個 `檔案:行號` 用眼睛對，改一版又要重對，第三版就沒人對了。）
做法：實體存在、連結存活、數字重算，第一次做就寫成 `./tmp/` 下的腳本；每次改版重跑。判準很簡單：一件手工檢查只要 5 秒，但報告會改 10 版，就值得自動化。但要分清：確定性檢查（實體存在、數字重算、禁詞 lint）命中即違規；只能列候選的掃描（連用承接語、概括句）命中只是待判讀的位置，須人判讀，不可當結論，也不可整批依候選改。

## 4. 每個檢查先回答六個問題

在執行任何一項檢查之前，先回答：

1. **檢查什麼？**——具體跑什麼、審什麼、量什麼。
2. **建置成本？**——時間、專業、需不需要拿到程式碼、資料或環境。
3. **誰執行？**——確定性工具、AI、人，或組合。
4. **實際證明了什麼？**——誠實寫出這項檢查「只」能證明什麼。例如：連結回 200 只證明 URL 存在，不證明那頁內容支持你的主張。
5. **產物是什麼？**——一份具體、可勾選、可以直接據以修改的東西。
6. **有什麼工具可用？**

第 5 問答不出來的檢查不算檢查。粒度的差別像這樣：

- ❌「請領域專家讀完這 2,500 字，告訴我對不對。」——產物是一句「大致沒問題」。
- ✅「我從報告抽出 18 條業務規則，請專家逐條確認或更正。」——產物是 18 格勾選與一個更正率。

六問卡的空白範本在 [references/產物範本.md](references/產物範本.md) §0。

## 5. 報告驗證分層表與選層決策表

依原框架的「文件／反向工程」階梯改寫為報告用。原則：**由低往高做；每一層都留產物；做到哪一層、哪幾層沒做，寫進回報。**

| 層 | 檢查什麼 | 怎麼做 | 產物 | 這一層證明了什麼 | 這一層不能證明什麼 |
|---|---|---|---|---|---|
| L0a 實體存在 | 報告提到的每個實體都真的存在 | 依 §6 Step 1 的查證方式表逐一查；寫成腳本 | `validate-entities.md` | 沒有捏造的名字 | 對該實體的描述是否正確；該實體是否在現行執行路徑上（要看 Step 3 證據門檻） |
| L0b 需求對齊 | 每一條需求都對得到報告的某一節；結構符合文類規範；術語一致；日期是絕對日期 | 需求逐行從原文取得並編號，做需求 × 章節矩陣 | `validate-requirements.md` | 沒有整條需求被漏掉 | 回應的內容是否正確 |
| L1 主張溯源 | 每句事實描述都指到證據，且證據通過證據門檻；因果句的目的與效益由機制看得出 | 先抽樣一節做，再做全量（成果／進度報告的期間改動句直接全量）；證據優先順序、證據門檻、判定值見 Step 3 | `validate-claims.md` | 已溯源的主張有依據；沒依據的已標記或刪除 | 證據本身是否過期（要看 L2）；句子是否讀得通（要看 L1b） |
| L1b 文句與因果審閱 | 文句不靠前後文讀得出原意（無過度縮寫、缺字、歧義）；因果句的主詞、因、果對得上 | 三段式：機械候選（lint、掃描）→ 未參與撰寫者逐句審閱 → 作者核實；見 Step 3b 與 references/文句與因果審閱.md | `validate-wording.md` | 審閱範圍內列出的文句與因果問題，已經作者核實並處置 | 未讀範圍；審閱者也會錯，通過不等於全文正確 |
| L2 可執行者實跑 | 報告裡能跑的東西全部真的跑一次，輸出與報告逐字比對 | 指令實跑、數字用腳本重算、截圖真的打開看 | `validate-claims.md` 內的執行紀錄 | 寫出來的行為與現在的實際行為一致 | 沒有寫進報告的行為 |
| L3 反向覆蓋 | 反方向查漏：從需求與系統列出「應該寫到的東西」，逐一問報告有沒有寫 | 盤點項用 grep 從系統取得，做盤點對照表；兄弟元素逐一比對 | `validate-coverage.md` | 沒有漏列；類別完整 | 寫到的內容是否正確（要看 L1） |
| L4 專家逐條確認 | 把報告抽出的規則／主張／假設列成清單，交使用者或專家逐條確認或更正 | 一條規則一行，每條配一個具體問題；不問「整份對不對」 | `validate-rules.md` ＋ 更正率 | 規則被正確捕捉；知道錯誤率 | 未列入清單的內容 |
| L5 持續一致 | 報告與活系統持續對齊：範例變成測試、契約變成斷言、漂移就告警 | 通常超出單次交付；不做要寫明 | 告警或對帳紀錄 | 日後仍一致 | — |

**選層決策表**（先判斷報告類型，再照表選層；把結果寫進 `validate-plan.md`）：

| 報告類型 | 必做 | 條件式必做 | 通常不做（回報要寫「不適用＋理由」） |
|---|---|---|---|
| 描述程式／系統行為（技術說明、呼叫鏈文件、設計文件、交付說明） | L0a、L1、L3 | 有可執行者就做 L2；L1b（見下方說明） | L4、L5 |
| 回應需求／招標／spec（服務建議書、驗收文件、需求回應） | L0b、L1b、L3、L4（至少抽樣一節） | 有引用系統行為就做 L1 | L2、L5 |
| 兩者都是（多數技術交付文件） | L0a、L0b、L1、L1b、L2、L3、L4 | — | L5 |
| 數據分析報告 | L0a、L2（數字全部重算）、L3 | 有引用系統行為就做 L1；解讀段落做 L1b | L4、L5 |
| 審計／審查結論 | L0a、L1（每一條發現都要有 `檔案:行號` 或實測）、L3（對稱性） | 有可執行者就做 L2；原因與影響的推論句做 L1b 的因果部分 | L4、L5 |
| 成果／進度報告（敘述某期間內的改動與效益） | L0a、L1（期間改動句全量，依 Step 3 證據門檻）、L1b（由未參與撰寫者審閱） | 有數字就做 L2；回應需求就做 L0b；改動清單可列舉時做 L3 | L4、L5 |

L1b 的選用：表中列為必做者，對全文做；列為條件式者，只對敘述性段落（設計理由、原因與影響的推論、數據解讀、交付說明的敘述）做；規格、呼叫鏈、流程表等結構化文件，只對含因果句、概括句或長複句的段落做，其餘以 lint 為限。L1 與 L1b 並行：改句會影響主張，定稿前以最後一版文字重驗被改動句的 L1。

表中沒有的報告類型（法規整理、調查、文獻回顧、純敘述）：依相近類型選層，把理由寫進 `validate-plan.md`。沒有原始碼或版本庫的報告，Step 3 的證據改以原文位置（條號、頁碼、段落）為據，目的句以原文或立法理由等來源為證，不套用依程式與提交判定之項。

## 6. 逐步流程

### Step 0：讀懂任務，選層，寫計畫

1. 把需求來源（需求文件、招標需求、spec、使用者原話）從頭到尾讀一遍，每一條可以獨立回答「有沒有回應」的句子編一個號（R01、R02……）。從原文逐行取得，不憑記憶列；需求來源是對話時，以使用者原話為準，不以摘要、記憶檔或舊紀錄代替（它們可能過時）。
2. 問自己：使用者要的是「一句話」還是「一個類別」？例如使用者說「第 3 節的旗標寫錯了」，要交的是「所有旗標都正確」，不是只改那一個。把類別寫下來。
3. 需求有歧義時，問使用者**一個具體的點**（「第 2 條的『完成』是指產檔還是指寄出通知？」），不要把整份理解丟回去請使用者 review。問不到就寫下你的假設，標明是假設。
4. 依 §5 決策表判斷報告類型、選層，把「做哪些層、不做哪些層、理由」寫進 `./tmp/validate-plan.md`。沒寫下來等於沒有選。

### Step 1：實體存在（L0a）

1. 掃報告全文，抽出所有實體。用正則會比用眼睛可靠：`檔案:行號` 樣式、反引號內的文字、URL、版本號、看起來像編號的字串。
2. 每個實體依類型查證：

| 實體類型 | 查證方式 |
|---|---|
| 檔案路徑 | Glob 或 `ls`；`檔案:行號` 要用 Read 打開那一行，確認內容真的是報告說的東西 |
| 函式名、變數名、選項鍵 | Grep 全專案，範圍包含 `node_modules/<套件>/`；只看一個檔不能下「不存在」的結論 |
| CLI 旗標 | `<cli> --help` 或 `<cli> <子命令> --help` |
| 設定鍵 | 套件 README 或官方設定文件 |
| 套件版本 | `node_modules/<套件>/package.json` 的 `version` |
| URL | `curl -s -o /dev/null -w '%{http_code}' <url>`，要 200；不可以用 `google.com/search?q=` 當參考連結 |
| i18n 鍵 | Grep 語系檔 |
| 資料表、欄位名 | schema 檔或 migration |
| 報告編號、法規條號 | 只能用真的查得到的；查不到就留空或改用泛稱，絕不自編 |

3. 每個實體一列寫進 `./tmp/validate-entities.md`（欄位見產物範本 §1）。
4. 查不到的實體，三選一：改成真的存在的名字；刪除；或（只有在使用者同意保留假設設計時）明確標示「非此系統實作」，不寫成 code block、不與真實內容混在一起。絕不留「大概是這個名字」。
5. 查證步驟寫成 `./tmp/` 下的腳本，之後每次改版重跑。

### Step 2：需求對齊（L0b）

1. 用 Step 0 的需求編號做矩陣：每條需求對到報告的哪一節。
2. 每條需求的狀態只有三種：**已回應**（寫章節）、**刻意不回應**（必須附理由）、**漏列**（必須補寫或標記處置）。
3. 同時檢查：章節結構是否符合該文類的規範（標案文件看 skill[role-writer-report]，流程或呼叫鏈文件看 skill[role-coder-for-spec]）；同一個東西全篇是否用同一個名字；日期是否為絕對日期（`2026-08-30`，不用「昨日」「上週」）。
4. 寫進 `./tmp/validate-requirements.md`。

### Step 3：主張溯源（L1）

1. 掃報告全文，抽出每一句事實描述（含數字、行為描述、結論），一句一列；一句含多個主張時拆成多列。句中的目的、原因、效益（為、使、以、避免、加快…），以及數量與範圍（各、全部、N 個），各自是一個主張。
2. 每句找證據，優先順序：
   - 靜態控制流：把程式碼讀到那一行，且該行在現行執行路徑上（見第 3 點），`檔案:行號` 才是證據（例如「handler 第一行無條件呼叫 X」）。
   - 測試：測試檔名與案例名。
   - 執行 log 或實跑輸出。
   - spec 段落編號。
   - 已驗證可連的外部文獻。
3. **證據門檻**（描述系統的報告每條都要過；無原始碼的報告見 §5 決策表後的說明）：
   - **現行執行路徑**：從入口走得到該行；被註解、未接上的備案、預設關閉者不算。檔案或函式存在只通過 L0a。
   - **提交訊息、檔名、檔案存在、功能要點文件只是線索**，要看 diff 與現行程式（訊息可能寫大改動，diff 只改一行備忘）。
   - **「原為 X，改為 Y」兩邊都要有依據**：舊狀態取 `git show <提交>^:<檔案>`，新狀態取現行程式。
   - **「某期間內做了什麼」要查日期**；版本庫首筆提交之前無紀錄者判「期間無法確認」，不判錯。
   - **全稱與數量要列舉成員**：「各」「全部」「皆」「N 個」逐一對到程式或設定的清單，成員寫進帳冊。
   - **目的與效益**：由機制直接看得出才算已證，並寫明機制（例：改為直接讀本機檔而不呼叫遠端服務，故不受遠端回應時間影響）；只是看似合理者判「目的或效益無依據」，查不到目的就不寫。機制能證的是依賴關係；量化的快慢、穩定度仍屬 runtime 行為，須實跑。
   - **依據欄寫完整路徑** `專案/相對路徑:行號`（舊檔 `提交短碼:路徑:行號`）以便機械複驗；判「查無依據」寫明查過的路徑與關鍵字。
4. **因果逐句五問**：對每個「為、故、使、以、因、隨著、配合、據以、以免」句問：①主詞、因、果對得上嗎；②因是真因，還是把不重要的事併在同一個「為…」底下；③果真由該因產生嗎，後面接的事與該因有關嗎（無關就另起一句）；④有沒有誇大，寫了該功能帶不來的效益；⑤有重點的因果是否反而沒寫。
5. 屬於 runtime 行為的主張（時序、畫面長什麼樣、效能、按下去會怎樣），只能以實跑為證，不能以讀碼推論為證；讀碼推論出來的東西不可以寫成「實測」。
6. **判定值**（每句必填其一）：已證／事實錯／範圍不符／查無依據／目的或效益無依據／期間不符／期間無法確認（定義見產物範本 §3.1）。另設「已證但值得知悉」欄，記不算錯但可更精確者。
7. 非「已證」者的處置三選一：改寫成有證據的句子；改成推測語氣並加註「需實測確認」；刪除（查不到目的就刪）。沒有證據的句子不可混在事實句裡。
8. 先抽樣一節再做全量；成果／進度報告的期間改動句直接全量（抽樣會低估另一節的錯誤）。帳冊本身也抽查數列（含已證列）回程式複驗；抽查通過不等於其餘已證列已驗。寫進 `./tmp/validate-claims.md`。

### Step 3b：文句與因果審閱（L1b）

適用範圍見 §5 決策表。做本步前必讀 [references/文句與因果審閱.md](references/文句與因果審閱.md)（方法總覽、候選判準、派工範本、通讀問題表）。作者手上有前後文，讀的時候會自動補字，自己讀不出缺字、過度縮寫與歧義，所以這一步必須由未參與撰寫者做。

1. **機械候選**：lint（命中即違規；專案沒有就寫「無」，不擋後兩段）加候選掃描（有形式特徵的文句問題；同段連用承接語，含換詞連用，可用本技能資料夾下的 `scripts/scan-connectives.mjs`，以絕對路徑執行）。結果只當候選，逐處判讀，「不改」也寫理由；PASS 或 0 筆都不是結論。
2. **未參與撰寫者逐句審閱**：新 context 讀全文（很長時分批）；只給報告與判準，不給作者的結論與修改紀錄；指定查哪幾類（過度縮寫、缺字或語句不通、因果敘述）；列出已定、不要回報之事；要求信心欄與讀取範圍。
3. **作者核實**：涉及事實者回程式查，採用才改，未採用者寫理由。審閱者也會錯，審閱通過不等於全文正確。無法安排未參與撰寫者時（例：不能再派子代理），第二段寫「未做＋原因」，整體寫「部分完成」，不以作者自審代替。
4. 要放進共用位置、供其他專案或讀者使用的文字（共用規範、技能、範本），另做他案試讀（參考檔 §9）；字樣掃描 0 筆不代表乾淨。
5. 產物 `./tmp/validate-wording.md`（欄位見產物範本 §3.3）；回報寫明審閱範圍與未讀範圍。

### Step 4：可執行者實跑（L2）

1. 列出報告裡所有能跑的東西：指令、範例程式、API 呼叫、統計數字、截圖。
2. 逐一真的執行一次，把實際輸出貼進執行紀錄，和報告所寫逐字比對。
3. 數字一律由腳本重算，不用心算；截圖一律真的打開看過（外部來源的圖檔先驗 magic number 再讀）。
4. 有差異時只有兩種處置：修報告、或修系統（系統是錯的）。不可以把數字改成「大約」把差異蓋掉。
5. 寫進 `./tmp/validate-claims.md` 的執行紀錄段。

### Step 5：反向覆蓋（L3）

這一步和 Step 3 方向相反：Step 3 是「報告寫的東西有沒有根據」，這一步是「該寫的東西有沒有寫」。

1. 先列軸。常見的軸：需求條目；spec 的每個 bullet；程式表面——所有 opt 鍵、所有錯誤路徑、所有步驟、所有枚舉值、所有同類兄弟元素。
2. 每個軸的成員用 grep 從系統取得，不憑記憶。例如：所有 opt 鍵 → grep 該函式內的 `get(opt, '`；所有錯誤路徑 → grep `reject`、`throw`、`return getErrorResult`；所有兄弟元素 → grep 同型的 class 或 selector。
3. 把軸的成員做成盤點對照表：每一項對到報告的位置，狀態只有三種：**已寫**、**刻意不寫**（附理由）、**漏列**（補寫）。表上不可以有空白格；空白格表示這一格還沒查，不是「沒問題」。
4. 對稱性檢查：報告對某一種元素寫了規則（例如節點的刪除行為），就要逐一檢查每個兄弟元素（邊、把手、畫布）是否也寫了，或明寫為什麼不需要。
5. 寫進 `./tmp/validate-coverage.md`。

### Step 6：專家逐條確認（L4）

1. 從報告抽出所有「規則、主張、假設」，一條一行，寫進 `./tmp/validate-rules.md`。
2. 每一條配一個具體問題（「規則 7：上櫃股票也適用嗎？」），讓使用者或專家可以逐條回答「對／錯／更正為……」。
3. 不要問「整份對不對」。先抽樣一節，得到更正率之後再決定要不要全量。
4. 收到回覆後，更正率寫進覆蓋聲明；更正的內容回到 Step 3、Step 5 重跑受影響的層。

### Step 7：修正——照 §7 做

### Step 8：整篇一致性掃描與回報

1. 報告超過約 300 行時，用 grep 對照每個實體在各段的描述是否一致；前段承諾「見第 N 節」的，確認第 N 節真的有。
2. 依 §8 寫回報：先貼勾選清單，再貼覆蓋聲明。

## 7. 失敗處置：被使用者抓到錯，或某一層抓到錯

照順序做，不要跳到第 4 步直接改：

1. **歸類**：這個錯是漏列、捏造、誤解，還是因果不實？
2. **寫下同類判準**：什麼樣的句子算「同一類」？判準寫到病理（為什麼錯），不是字面（長得怎樣）。例如「所有沒有附產生腳本的數字」「所有只寫了節點沒寫兄弟元素的段落」「所有省略主語、其動作對前一分句的主語做不到的分句」；不是「含某幾個字的句子」。
3. **全文掃描同類**：同形不等於同類——grep 同樣的字串或句型只找得到同形，找不到字面不同而病理相同的句子。要依同類判準逐段通讀（範圍大時交 Step 3b 的審閱者），lint 與 grep 只當門檻與輔助。三層依序、缺一不可：lint（門檻）→ 候選掃描（列候選）→ 逐段通讀（判斷）。範圍不自限：依專案撰寫要點的全部條目逐條標已對照或不適用，不以「lint 已擋」「近期才加」略過，放行區（lint 放行的畫面原文、照錄紀錄等）仍須人工對照。把同類全部列成表（產物範本 §5），註明逐句通讀的範圍與只以搜尋盤查的範圍，未讀完者明寫。
4. **全部修掉**，不是只修被抓到的那一句。要修多處時走下方「修正管線」。同類以外的新發現另列於回報，不順手改寫。
5. **重跑該層與其下各層**（例如 L2 抓到的錯，修完後 L0a、L1、L2 都重跑）。
6. **回報的第一段**寫歸類與同類掃描結果（「這是捏造類：數字未跑過。同類掃描另找到 3 處，已全部重算並附腳本」），不是只寫「已修正」。

**修正管線**（改動多處時）：
- **改原稿不改產物**：報告由程式、模板或資料檔組裝時，只改內容的原始檔再重產；撰寫要點的範例隨正文同改，否則下輪照範例寫回舊字。
- **修補先驗後寫**：批次修改前，每處先驗證恰好命中預期次數（多或少都中止），全部通過才一次寫檔（寫法見參考檔 §11）。
- **同類掃描涵蓋全部輸出**：正文、圖名、圖內文字、用同一句的他本報告、相關規格。
- **規則本身也要查**：撰寫要點或範本若有誘導同樣錯誤的句子（例：「查程式與提交紀錄」會把提交訊息當證據），一併改。
- 新裁定的用語可機械判定者入 lint，並先對全部報告跑一次，誤中放行區者收窄或移除。

## 8. 回報模板與完成前勾選清單

回覆末尾先貼勾選清單，全部打勾才可以寫「完成」；有任何一格沒打勾，就寫「部分完成：做了 X，未做 Y」。決策表列為不適用的行寫「不適用（理由）」，視為已勾。

```
完成前勾選
- [ ] validate-plan.md 已寫，選層有理由
- [ ] 實體帳冊每一列都有查證結果，沒有「應該存在」
- [ ] 需求矩陣每條需求的狀態是 已回應／刻意不回應（有理由）／漏列（已補）
- [ ] 主張帳冊每句有判定值，通過證據門檻；非「已證」者已處置（改寫／改推測語氣並加註／刪除）；帳冊已抽查
- [ ] 文句與因果：未參與撰寫者已審，作者逐條核實（未採用者有理由）；候選逐條判讀；已寫明審閱與未讀範圍
- [ ] 可執行者全部真的跑過，差異已處置
- [ ] 盤點對照表沒有空白格；兄弟元素逐一比對過
- [ ] 被抓到的錯已附同類掃描結果
- [ ] 覆蓋聲明已貼，未做的層有原因
```

覆蓋聲明的格式（每一層只能是「已做＋統計＋產物路徑」「未做＋原因」「不適用＋理由」三種之一；下列數字為示意）：

```
驗證覆蓋
- L0a 實體存在：已做，37 項全部存在（./tmp/validate-entities.md）
- L0b 需求對齊：已做，需求 12 條——已回應 11，刻意不回應 1（理由：…），漏列 0
- L1 主張溯源：已做（全量），主張 58 句——已證 49，事實錯 1，範圍不符 3，查無依據 2，目的或效益無依據 3；處置：改寫 5，改推測語氣 2，刪除 2；帳冊抽查 5 列
- L1b 文句與因果審閱：已做，候選 12 筆（改 5，不改 7 附理由）；審閱者 1 名（新 context），讀取範圍第 1 至 240 行，回報 30 條——採用 21，未採用 9（理由見帳冊）；未讀範圍：無（./tmp/validate-wording.md）
- L2 實跑：已做，7 項——一致 6，差異 1 已修報告（第 4.2 節數字 1,203 → 1,187）
- L3 反向覆蓋：已做，盤點 24 項——已寫 22，刻意不寫 2（理由：…），漏列 0
- L4 專家確認：未做——待使用者逐條確認 ./tmp/validate-rules.md 的 18 條
- L5 持續一致：不適用（單次交付）
```

回報用語規則：

- 沒有對應產物與統計，不可以寫「完整」「全部」「全盤」「已驗證」。
- 沒有溯源的主張一律用「推測」「看起來」「可能」並加註「需實測確認」。
- 「lint 通過」「掃描 0 筆」「審閱通過」只能寫成該項結果，不可寫成「文句無誤」「全文正確」。
- 報表日期用絕對日期。外部連結與編號必須真實可連、可查。

## 9. 反模式與正確作法對照

| 錯的做法 | 為什麼錯 | 正確作法 |
|---|---|---|
| 「我審閱過了」「看起來沒問題」 | 沒有產物，別人無法複驗 | 交出 §0 的產物檔 |
| 連結都 200、渲染正常，就當內容正確 | 工具只證明格式與存在性（鐵則二） | 內容正確性靠 L1–L4 |
| 讀程式碼推論出來的行為寫成「實測」 | 這是捏造 | runtime 行為只能以實跑為證；推論就寫「推測」 |
| 數字沒跑就寫；截圖沒打開就描述 | 這是捏造 | 數字用腳本重算，截圖真的看 |
| 引用沒打開過的 `檔案:行號`；猜函式名、旗標名 | 這是捏造 | Step 1 逐一查證，查不到就改或刪 |
| 拿 `google.com/search?q=` 當參考連結；自編報告編號、法規條號 | 業主一點就知道是假的 | 只用 `curl` 驗過 200 的連結與查得到的編號；查不到就留空 |
| 被抓到一處錯只改那一句 | 「你說得對」陷阱（鐵則一） | §7 的六步 |
| 把整份報告丟給使用者「幫我 review」 | 把讀 spec 的責任外包給使用者 | Step 6 逐條清單，每條一個具體問題 |
| 需求條目憑記憶列 | 一定會漏 | 從原文逐行取得並編號 |
| 覆蓋聲明缺層卻寫「完成」；用「大致」「基本上」蓋過沒做的層 | 回報不誠實 | 缺層就寫「部分完成」 |
| 長報告末段與前段矛盾 | context rot | Step 8 整篇一致性掃描 |
| lint PASS 就交；掃描候選未判讀就整批改；候選 0 筆就說乾淨 | lint 只擋固定字面，候選只是形式特徵，都會誤報也會漏 | lint 只當門檻；候選逐條判讀並寫理由；再做逐句審閱（Step 3b） |
| 同形搜尋代替閱讀：被指一處就 grep 同樣的字串 | 同形不等於同類，字面不同而病理相同的句子找不到 | 同類判準寫到病理，依判準通讀（§7 第 2、3 步） |
| 依提交訊息、檔名、檔案存在寫成果句；因果句通順就放行 | 訊息可能與內容不符；通順不證明目的屬實 | 過證據門檻與因果五問（Step 3） |
| 成果報告只抽樣查證；作者自審就當審過 | 抽樣會低估另一節的錯誤；作者自動補字，讀不出缺字與歧義 | 期間改動句全量；文句與因果由未參與撰寫者審（Step 3b） |

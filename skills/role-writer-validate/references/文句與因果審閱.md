# 文句與因果審閱：方法、判準與派工範本

入口是 SKILL.md 的 Step 3b（L1b）。本檔放「怎麼做」：方法總覽、候選掃描的判準、三段式審閱、三種派工範本、通讀問題表、他案試讀、掃描程式的取捨、修補先驗後寫。章節名與編號一起引用（例：「文句與因果審閱.md §5 派工範本：獨立逐句審閱」），章節名不改，編號有變動時以章節名為準。

範例句與範例名稱皆為虛構，只示意形狀；派工時的「不要回報」清單、用字規則、程式位置一律由派工者依本案填寫，不沿用別案。專案有自己的派工提示詞模板或固定回報格式時，只取本檔的判斷內容（查什麼、判準、回報欄位）併入該模板。

## 1. 方法總覽

各方法性質不同，先看「能不能下判斷」：確定性檢查命中即違規；候選只是待判讀的位置；AI 審閱會誤報也會漏。每項依 SKILL.md §4 的六問使用。

| 方法 | 性質 | 能下判斷嗎 | 適用 | 不適用 |
|---|---|---|---|---|
| 字面 lint | 確定性 | 能，命中即違規 | 已裁定的禁詞、用字、標點 | 語意、句構、內容真假 |
| 機械字元校對 | 確定性加候選 | 字元類能；誤字類只列候選 | 繁體中文正式文件的特殊字元、簡體、半形標點、疊字、形近誤字 | 文句 |
| 產線內建中止 | 確定性 | 能（結構） | 報告由程式組裝時：落單的一句、圖說後又接正文等結構問題 | 內容 |
| 圖內文字套同一份規則 | 確定性 | 能（已知詞） | 圖內文字也是正文；圖由 HTML 或資料產製者（例：skill[role-design-web-for-showcase] 的 check-crops 以 --rules 帶入同一份 lint） | 同上 |
| 候選掃描 | 啟發式 | 不能，只列候選 | 有形式特徵的文句問題 | 無形式特徵者；沒有人判讀時 |
| 逐字校對（派工） | AI 逐行讀 | 只列不改，由人裁定 | 疊字、漏字、語病、截斷、表敘不一 | 文風與結構 |
| 獨立逐句審閱 | AI 判斷，必要時對程式 | 能判斷，但須留範圍，會誤報 | 縮寫、缺字、因果、被懷疑的事實；重要交付，尤其作者為 AI | 未被懷疑的事實句；不保證完整 |
| 逐句主張核對 | AI 加程式加版控 | 能 | 事實、範圍、期間；有原始碼與版控 | 範圍外的句子；無法靜態判定的效益 |
| 作者核實 | AI 或人加工具 | 能 | 審閱的誤報；一律要做 | 審閱沒點到之處 |
| 他案試讀 | AI 審查 | 列疑點，人核實 | 跨專案或跨讀者使用的文字 | 單一專案內部文件 |

選用原則：lint 與候選掃描便宜，先做；獨立審閱要新 context；逐句主張核對最耗，但描述系統的成果類報告值得。經驗：作者修過一輪後，全量核對仍查出事實錯與範圍不符（最大宗是全稱寫大，例如「各」「皆」有例外）；只抽一節會低估另一節的錯誤。

## 2. 字面 lint 與機械字元校對

**字面 lint**：每條規則是「正則加放行條件」。放行區（引號內的畫面原文、照錄的紀錄、凍結版）內的問題 lint 查不出，須人工對照。規則與裁決紀錄同步維護：新裁定先入紀錄，再入 lint。新規則先對全部報告跑一次，誤中放行區者收窄或移除。lint 只防已知寫法再犯，找不到新的；PASS 是門檻，不是結論。

**機械字元校對**：
- 非許可字元：全形空格、彎引號、零寬字元、注音、假名、圈號、箭號。
- 簡體與異體字、半形標點夾中文。
- 疊字：`([的了是在與及之於和並或而則即亦皆均其該此])\1`。
- 形近誤字對照（重覆→重複、必需→必須等），須依語境判讀（「反覆」可用）。
- 過度省略的單字、臨時縮短的名稱、未定義的英文縮寫。

字元類 0 筆可信；誤字與省略類只是候選，交逐字校對（§6）。

## 3. 候選掃描：共通原理與判準

**原理**：問題本身是語意的，但常有形式特徵。程式只抓形式特徵、列候選，不下判斷。

**共通規則**：
1. 候選逐條判讀，「不改」也寫理由（候選不是違規清單）。
2. 輸出放暫存夾，改前改後各跑一次並比對，差異只能是本輪的改動。
3. 掃產出的文字（md 或渲染前的內容），不掃產製它的程式：字串拼接、條件分支、模板會漏讀。
4. 先對現有報告全跑一次，估雜訊量級再決定要不要逐條判讀；實際專案多輪實測（未逐條重判）的經驗是「逗號當括號」類雜訊最高、「同段連用承接語」最低。
5. 掃描 0 筆不代表乾淨：只代表沒有這種形式特徵。

**判準表**（每項是候選的形式特徵；是否為問題由人判）：

| 文句問題 | 形式特徵（候選判準） |
|---|---|
| 同段連用承接語（含換詞連用） | 見下方「換詞連用」 |
| 同段重複句組 | 去除引號內文字與已知名稱後，以固定長度（約 8 至 40 字）滑動比對；同段出現 2 次以上且含連續 4 個以上中文字者，取最長 |
| 要點直接串連 | 連續 3 句以上為短主語（約 14 字內、無逗號）加「為、係、涵蓋」等定義句 |
| 概括句以句號收尾 | 含概括詞（多次、諸多、逐步…）、無具體內容（數字、日期、引號、圖表引用）、約 70 字內，且後面還有他句 |
| 頓號與逗號層級不分 | 以逗號切段，含頓號的段達 3 個以上 |
| 逗號當括號 | 「X，A、B、C，Y」且中段無「如、含、包括」等引導詞 |
| 只列部分卻接總括詞 | 列舉 2 項後，同分句或緊接的「其…」分句出現「完整、全部、所有」 |
| 從功能反推的目的與因 | 含「為便於、為使、以便、配合、隨著、以免」的句子；全列後逐句過因果五問（SKILL.md Step 3） |
| 不同大類的因併寫 | 「因…，故…」句；因項是否含兩種以上性質不同的原因由人判 |
| 「則」無所承 | 主題語或主語加逗號後接「則」，前面沒有對照項 |
| 一功能散落多段 | 同一節內，某功能名詞出現於 3 段以上 |
| 段圖交替破碎 | 同標題下連續 2 組以上「短段加其圖」 |
| 縮寫未定義 | 英文縮寫首次出現未以全稱定義（一般讀者皆知者除外） |
| 橫圖入頁後字過小 | 量圖的方向與寬高比，估算縮放進頁面後的字級 |

**換詞連用**（同段連用承接語）：
- 計次單位是「類」，不是「詞」。只比同一個詞，會漏掉「因此…因而…故…」這種換詞連用。分類例：因果類（因此、因而、故、所以、是以、從而、據此、以致）；累加類（此外、另外、再者、同時、並且、而且、另）。同類在同一段達 2 次即列；同詞重複與換詞連用都列。
- 位置：只計段首或句號、分號、逗號、冒號之後的分句首；引號內的畫面原文不計。
- 單字詞（故、另）易誤中複合詞（故障、故意、另行、另一），須排除或要求後接逗號。
- 順序類（首先、其次、最後）是條列用語，不計，否則整批誤報。
- 缺口：只看同一段，跨段或跨節的重複要另外統計全文頻率；詞表只涵蓋繁體中文書面語。
- 判讀時先問：這幾個承接語表達的關係真的相同嗎？相同，就合併成一個複句或省略多餘者；不同，就改用能區分關係的詞。對稱句的刻意重複、真正的因果鏈可保留，但要寫理由。只在同類詞之間輪流換字（因此→因而→故）不算改好，同一支掃描仍會列出。

## 4. 三段式審閱流程

SKILL.md Step 3b 的完整說明。為什麼要三段：作者手上有前後文，讀的時候自動補字，自己讀不出缺字、縮寫與歧義（研判）；工具只抓得到形式特徵；未參與撰寫的審閱者讀得出，卻會誤報，也不保證完整。

**第一段：機械候選。** lint、字元校對、候選掃描。結果只當候選，逐處判讀。

**第二段：未參與撰寫者逐句審閱。**
- 新 context 讀全文；報告很長時分批，每批大小設上限（經驗值約 200KB），一次一個子代理，否則讀不完又不自知。
- 只給報告與判準，不給作者的結論、不給作者已改過什麼。
- 指定查哪幾類（過度縮寫、缺字或語句不通、因果敘述），其他類不查，才不會淹沒。
- 列出已定、不要回報之事（見 §5 範本）。
- 要信心欄（高、中、低），沒把握標低，不要灌水也不要省略。
- 要讀取範圍：回報末尾列每檔總行數與實際讀到的範圍。
- 需要時可讀程式核對因果句；此時依 SKILL.md Step 3 的證據門檻。

**第三段：作者核實。**
- 涉及事實者回程式查，採用才改，未採用者寫理由。
- 審閱者也會錯：低信心條目常有不宜採用者（例：與另一本報告的同句須兩處同步、使用者已定的用語）。
- 不要把審閱結果當真相，也不要因審閱通過就宣稱全文正確。

**回報要寫**：候選數與處置（改幾處、不改幾處與理由）；審閱者回報條數（採用、不採用）；逐句通讀的範圍與只以搜尋盤查的範圍，未讀完者明寫。只對照近期新增的條目，也算沒做。

## 5. 派工範本：獨立逐句審閱

派工訊息範本（`<…>` 由派工者填寫）：

```markdown
你是獨立審閱者，請以「將交付 <讀者> 審查」的標準，逐句審一份繁體中文報告，只回報發現，不改任何檔案。全程用繁體中文。

## 審閱對象

`<報告路徑>`（<總行數> 行，第 <N> 行起為正文）。<一句話說明讀者與用途；若讀者擔心被看出內容不實或由 AI 產製，寫明>

## 只查三類

1. 過度縮寫：字詞縮得太短，使意思改變、含糊或讀不懂，須還原者。例：「重試三次仍敗則告警」的「敗」應為「失敗」；「前述設定之預設值」讀不出前述指哪一項設定；把「訂單處理服務」臨時縮成「訂單服務」。領域內通用的專有名詞不算。
2. 缺字、漏字、語句不通：少了字詞、主詞動詞受詞接不起來、修飾對象錯、有歧義（如「備份前一日資料」可讀成備份「前一日的資料」，也可讀成「備份之前一日」再接資料）。請一句一句讀，不要跳讀。
3. 因果敘述不當：每個「為…」「故」「使」「以」「因」「隨著」「配合」「據以」「以免」句，逐一問：
   - 主詞是誰？主詞、因、果三者對得上嗎？
   - 因是真正的因，還是把不重要的事併在同一個「為…」底下？
   - 果真的由該因產生嗎？後面接的事有沒有與該因無關？
   - 有沒有誇大（寫了該功能帶不來的效益）？
   - 有重點的因果是否反而沒寫出來？

## 判準來源（請先讀）

- <本案的用字規則或撰寫要點位置；沒有就刪此節>
- <他案或上游要點的位置，註明其專屬內容不適用於本報告>

已定、不要回報為問題的：<由派工者依本案填寫：使用者已裁定的用語、刻意保留的寫法、全文定義過的簡稱、畫面原文照錄處。沒有這份清單，結果會被雜訊淹沒>

## 事實核對

因果句需要時請讀程式確認，程式在：<程式位置；無程式則寫來源文件的位置>。

只讀不改。搜尋用 Grep、Glob，不要對大型資料目錄做遞迴搜尋。暫存檔放 <暫存夾>。不得執行會寄信、通知或寫入外部系統的程式；不得印出任何密碼或權杖。

（上方五問是 SKILL.md Step 3「因果逐句五問」的複本，因為派工對象可能沒讀技能；改一處須同步另一處。）

## 回報格式

依行號排序的表格，每列：行號｜原文片段（逐字）｜類別（縮寫、缺字、因果）｜問題（一句話）｜建議改寫｜信心（高、中、低）。

因果類若有核對程式，在「問題」附 `檔案:行號`。沒有把握的標「低」，不要灌水，也不要因為怕多而省略；寧可完整逐句看完。回報末尾列出實際讀到的行數範圍，再用 3 行以內寫你認為全篇最嚴重的 3 個問題。
```

## 6. 派工範本：逐字校對（只列不改）

用於「重查特殊字、錯字與過度省略，先列表」這類要求。流程：機械掃描加分批子代理逐冊讀，彙整成表交使用者逐項裁定，再改正、入 lint、重產報告。

```markdown
# 報告校對派工說明（只列不改）

## 任務

逐字閱讀指派的報告（路徑由派工訊息給定），找出三類問題，只列表回報，不得修改任何檔案：

1. 錯字：同音或形近誤字（的得地、在再、須需、即既、以已、己已、辨辦、戴載…），詞語內部字序顛倒，漏字、多字、疊字（「的的」「，，」），形近詞誤用（稍後與稍候、反應與反映、必需與必須、預訂與預定）。用字裁定因專案而異，依 <本案裁定表>。
2. 特殊字：不應出現在正式中文報告的字元——簡體字、異體字、注音符號、日文假名、全形空格、半形標點夾在中文句中、半形括號包中文、彎引號（依專案規定的引號為準）、箭號、圈號、佔位符（○○、XX、TODO、待補）、亂碼、殘留的 Markdown 強調符或 HTML 標籤文字。
3. 過度省略之詞：把常用雙字詞壓成單字，讀來像被截斷（例：「驗」代「驗證」、「傳畢」代「傳送完畢」、「刪後」代「刪除後」）；臨時縮短的系統名或專有名詞（例：把「訂單處理服務」縮成「訂單服務」）；英文縮寫在該報告內首次出現未以「中文（English, ABBR）」定義者（一般讀者皆知者不算）。

## 不要列的

<由派工者依本案填寫。沒有這份清單，結果會被雜訊淹沒。常見類別：>
- 已裁定的用語（貼入本案的用語裁定表）。
- 可接受的書面單字（例：係、惟、均、即；只有讀來像把常用雙字詞截斷者才列）。
- 畫面上的按鈕、欄位、訊息原文（置於「」內者照錄；但明顯錯字仍列，並註明「畫面原文」）。
- 文風、文法、語氣、句構、冗長、連接詞等問題不在本次範圍。
- 照錄原文的表格（例：引用的紀錄或條文原文）整表跳過，其餘敘述段落照常校對。

## 作法要求

- 以 Read 分段讀完整份檔案（每段不超過 400 行），每一行都要讀到，不得抽樣、不得只讀前半（逐字校對本來就須全讀，是一般「只讀需要的行段」守則的例外）。讀完後在回報末尾列出每檔總行數與實際讀到的行數範圍，供核對。
- 不得用 shell 的 cat、head、tail、sed 讀檔；不得修改或寫入任何檔案；非得產生暫存檔，一律放 <暫存夾>。
- 每筆發現附檔名、行號、原文片段（30 字內，含前後文）、類別、問題、建議；不確定者仍列，於「問題」欄註明「待判」。
- 回報只含發現表格與讀取範圍，不重述任務、不加總結感想。

## 回報格式

| 檔案 | 行號 | 原文片段 | 類別 | 問題 | 建議 |
|---|---|---|---|---|---|

末尾：讀取範圍：A 共 N 行，已讀 1 至 N；B 共 N 行，已讀 1 至 N。
```

## 7. 派工範本：事實核對（逐句主張核對）

用於描述系統、敘述某期間改動與效益的報告。判定值表照 產物範本.md §3.1 貼入派工訊息。無程式碼或版本庫的報告（法規、調查、文獻），核對對象改為原文來源：刪去下方範本中依程式與提交判定的段落，證據欄改寫來源位置（條號、頁碼、段落），目的句以原文或立法理由等來源為證。

```markdown
# 報告改動句之事實核對：派工範本

## 對象

`<報告路徑>`。報告將交 <讀者> 審查。每位核對者只看派工訊息指定的行號範圍。

## 查什麼

逐句抽出期間改動句，一句一列，含：

1. 明寫或實質表示「<期間> 做了什麼」的句子（新增、改為、重構、擴充、調整、移至、原為…、已納入、不再…）。
2. 上述句子所接的目的、原因與效益（為…、使…、以…、避免…、減少…、加快…、大幅提升…、不須…）。
3. 句中的數量與範圍（N 個、全部、各、皆、全線）。

只描述系統本來如此、與期間改動無關的句子不列入帳冊；若順帶發現其事實有誤，另列於帳冊末〈範圍外之發現〉。

## 什麼算證據（依序）

1. 現行實際執行的程式：`專案/相對路徑:行號`，且須確認這段程式真的被走到：入口、排程或服務設定有接上，有呼叫端，不是被註解掉，不是未啟用的備案版本。
2. 提交的 diff：佐證「改動確實發生」與日期；要看 diff 內容，不只看訊息。
3. 規格案例與測試斷言（經實跑者）。
4. 功能要點與說明文件只當線索，可能過時，要回程式確認。

提交訊息不是證據，檔案存在也不是證據。提交訊息可能與內容不符（訊息寫大改動，diff 只改一行備忘；訊息寫「全部頁面」，實際只改其中一頁）。

「原為 X、改為 Y」兩邊都要有依據；舊狀態以 `git show <提交>^:<檔案>` 或該提交的 diff 取得。

目的與效益句：機制上由程式可直接看出者（依賴關係，例：不呼叫遠端服務，故不受其回應時間影響）可判已證，並寫明機制；只是看似合理、程式與提交都看不出者判「目的或效益無依據」。不要因為句子通順就放行。不做實機量測，量化的快慢、穩定度因此不能判已證。

全稱與範圍：寫「各」「全部」「全線」要列舉成員逐一確認；寫「N 個」要對到程式或設定的清單。
```

## 8. 通讀問題表

| 面向 | 問法 | 實例 |
|---|---|---|
| 名詞所指 | 這個角色、元件或功能現況真做這件事嗎？名稱全篇統一嗎？作業系統層的帳號有沒有被誤寫成系統內的角色？ | 「值班人員可關閉告警」，但關閉只能在維運工具操作，系統內並無此角色 |

## 9. 他案試讀

**情境**：要給其他專案或其他讀者用的文字（共用規範、技能、範本），檢查會不會誤導。

**作法**：專案字樣掃描歸零後，另派未參與起草的審查者，以另一案的 agent 自居，先讀該案的實際文件，再讀草稿，回答四類：
1. 會被誤當成本案事實的句子。
2. 與該案已有的裁定衝突、且沒有「依專案」出口的規定。
3. 洩漏來源痕跡（專案名、路徑、人名、日期、內部編號、領域用語）。
4. 無法操作的步驟。

每條附雙方的 `檔案:行號`。

**實績形狀**：字樣掃描 0 筆後仍找出多項，例如無條件的「每個步驟都要附截圖」會讓他案為沒有畫面的批次作業補寫截圖欄；「一律不寫版本號」會誤刪升版說明中必要的版本號。字樣掃描 0 筆不代表乾淨。

**限制**：需要另一案的真實文件當對照；只能找出對該案的問題。

## 10. 掃描程式之取捨

- 預設只寫判準（§3），不附程式：詞表、段落定義、放行區都隨專案，寫死的程式搬到別案會誤報或漏報。
- 本技能附一支 `scripts/scan-connectives.mjs`（同段連用承接語，含換詞連用）：通用於繁體中文 md、零依賴、誤報可接受、換詞連用也抓得到。以本技能資料夾的絕對路徑執行：`node <本技能資料夾>/scripts/scan-connectives.mjs --self-test` 跑自我測試；用法 `node <本技能資料夾>/scripts/scan-connectives.mjs [--min 2] <md 檔或資料夾>...`（資料夾請限定在報告所在處，不要傳整個專案根）。輸出是候選，不是違規清單。
- 其餘判準（§3 表）不附程式。自建時：先寫判準，再寫程式；附自我測試（好句不誤報、壞句抓得到）；在自己的語料上實測誤報量；輸出只列候選。
- 自建或沿用掃描程式的結果，一律回到 §4 第一段處理：逐條判讀，不整批依候選改。

## 11. 修補先驗後寫（批次改原稿時）

SKILL.md §7 修正管線的寫法示意：每處修補先驗證恰好命中預期次數，全部通過才一次寫檔，避免默默漏改或改到別處。

```js
let files = {} // 路徑 -> 修改後內容(暫存)
let load = (fp) => files[fp] ?? fs.readFileSync(fp, 'utf8')
let rep = (fp, from, to, n = 1) => {
    let s = load(fp)
    let c = s.split(from).length - 1
    if (c !== n) {
        throw new Error(`${fp} 命中 ${c} 次(應 ${n}): ${from.slice(0, 60)}`)
    }
    files[fp] = s.split(from).join(to)
}
// 先呼叫全部 rep(...); 都沒有拋錯, 才逐檔 fs.writeFileSync(fp, files[fp])
```

改完後以同類判準重新掃描全部輸出（正文、圖名、圖內文字、用同一句的他本報告、相關規格），並重跑 lint。

# 文句與因果審閱：方法、判準與派工範本

入口是 SKILL.md 的 Step 3b（L1b）。本檔放「怎麼做」：方法總覽、候選掃描的判準、三段式審閱、三種派工範本（全文在 [派工範本.md](派工範本.md)）、通讀問題表、他案試讀、掃描程式的取捨、修補先驗後寫。章節名與編號一起引用（例：「文句與因果審閱.md §8 通讀問題表」「派工範本.md §5 派工範本：獨立逐句審閱」），章節名不改，編號有變動時以章節名為準。

範例句與範例名稱皆為虛構，只示意形狀；派工時的「不要回報」清單、用字規則、程式位置一律由派工者依本案填寫，不沿用別案。專案有自己的派工提示詞模板或固定回報格式時，只取本檔的判斷內容（查什麼、判準、回報欄位）併入該模板。

## 1. 方法總覽

各方法性質不同，先看「能不能下判斷」：確定性檢查命中即違規；候選只是待判讀的位置；AI 審閱會誤報也會漏。每項依 SKILL.md §4 的六問使用。

| 方法 | 性質 | 能下判斷嗎 | 適用 | 不適用 |
|---|---|---|---|---|
| 字面 lint | 確定性 | 能，命中即違規 | 已裁定的禁詞、用字、標點 | 語意、句構、內容真假 |
| 機械字元校對 | 確定性加候選 | 字元類能；誤字類只列候選 | 繁體中文正式文件的特殊字元、簡體、半形標點、疊字、形近誤字 | 文句 |
| 產線內建中止 | 確定性 | 能（結構） | 報告由程式組裝時：落單之短段（判準依 skill[role-writer-report-final]〈文句與段落診斷〉第 5 節：短且接於前文，不看句數）、引圖句後另起內容句（同句接於引圖短語之後之圖內說明不算，見該技能〈亮點與配圖〉第 5 節）等結構問題 | 內容 |
| 圖內文字套同一份規則 | 確定性 | 能（已知詞） | 圖內文字也是正文；圖由 HTML 或資料產製者（例：skill[role-design-web-for-showcase] 的 check-crops 以 --rules 帶入同一份 lint） | 同上 |
| 候選掃描 | 啟發式 | 不能，只列候選 | 有形式特徵的文句問題 | 無形式特徵者；沒有人判讀時 |
| 逐字校對（派工） | AI 逐行讀 | 只列不改，由人裁定 | 疊字、漏字、語病、截斷、表敘不一 | 文風與結構 |
| 獨立逐句審閱 | AI 判斷，必要時對程式 | 能判斷，但須留範圍，會誤報 | 縮寫、缺字、因果、被懷疑的事實；重要交付，尤其作者為 AI | 未被懷疑的事實句；不保證完整 |
| 逐句主張核對 | AI 加程式加版控 | 能 | 事實、範圍、期間；有原始碼與版控 | 範圍外的句子；無法靜態判定的效益 |
| 作者核實 | AI 或人加工具 | 能 | 審閱的誤報；一律要做 | 審閱沒點到之處 |
| 他案試讀 | AI 審查 | 列疑點，人核實 | 跨專案或跨讀者使用的文字 | 單一專案內部文件 |

產線內建檢查須能放行各報告類技能所列之例外；檢查與裁定者之段落分工衝突時，改檢查，不改段落。

選用原則：lint 與候選掃描便宜，先做；獨立審閱要新 context；逐句主張核對最耗，但描述系統的成果類報告值得。經驗：作者修過一輪後，全量核對仍查出事實錯與範圍不符（最大宗是全稱寫大，例如「各」「皆」有例外）；只抽一節會低估另一節的錯誤。

## 2. 字面 lint 與機械字元校對

**字面 lint**：每條規則是「正則加放行條件」。放行區（引號內的畫面原文、照錄的紀錄、凍結版）內的問題 lint 查不出，須人工對照。規則與裁決紀錄同步維護：新裁定先入紀錄，再入 lint。新規則先對全部報告跑一次，誤中放行區者收窄或移除。lint 只防已知寫法再犯，找不到新的；PASS 是門檻，不是結論。專案已裁定「之」之上限者，§3「分句內「之」過多」之計數可入 lint（命中即違規，放行「」內畫面原文與圖表題）；未裁定者仍為候選。

**機械字元校對**：
- 非許可字元：全形空格、彎引號、零寬字元、注音、假名、圈號、箭號。
- 簡體與異體字、半形標點夾中文。
- 疊字：`([的了是在與及之於和並或而則即亦皆均其該此])\1`。
- 形近誤字對照（重覆→重複、必需→必須等），須依語境判讀（「反覆」可用）。
- 過度省略的單字、臨時縮短的名稱、未定義的英文縮寫。

字元類 0 筆可信；誤字與省略類只是候選，交逐字校對（[派工範本.md](派工範本.md) §6）。

## 3. 候選掃描：共通原理與判準

**原理**：問題本身是語意的，但常有形式特徵。程式只抓形式特徵、列候選，不下判斷。

**共通規則**：
1. 候選逐條判讀，「不改」也寫理由（候選不是違規清單）。
2. 輸出放暫存夾，改前改後各跑一次並比對，差異只能是本輪的改動。
3. 掃產出的文字（md 或渲染前的內容），不掃產製它的程式：字串拼接、條件分支、模板會漏讀。
4. 先對現有報告全跑一次，估雜訊量級再決定要不要逐條判讀；實際專案多輪實測（未逐條重判）的經驗是「逗號當括號」類雜訊最高、「同段連用承接語」最低。
5. 掃描 0 筆不代表乾淨：只代表沒有這種形式特徵。

**判準表**（每項是候選的形式特徵；是否為問題由人判）：

| 文句問題 | 形式特徵（候選判準） |
|---|---|
| 同段連用承接語（含換詞連用） | 見下方「換詞連用」 |
| 同段重複句組 | 去除引號內文字與已知名稱後，以固定長度（約 8 至 40 字）滑動比對；同段出現 2 次以上且含連續 4 個以上中文字者，取最長 |
| 要點直接串連 | 連續 3 句以上為短主語（約 14 字內、無逗號）加「為、係、涵蓋」等定義句 |
| 概括句以句號收尾 | 含概括詞（多次、諸多、逐步…）、無具體內容（數字、日期、引號、圖表引用）、約 70 字內，且後面還有他句 |
| 頓號與逗號層級不分 | 以逗號切段，含頓號的段達 3 個以上 |
| 逗號當括號 | 「X，A、B、C，Y」且中段無「如、含、包括」等引導詞 |
| 只列部分卻接總括詞 | 列舉 2 項後，同分句或緊接的「其…」分句出現「完整、全部、所有」 |
| 從功能反推的目的與因 | 含「為便於、為使、以便、配合、隨著、以免」的句子；全列後逐句過因果五問（SKILL.md Step 3） |
| 不同大類的因併寫 | 「因…，故…」句；因項是否含兩種以上性質不同的原因由人判 |
| 「則」無所承 | 主題語或主語加逗號後接「則」，前面沒有對照項 |
| 一功能散落多段 | 同一節內，某功能名詞出現於 3 段以上 |
| 段圖交替破碎 | 同標題下連續 2 組以上「短段加其圖」 |
| 縮寫未定義 | 英文縮寫首次出現未以全稱定義（一般讀者皆知者除外） |
| 橫圖入頁後字過小 | 量圖的方向與寬高比，估算縮放進頁面後的字級 |
| 同段相鄰句以同一功能詞起首 | 以「。！？」切句（先去「」與反引號內文字）；相鄰兩句之句首為同一功能詞即列，連續 3 句同詞列 1 筆。詞表依專案增刪（示意：為、因、若、針對、並、亦、而、惟、本期）；序數列舉（其一…其二…）不列；句首詞已在 `scan-connectives.mjs` 詞表者由該程式列出，本列補其未涵蓋之詞與「相鄰」之限定。判讀問：第二句能否改以「此外，」承接、目的移到句末以「以…」交代？ |
| 同段重點詞重複 | 取各句之「動作詞尾連同其前 2 字」（詞尾表依專案增刪，示意：調校、整併、優化、重構、調整、擴充、更新；如「排程調校」），比對前先去「之」與引號內文字；同段不同句出現同一詞即列，補「同段重複句組」之窗口抓不到之短詞。判讀問：首句以名詞點出之重點，次句是否又以同一詞收尾而未寫出具體做法？對稱句之刻意重複可保留並寫理由 |
| 連續處理動作過多 | 以「。」切句、「；」切段（各段分別計），再以「，」切分句（先去「」內文字）；每段第 1 分句為「頭」，其後以動作起首之分句多於 3 個即列（3 為經驗值）。起首詞表依專案增刪（示意：並、再、即、隨即、接著、然後、進而、據以、以此、又、且、以、依、經、將、先、預先、只須、供、於，加專案之動詞表）；有主語之分句、「以及」「如圖」「如表」「例如」不計。判讀問：頭之後做了幾件事？動作之間有交代先後與目的之連接詞嗎？ |
| 事件後反應過多 | 切分同上；以「後」「時」結尾之分句為「事件」，其後連續 3 個以上無主語、以動作起首之分句即列（門檻為產線自擬；以「其、該、此、若、但、惟、則、因、而」起首者不計），有主語之結果句中斷計數；先排除「以及」，以免讀成介詞「以」。判讀問：這件事做完之後又接著做了幾件事？中途之動作可否改成下一段之事件、同類動作可否合併？ |
| 拆句後孤立短句 | 句首為「另、另外、亦、並、且、而」（排除「另一」「而當」）且約 40 字以內者；或不論句首，約 25 字以內而含「亦一併」「亦予以」「亦同步」者（字數為產線自擬）。判讀問：單獨讀這句，知道是誰做、與前句之關係、做來做什麼嗎？ |
| 分句內「之」過多 | 以「，。；：！？」與頓號切段，每段「之」多於 2 個即列（2 為經驗值，依專案調整）；「」內之畫面原文、圖表題與引用標記不計。判讀問：念一遍要不要換氣？「之」所修飾之對象，讀者能一次對上嗎？ |
| 不同部分以逗號串成一句 | 同一句以「，」「；」切分句，有 2 個以上分句各以不同之「部分名詞」起首（名詞在分句前 10 字內；以連接詞、介詞或指代詞起首之分句不計，如並、且、以、使、故、即、於、針對、若、當、其、此、該、而）即列。部分名詞表由專案以其系統與組成之名稱，加通用詞（前端、後端、軟體、硬體、網站、頁面、服務、排程、主機）自編；表外者靠通讀。同一主語之連續述語、明確列舉、以「則」「另」寫出之對照不列。判讀問：逗號前後是同一件事嗎？讀者會不會把後一分句之結果或範圍套到前一分句？ |
| 名稱早於介紹 | 先定位正文之「組成句」（含「分為 N 個系統」「由…組成」）；某系統或子系統名稱以句首或段首主語首次出現之位置早於組成句者即列；作受詞或定語且自明者不計；只適用於有組成句可定位之文件。判讀問：只讀到這一段為止，讀者知道這個名稱是什麼、屬於什麼嗎？ |
| 段首句無作用 | 緊接標題之段首句約 40 字內（產線自擬），句末為「落實／遵循／辦理／執行／完成／具備／符合…事項／規定／要求／措施／作業」之形式，且不含因果與方針之詞（為、因、故、使、須、以免、方針、原則、重點、如下、如後）。判讀問：拿掉段首句，讀者是否少了概念之強調、鄭重事項之釐清、方針之指引或連續處理之起頭？ |
| 表格儲存格塞多項 | 表格之單一儲存格內頓號 5 個以上即列（產線自擬）。判讀問：一格內列舉多項，與全用文字有何差別？可否一項一列、共同欄合併儲存格？ |
| 亮點情境出現機制語 | 前提：專案已訂亮點清單。於前言前 2 段、小結（結論）全章與含時效宣稱之段落，搜尋專案自編之機制或小改動詞（示意：依序執行、共用組件、快取、重試），命中即列（範圍為產線自擬）。判讀問：這句是亮點，還是在說明既有功能？讀者看得出得到什麼嗎？日後再優化，這句還成立嗎？ |

上表最後 11 列之寫法（怎麼改）在 skill[role-writer-report-final]：〈文句與段落診斷〉第 3 節（修飾語不堆疊）、第 5 節（主語轉換、段首句要有作用、同段承接語之寫法側）、第 6 節（不同之事不併）、第 7 節（連續處理之句）；〈章節與敘事〉第 2 節（先介紹再使用）、第 6 節（機制依情境寫）；〈內容邊界與防禦性寫作〉第 4 節（機制不寫死）；〈格式、標點與用字〉第 7 節（用表是為了逐項看）。詞表、門檻與範圍皆為示意，依專案之語料實測誤報後調整（§10）；手冊等操作步驟類文件之「連續處理動作」誤報較多，判讀時依其體例。

**換詞連用**（同段連用承接語）：
- 計次單位是「類」，不是「詞」。只比同一個詞，會漏掉「因此…因而…故…」這種換詞連用。分類例：因果類（因此、因而、故、所以、是以、從而、據此、以致）；累加類（此外、另外、再者、同時、並且、而且、另）。同類在同一段達 2 次即列；同詞重複與換詞連用都列。
- 位置：只計段首或句號、分號、逗號、冒號之後的分句首；引號內的畫面原文不計。
- 單字詞（故、另）易誤中複合詞（故障、故意、另行、另一），須排除或要求後接逗號。
- 順序類（首先、其次、最後）是條列用語，不計，否則整批誤報。
- 缺口：只看同一段，跨段或跨節的重複要另外統計全文頻率；詞表只涵蓋繁體中文書面語。
- 判讀時先問：這幾個承接語表達的關係真的相同嗎？相同，就合併成一個複句或省略多餘者；不同，就改用能區分關係的詞。對稱句的刻意重複、真正的因果鏈可保留，但要寫理由。只在同類詞之間輪流換字（因此→因而→故）不算改好，同一支掃描仍會列出。

## 4. 三段式審閱流程

SKILL.md Step 3b 的完整說明。為什麼要三段：作者手上有前後文，讀的時候自動補字，自己讀不出缺字、縮寫與歧義（研判）；工具只抓得到形式特徵；未參與撰寫的審閱者讀得出，卻會誤報，也不保證完整。

**第一段：機械候選。** lint、字元校對、候選掃描。結果只當候選，逐處判讀。

**第二段：未參與撰寫者逐句審閱。**
- 新 context 讀全文；報告很長時分批，每批大小設上限（經驗值約 200KB），一次一個子代理，否則讀不完又不自知。
- 只給報告與判準，不給作者的結論、不給作者已改過什麼。
- 指定查哪幾類（過度縮寫、缺字或語句不通、因果敘述；報告有前言、開場或概述者加閱讀次序），其他類不查，才不會淹沒。
- 列出已定、不要回報之事（見 [派工範本.md](派工範本.md) §5）。
- 要信心欄（高、中、低），沒把握標低，不要灌水也不要省略。
- 要讀取範圍：回報末尾列每檔總行數與實際讀到的範圍。
- 需要時可讀程式核對因果句；此時依 SKILL.md Step 3 的證據門檻。

**第三段：作者核實。**
- 涉及事實者回程式查，採用才改，未採用者寫理由。
- 審閱者也會錯：低信心條目常有不宜採用者（例：與另一本報告的同句須兩處同步、使用者已定的用語）。
- 不要把審閱結果當真相，也不要因審閱通過就宣稱全文正確。
- 採用審閱者之建議句或改寫前，作者先自己讀過（主語、動詞、受詞，與前後句之銜接），並讓它過與正文同一套規則（lint、候選掃描、專案用字裁定）；建議句是另一個 context 寫的新句，不因出自審閱者而免檢。

**回報要寫**：候選數與處置（改幾處、不改幾處與理由）；審閱者回報條數（採用、不採用）；逐句通讀的範圍與只以搜尋盤查的範圍，未讀完者明寫；同類掃描由作者自行盤查者（SKILL.md §7 第 3 步）寫明「同類掃描為作者自審」與讀取範圍。只對照近期新增的條目，也算沒做。

## 8. 通讀問題表

逐段通讀時，每段依下表發問。讀產出的文字，不讀產製它的程式。讀到機制句就開程式對照：答不出「對什麼、做了什麼、結果、用處」，就是壓縮過頭。實例皆為虛構。

| 面向 | 問法 | 實例 |
|---|---|---|
| 名詞所指 | 這個角色、元件或功能現況真做這件事嗎？名稱全篇統一嗎？作業系統層的帳號有沒有被誤寫成系統內的角色？ | 「值班人員可關閉告警」，但關閉只能在維運工具操作，系統內並無此角色 |
| 事實與機制 | 功能、設定、數字與現行程式、設定檔、套件預設一致嗎？機制句答得出對象、步驟、結果、用處嗎？ | 「通知亦改以佇列處理」：所有通知還是失敗者？處理成什麼？為了什麼？ |
| 主語與分句 | 抽出主語與動詞單獨讀成立嗎？省略主語的分句接的是誰？ | 「檔案由甲服務產生，並可於畫面下載」：可下載的是檔案還是甲服務？ |
| 指代 | 「其」「則」「上述」「該」有所承嗎？概稱（本系統、該模組）固定指同一對象嗎？ | 同段先說「乙模組」再說「該元件」，讀者不知是否同一個 |
| 因果 | 逐句五問（SKILL.md Step 3）：主詞與因果對得上嗎？因是真因嗎？果由因生嗎？有無誇大？真因是否漏寫？ | 「搜尋改為分頁載入，以降低伺服器負載」：分頁載入是真的，降低負載是作者補的目的 |
| 列舉 | 一句一層嗎？只列部分卻接「完整、全部」嗎？頓號與逗號層級分得清嗎？ | 「支援匯入甲、乙，可完整處理所有格式」 |
| 概括句 | 只有概括沒有內容嗎？ | 「本服務提供多方面之穩健保障。」：哪幾方面、怎麼保障，沒說 |
| 重複 | 同段重複句組或承接語（含換詞連用）嗎？ | 同段「因此…因而…故…」 |
| 缺字與歧義 | 不靠前後文讀得出原意嗎？有第二種讀法嗎？ | 「逾時未回應重送」缺「則」，可讀成「逾時」與「未回應重送」兩件事 |
| 跨文件同步 | 同一事項在各報告寫法一致嗎？改一處時，上游資料與他本跟著改了嗎？ | 本報告改了簡稱，共用資料檔仍是舊稱 |
| 承諾與範圍 | 有無保證、承諾、後續義務，或超出本方職責的句子？ | 「保證永不中斷」 |
| 定位與例外 | 定位陳述（「由○○統一維護」「僅供○○」）與例外情境並置時，例外帶條件語（必要時、未來若需）嗎？ | 「書目由總館統一維護。分館亦可直接編修書目。」並置而無條件，讀者看到矛盾；改「書目由總館統一維護，必要時分館亦可直接編修。」 |
| 閱讀次序 | 讀到這一句時，這個名稱、簡稱、數字（含其成員）、「如後」所指，讀者已經知道是什麼了嗎？ | 前言首段以「館藏管理系統」為句首主語敘述功能，「借閱平臺分為 2 個系統」到第三段才出現 |
| 去留 | 拿掉這句，這段少了什麼？事實正確不等於該留 | 「並以架構圖與流程圖呈現整體架構。」：讀者看得到圖，零增量 |
| 圖文對位 | 圖內說明（線型、圖例）接在引圖短語之後嗎？正文說幾個物件，紅框就框了幾個嗎？圖名是同一範圍嗎？ | 正文寫各統計圖皆已可依分館篩選，紅框只框其中一個 |

後四列之寫法（「定位與例外」無對應之寫法條，依通讀判斷）見 skill[role-writer-report-final]：〈文句與段落診斷〉第 2 節（留句看重要性）、第 6 節（小數字寫明成員）；〈章節與敘事〉第 2 節（先介紹再使用）；〈格式、標點與用字〉第 2 節（「如後」）；〈亮點與配圖〉第 4、5 節（紅框範圍、圖內說明）。

## 9. 他案試讀

**情境**：要給其他專案或其他讀者用的文字（共用規範、技能、範本），檢查會不會誤導。

**作法**：專案字樣掃描歸零後，另派未參與起草的審查者，以另一案的 agent 自居，先讀該案的實際文件，再讀草稿，回答四類：
1. 會被誤當成本案事實的句子。
2. 與該案已有的裁定衝突、且沒有「依專案」出口的規定。
3. 洩漏來源痕跡（專案名、路徑、人名、日期、內部編號、領域用語）。
4. 無法操作的步驟。

每條附雙方的 `檔案:行號`。

**實績形狀**：字樣掃描 0 筆後仍找出多項，例如無條件的「每個步驟都要附截圖」會讓他案為沒有畫面的批次作業補寫截圖欄；「一律不寫版本號」會誤刪升版說明中必要的版本號。字樣掃描 0 筆不代表乾淨。

**限制**：需要另一案的真實文件當對照；只能找出對該案的問題。

## 10. 掃描程式之取捨

- 預設只寫判準（§3），不附程式：詞表、段落定義、放行區都隨專案，寫死的程式搬到別案會誤報或漏報。
- 本技能附一支 `scripts/scan-connectives.mjs`（同段連用承接語，含換詞連用）：通用於繁體中文 md、零依賴、誤報可接受、換詞連用也抓得到。以本技能資料夾的絕對路徑執行：`node <本技能資料夾>/scripts/scan-connectives.mjs --self-test` 跑自我測試；用法 `node <本技能資料夾>/scripts/scan-connectives.mjs [--min 2] <md 檔或資料夾>...`（資料夾請限定在報告所在處，不要傳整個專案根）。輸出是候選，不是違規清單。
- 其餘判準（§3 表）不附程式。自建時：先寫判準，再寫程式；附自我測試（好句不誤報、壞句抓得到）；在自己的語料上實測誤報量；輸出只列候選。
- 自建或沿用掃描程式的結果，一律回到 §4 第一段處理：逐條判讀，不整批依候選改。

## 11. 修補先驗後寫（批次改原稿時）

SKILL.md §7 修正管線的寫法示意：每處修補先驗證恰好命中預期次數，全部通過才一次寫檔，避免默默漏改或改到別處。

```js
let files = {} // 路徑 -> 修改後內容(暫存)
let load = (fp) => files[fp] ?? fs.readFileSync(fp, 'utf8')
let rep = (fp, from, to, n = 1) => {
    let s = load(fp)
    let c = s.split(from).length - 1
    if (c !== n) {
        throw new Error(`${fp} 命中 ${c} 次(應 ${n}): ${from.slice(0, 60)}`)
    }
    files[fp] = s.split(from).join(to)
}
// 先呼叫全部 rep(...); 都沒有拋錯, 才逐檔 fs.writeFileSync(fp, files[fp])
```

改完後以同類判準重新掃描全部輸出（正文、圖名、圖內文字、用同一句的他本報告、相關規格），並重跑 lint。修補後之讀回與全文重掃見 SKILL.md §7 修正管線（「改後讀回」「重掃範圍是全文」）。

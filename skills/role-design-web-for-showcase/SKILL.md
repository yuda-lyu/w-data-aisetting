# 亮點展示圖設計規範

**定位**:亮點展示圖是**放在報告內**的成果圖:一張圖一個主張,畫面多,文字少,委託方會直接拿去呈報.它不是投影片,不是網頁,也不是報告內文換個版型.讀者第一眼就判斷「有沒有設計過」,看不出設計就會被認為偷懶;標題、配色、對齊的小誤差都會被看到.

**與其他技能之分工**:

| 情境 | 技能 |
|---|---|
| 配色取色程序、字體選擇、預設禁令、截圖評審之通識 | skill[role-design-web-for-prototype].本技能為報告用圖設定了較嚴之專屬規定,**與其衝突時,於報告用亮點圖範圍內以本技能為準**;已知衝突:①標題淺色圓底圖示(該技能圖示不放彩色或飽和圓圈);②標題內關鍵詞用標題主色(該技能預設禁令禁標題內換色之強調字);③標題列右側留白(該技能之頁面規則要求首屏右上要有東西,針對網頁首屏);④字級種類(該技能全頁最多 5 種,版型含放射總覽時較多);⑤連接細線與前後關係之陰影(該技能預設禁令禁細線與靜止元素陰影).本技能之預設色票已避開該技能禁用之紫/靛色系 |
| 對這類圖說「重新設計」 | 走本技能 §9;不走 skill[role-design-web-for-redesign],該技能管既有 production 系統 |
| 圖內之單一統計圖表(長條、折線)之形式與標記規格 | dataviz 技能(隨 Claude 提供,不在本庫;不可用時依本技能 §4 色彩) |
| 圖內之系統畫面取自 e2e 標準圖 | skill[role-coder-for-test-e2e];紅框為 #f26、5px.新增案例與重產標準圖須依該技能並先取得使用者授權;標準圖一經重產,本技能之裁切須重跑 `check-crops` |
| 圖內文字之文體與禁詞 | 專案之報告撰寫規則;無則依本技能 §2.不引用 skill[role-writer-report],其文體為標案白皮書體,不適用圖內短語 |

**閱讀順序**:本檔 → 要選版型時讀 [references/layout-patterns.md](references/layout-patterns.md) → 被指正或要自審時對 [references/pitfalls.md](references/pitfalls.md).

## 0. 六條鐵則

1. **先問成品放哪裡**.放報告就不做投影片的設計;調研也要查報告圖,不是投影片.
2. **一張圖一個主張,主角只有一個**.完成後瞇眼看,第一眼要落在主角;灰階下主角仍要最重.
3. **先看最大的矩形**.大區塊上下緣對齊,間距分層;外形不整齊,內容再好也看不出設計.
4. **強調色只給亮點**.色塊面積與圖示體積都是權重,大的東西不用強調色.
5. **圖內文字比照報告審**.假設自己是審查委員,逐句問「這句會被反問什麼」.
6. **量得到的交給程式,量不到的逐張看**.程式通過不代表設計好;取景、輕重與達意只能靠眼睛.

## 1. 動手前六問

答案寫進每張圖 html 開頭之註解(連同數據依據),不憑感覺開工.

| 問 | 怎麼做 | 典型錯誤形狀 |
|---|---|---|
| ①成品放哪裡 | 報告、投影片或海報,做法不同.報告用圖不用貼齊邊界之滿版色帶 | 用投影片的滿版報頭放進報告,一眼就像把投影片貼上來 |
| ②本期核心是什麼 | 先從任務書或進度提取本期主軸(範圍、對象、主題),取景與舉例對齊;現有畫面沒有就新增,不遷就 | 本期主軸是甲區,卻因現成而挑乙區畫面 |
| ③一句主張是什麼 | 提煉系統之亮點本身,寫成完整句;期別、案名等無關之字不放,委託方要呈現時可自行加註 | 標題放「某年度」,稀釋注意力 |
| ④主角與次要 | 成果是主角,手段與背景是次要;先分清楚才定配色與尺寸 | 手段區塊用強調色實底,壓過成果數字 |
| ⑤圖源與證據 | 系統畫面直接引用 e2e 標準圖(審查之一環,證明該功能確已測試),不用現場截圖或另拍之圖;數據寫明出處 | 為了好看另拍無紅框畫面,失去可追溯性 |
| ⑥讀者會反問什麼 | 逐項想委託方或審查委員會怎麼問,用字先堵住;不推卸、不指責前期或委託方 | 寫「已使用 N 筆」,被問「其他為何不用」 |

## 2. 圖內文字

**與報告共用同一份用字規則**:用字、禁詞只記在專案之報告規則與 lint,圖內文字套用同一份;不在圖端另記一份,也不得不參考報告就設計圖.以下為無專案規則時之預設,專案規則另有規定者從專案.

- **以圖與圖示為主,文字從簡**:委託方偏好圖內多圖或圖示,字不要過大,但縮進報告後仍要讀得清楚.
- **不湊字**:一個詞組傳達一個概念.時間概念不接資料格式(「逐時 JSON」),要傳達的是畫面能做什麼就直接寫.
- **不列一般技術**:非特殊技術不列名稱(內插法、檔案格式);寫做了什麼內容,不寫格式.寫前對程式確認實際做了什麼.
- **小標題寫清楚主詞,敘述機制一致**:單獨讀得懂(「系統效能提升」不寫「大幅提升」);同一張圖各區都寫亮點,不混入純數量,數量退為說明.
- **數字旁之用語須與數字同義**:數量是篩選後之有效數量,旁邊就不可寫「全部」;「全部」要與「有效」連寫.用字改完連同相鄰之數字與標題重讀一次.
- **數字要對系統之實際範圍**:面板合計與清單總數不同時,寫清楚是哪個範圍,不把局部合計寫成全體.
- **以讀者之反問驗用字**:字面中立不夠.借用他行業之術語描述系統能力會被誤解,先查證定義再用.
- **預設不放會成標準之數據**:明年量出來較差時,委託方會不會拿它比?實測耗時、倍數、百分比、排程週期預設一律定性(「大幅提升」「定時觸發」),實測數字只放測試報告.規模與規格(數量、核心數)不受限.委託方或專案明確要求放數字者從其要求,並在 html 註解寫出處.
- **標題與標籤不截短至失去原意**(「整體效能提升成果」不寫「整體效能成果」).
- **預設不放左下角說明文字**;圖內短句也要對流程,字數短不是可以不準之理由.

## 3. 標題

標題不是內文,要真正設計.現行作法(`assets/base.css` 之 `.ttl`):

- **位置**:一律放**左上角,獨立一列**,不與主要文字區擺在一起(否則沒有層次、有擠壓感);右側留白即可,不為了填空而升高下方區塊.
- **結構**:圓形圖示 + 一句完整之主張(主標) + 約一半字級之灰色副標(圖示關鍵詞;有先後者以箭頭連接,並列之原因以加號連接).
- **主色**:關鍵詞、圓形圖示與副標圖示用標題主色,圓底為其淺色;**不用強調色**,強調色留給亮點.

**不要**:標目加冒號(「某功能:敘述」,讀來就是報告內文搬上來);左側色條加文字(最常見,等於沒設計);貼齊邊界之滿版色帶(投影片式);期別年度.流程圖、架構圖等版面確有需要者例外.

**依據**(2026-11-04 逐項查證,可查得者如下;查不到或不一致者不採為依據):

- 標題靠左、與內容同一左緣:Urban Institute 圖表樣式指南明載「all titles are left aligned」(urbaninstitute.github.io/graphics-styleguide);Datawrapper 部落格稱靠左或靠右之文字比置中整齊、靠左時標題與圖對齊(datawrapper.de/blog/text-in-data-visualizations).
- 主標加較小之副標:英國 Analysis Function 之圖表指引建議標題兩個,一為傳達訊息之主標題、一為說明資料與期間之統計副標題(analysisfunction.civilservice.gov.uk/policy-store/data-visualisation-charts);Datawrapper 同文稱較不重要之說明用小而細之灰字.
- **「副標約一半字級、灰色」是本技能由定稿圖歸納之經驗值,不是上述來源之規定**:Urban 指南之標題 20px、副標 16px 斜體黑字;Analysis Function 未規定字級或對齊.
- 色條屬生成式簡報之常見樣態:plusai.com 部落格(廠商文章,僅供參考)列「上方或側邊之彩色強調條與 eyebrow 小標」為 AI 簡報常見樣態;未查得來源專談「標目加冒號」.
- 注意:Analysis Function 同文亦建議標題置於頁面內文而非圖內(為無障礙);本技能之成品為放進報告之 PNG,標題放圖內是本技能之決定,報告另有無障礙要求時由專案規則定.

## 4. 色彩

以下數值為本技能由定稿歸納之經驗值,檢核程式之常數與之一致,專案有明確色票者依專案.

- **強調色只給最重要之訊息**:成果之數字與文字才用.色塊面積就是權重,整區強調色會使讀者認定該區最重要,並擠壓其他同色重點;同圖強調色實底合計不超過畫布 10%(參 60-30-10).手段類區塊用次要色;核心與外圍不同配色,實色只給核心,外圍用中性底.
- **體積也是權重**:標題圖示等體積大者不用強調色;體積小之圖示用強調色不易被關注,可以.
- **要強調的字本身就是焦點**:不以鮮明實底襯白字,實底內也不放白底小框,否則注意力被底色與小框分攤到次要資訊;技術細節退為一行灰字.同區有 2 個大數字時,次要者換中性色.
- **重要文字用最強對比**:實底上之重要文字用白字;不重要之文字才退色(標 `data-minor`).不為求變化而犧牲可讀性(紅底黃字).
- **同組裝飾色用近似色依序變化**(每支箭頭或圖示各自平塗,不用 CSS 漸層):同組之箭頭、圖示,色相跨度約 40~100 度並逐步變化.不用色相差很大者(藍配深橘,很跳);也不用過近者(紅至粉紅,色階稀薄).資料類別色與圖例色階對應畫面者不受此限.
- **輔色要配合主色**:先定主色,輔色取色相相鄰者,飽和度較低,面積較小;與主色不搭時可把元素縮小,否則主色被擠壓與稀釋.
- **配色來回多輪就給選色器**:文字描述顏色對不上時,以 `assets/color-tool.js` 讓使用者直接選兩端,定稿後移除(§8).
- **不用白底框蓋圖**:白色讀起來像把背後之圖挖空;文字放圖之空曠處或白底上,前後關係用陰影.文字放在圖之空曠處時,超出圖邊會直接消失,要看圖確認.

## 5. 版面

- **單一主角,明確之尺度層次**:不要只基於底線一致去排(左小、中多格、右高);相鄰區塊排版太像就是沒設計過,要分區塊並用不同配色或風格.可混用不同大小之格(bento 格線).要圖片錯位重疊時,先算被遮處是否只含非主體,裁切與重疊位置一起定,不是先裁好再疊.
- **大矩形對齊**:大矩形區塊(含圖片)是畫面上最顯眼之形狀,並排時上下緣須落在同一條線,或次邊界對齊(欄內小標題與鄰欄上緣同高).不可為多放內容或填補空白而單獨升高、加長某一區塊.
- **間距分層**:大區塊間距要大,子區塊要小,同層一致(預設大區塊 16、子區塊 12).子區塊間距大於大區塊就是層次顛倒.圖要填滿欄寬時等比放大,不靠加大間距.
- **同階字級一致**:同階標題字級與粗細相同,只有全圖之主要亮點可大一階並用強調色;差異過大讀來就是沒有仔細調整.
- **焦點內字級要有明顯差異**:同一焦點之上下排,重點最大,次要明顯縮小.圓內文字依弦長配置,中間最寬,向上下遞減.
- **以墨跡對齊**:行框置中不等於看起來置中(混排字型時可差 5 像素);高亮區與大字以實際渲染之墨跡量測,以 `position:relative;top` 校正.箭頭等符號用 svg 置於 flex 列,不用字元.聚焦之處的微小誤差最顯眼.
- **多格畫面完整不裁切**:要呈現多格畫面就完整且對齊,先由畫面之長寬比定區塊尺寸再排版.裁切後看邊緣有無被切半之文字列;底部被截之圖表不要硬放.
- **圖示與標題同一列,說明佔滿全寬**:不要圖示下塞標題又塞文字,使右邊大量留白.
- **標籤放空白處**:不蓋住主要內容;畫面取景減少無資訊之大片空白,主要對象放在扣除圖例後之可見範圍內.多格圖例寬不同時各格各自計算;取景之中心與視覺中心常有落差,以「量測後再修正」收斂,不算一次就假設到位.
- **放射式版面**:連線等長、等角,位置有規則;箭頭小於主角,不搶視線.

**預設幾何**(1920×1080):外邊距 40;標題列 y 16~100;內容區 y 112~1040;大區塊間距 16;子區塊間距 12;主標 48、副標 25、小標題 26~30、說明 22~25;最小字 20(縮進報告後仍可讀);白底.

## 6. 圖像與圖示

- **圖示要連同旁邊文字看**:田字形放在「4 個…」前會被讀成「田 4」;選定後在實際字級下看一次.
- **圖示須完整**:下方開口之半圓儀表會被讀成被裁切.
- **圖示要傳達意含**:通用符號不代表主題(閃電不等於任何效能、燈泡不等於任何改善);找不到就上網查意象後自繪,單一描邊風格.
- **系統畫面裁切**:標準圖之紅框要驗像素,不靠算座標(框線含反鋸齒,內縮後仍常殘留 1~2 像素);紅框內緣先量好再放大.

## 7. 版型

依成果之性質選版型,細節與幾何參考值見 [references/layout-patterns.md](references/layout-patterns.md).

| 版型 | 適用 | 主角 |
|---|---|---|
| 放射總覽 | 全期亮點總覽(5~7 項) | 上方核心圓 |
| 資料接入 | 新接入之資料源 | 分布圖與放大圖 |
| 並排比較 | 多視窗、介面重構 | 多格畫面 |
| 大量呈現 | 大量資料一次呈現、效能提升 | 全覽畫面 |
| 流程時效 | 自動化鏈、全線時效 | 全寬時限橫帶 |
| 整體成效 | 期末整體總結 | 成果四格 |

同一份報告內各版型不同,但標題、字級、間距、主色共用同一份樣式.

## 8. 產製流程與檔案約定

**檔案**(皆在本技能根):`assets/base.css`(色票與版面元件,色票依專案改)、`assets/viewer.js`(檢視時縮放平移,不影響截圖)、`assets/index.html`(切換檢視頁,交給使用者看;一次單張全幅,不直排 iframe,因 viewer 接管滾輪後整頁會捲不動)、`assets/color-tool.js`(選色器)、`assets/example.html`(可通過檢核之骨架,含六問註解)、`scripts/render.mjs`(輸出 PNG)、`scripts/check-layout.mjs`、`scripts/check-crops.mjs`、`scripts/lib.mjs`(共用)、`scripts/selftest.mjs`(檢核程式之自我測試).`assets/` 內之檔複製到專案之圖夾使用(base.css、viewer.js 與 html 同夾);`scripts/` 不必複製,直接以技能根路徑執行.

**程式之執行環境與界線**:

- 須於**專案根**執行,專案須已安裝 `playwright`(含 chromium)與 `pngjs`(技能不帶 `node_modules`);缺依賴時印出原因並以離開碼 2 結束.離開碼:0 通過;1 有不合格項;2 參數、路徑或依賴錯誤.
- 只讀 `--dir` 指定之 html 夾及其引用之圖檔;只寫 `render` 之 `--out` 夾與 `selftest` 之 `./tmp/showcase-selftest`;圖名不得含路徑;不執行 shell.
- **不連外**:渲染時只放行 file、data、blob,http(s) 等外部連線一律中止,`check-*` 記為「外連」不合格、`render` 記為 requestfailed;字型、圖與腳本都須在本機.
- `check-crops --rules <檔>` 以 import 載入該檔(會執行其程式),只用專案自己之規則檔.
- 預設字型為 Windows 之微軟正黑體與 Bahnschrift(缺時退 Noto Sans TC、無襯線);墨跡對齊之容差以前者調校,換作業系統或字型須重看容差.

**圖示**:svg 直接放進 `<i data-ic="名稱">`(線框,同一套);常用者由專案之圖示套件取子集,找不到意象才自繪.

**畫面元素之標記**(檢核程式依此判讀):`.stage` 畫布;`.ttl` 標題、其內 `h1` 為標題文字、`.mk` 圓形圖示;`.pic` 裁切圖;`.hd` 欄內小標題;`data-peer` 同階標題;`data-sub="組別"` 同組子區塊;`data-minor` 次要文字;`data-t` 資料文字(`render` 查出界);`svg.ov use[fill]` 同組裝飾箭頭;`.foot` 左下角說明文字(`check-crops` 視為違規);`i[data-ic]` 圖示(`grid-2x2`、`gauge` 兩個名稱被視為違規,其餘圖示靠目視).版面元件(`.abs`、`.panel`、`.tag`、`.lb`、`.sm`、`.num`)見 `base.css`.

**檢核程式未涵蓋(須目視)**:標題之左側色條、離邊界數像素之近滿版色帶、文字落在 `.pic` 圖上之對比、取景與輕重、文字是否達意.

**流程**:

1. 答完 §1 六問,選版型;只屬單一專案之色票與用字留在專案.
2. 寫 html,畫面引用標準圖;每張開頭註解寫依據.
3. `node <技能根>/scripts/check-layout.mjs --dir <html 夾> --accent <強調色>`;放射等非分欄版面以 `--skip-align <名稱>` 略過大區塊對齊與間距分層,其餘項目照查.
4. `node <技能根>/scripts/check-crops.mjs --dir <html 夾> --baseline test/pics/`(圖內文字規則可以 `--rules` 帶專案之 lint).
5. `node <技能根>/scripts/render.mjs --dir <html 夾> --scale 2`,**逐張開圖看**:第一眼落在哪、最大的矩形、大片空白、文字是否達意.
6. 自己先審再交付,以 `assets/index.html` 給使用者看,不說「待你審」.放入報告前確認報告內之圖與 PNG 相同.

## 9. 被指正或反覆不滿時

- **先歸類,再全掃同類**:一處被指出,同類全部改(圖內文字、alt、標題、圖名、報告、規格、手冊內容).不要等使用者一張一張指.
- **被指沒設計感時,先真的上網調研**,附來源並說明來源可信度(多為廠商部落格時要明講);不用換色、加色條等微調交差.
- **調版面後重算**:搬動區塊會留下不一致之間距與對齊;先看外形,再看內容.回報時不把省空間當優點講,先確認外形沒壞.
- **新增檢核先用壞版本實跑**:確認抓得到才算數,再修圖.改檢核程式後跑 `selftest.mjs`.
- **原則寫進共用文件**:用字與注意事項於報告、投影片、出圖一致,不只記在片面之文件.

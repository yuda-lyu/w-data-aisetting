# 修前基準之複本:取法、換行、接續輪與修前紅之作法

> 本檔為 skill[role-coder-for-test] §10 第 4 點之細則,亦為 skill[role-coder-for-validate] 之 Step 2 第 5 點、Step 3 第 6 點(對拍之舊版基準)與 §7 第 2 點(重現測試)所引.作法歸納自使用端多輪「先紅後綠」與新舊對拍之實作(2026-11);其中換行之觀察在不同機器上方向不一,故本檔只規定「驗證」,不規定哪個指令必然產出哪種換行.

**觸發**:要取得「修前版」作基準——先紅後綠(新測試疊在舊版複本上看它紅)、新舊輸出對拍、以舊版重現 bug、要證明「其餘逐字不變」;新測試之輸入可能使修前版懸置、耗盡記憶體或起真實外部呼叫(§6);審查他人之此類作法.

## 1. 先判斷要的是哪一種「修前」

| 情形 | 修前基準 | 取法 |
|---|---|---|
| 已入版控,改動尚未提交 | HEAD | §2 |
| 未入版控之檔 | 改前之檔 | 改動**前**先複製到 `./tmp/<案名>/pre/`(skill[role-coder-for-validate] Step 2 第 5 點),事後無法重建 |
| 接續輪:工作樹已含前一輪(未提交)之成果,無檢查點 | 前一輪凍結之碼 | 動工前以 §2 法 1 留快照;未留者 §3 |

## 2. 取原位元組:不以 `git archive` 作逐字基準

**陷阱**:`core.autocrlf=true`(Windows 上常見之安裝預設)下,`git archive` 輸出之換行**可能與工作樹之原位元組不同**.使用端三次觀察皆為 archive 輸出 CRLF,與工作樹之原位元組(LF,或 LF 與 CRLF 混合)不同;本庫另在 git 2.53 + `core.autocrlf=true` 之實測,則是 archive 輸出索引之 LF、而部分工作樹檔為 CRLF——**方向不一,但皆可能不等於工作樹之原位元組**.以之作「逐字不變」之基準,會混入換行之差:逐字比對之測試假失敗;逐檔雜湊與先前記錄者不符.

**取原位元組之三法**(依要的是「工作樹現況」或「HEAD 之內容」選):

1. **要工作樹現況**:自工作樹複製已追蹤之檔,不經換行轉換——`git ls-files -z | tar --null -T - -cf - | tar -xf - -C <目的>`(未追蹤之檔另複製;排除 `node_modules`、`tmp`、`.git`).不建目錄連結.
2. **要 HEAD 之內容**:`git ls-tree -r -z HEAD` 列出,逐檔以 `git cat-file blob <物件>` 寫出原位元組(不經換行轉換).以先前已記錄之逐檔雜湊回驗(實例:改動檔之雜湊相符,而 `git archive` 之輸出雜湊不符).
3. **要「工作樹 − 本輪差異」**:複製工作樹後,對複本以 `patch -R --binary` 反向套用本輪之差異;回驗「各檔去 CR 後與 `git show HEAD:<檔>` 相同」.差異若經文字通道傳遞(議題留言、聊天),CR 可能全失(留言以 LF 存);補回 CR 後,**以位元組數與雜湊(如 sha256 前 16 碼)與原附件逐位相符,才當作還原成功**.

無論用哪一法:複本建好後以雜湊或逐檔比對**回驗**,不憑指令名稱推定其位元組.

## 3. 接續輪:取「前一輪凍結之碼」

情形:工作樹已含前一輪之成果(未提交)與本輪之改動,要以前一輪結束時之碼作修前基準.此時 `git archive HEAD`(或 §2 法 2)取得者**缺前一輪全部成果**,以之作修前基準,修前紅會夾雜前一輪之差異.

**動工前即知為接續輪者(前一輪成果已完成而未提交),最簡為動工前以 §2 法 1 複製工作樹(原始碼、測試工具、`package.json` 等)為修前快照**,不必事後重建(實例:以此快照得修前紅 8＋3 案).HEAD 恰為前一輪提交之基準者,§2 法 2 即可.

動工時未留快照、事後才要取者,以差異還原,比逐項手寫反向取代不易錯:

1. 以前一輪之附件(差異檔)套用於 HEAD 之原位元組複本(§2 法 2),得凍結版 F.
2. 與現行之檔做 `diff -u F <現行>`;**去掉非本輪之 hunk**(依前一輪報告之差異清單辨認哪些 hunk 屬前一輪之範圍).
3. 對現行之副本 `patch -R`(反向套用上一步留下之本輪 hunk),得修前基準.
4. 逐檔 `diff` 回驗:基準與 F 之差,**只剩第 2 步去掉之那些 hunk**.

(實例:12 個 hunk,11 個屬本輪、1 個屬前一輪之範圍;回驗時只剩該 1 個.)

## 4. 修前紅之鏡像根作法

把新測試疊在修前版複本上跑,得「紅」;作法與陷阱:

1. 複本置於 `./tmp/<任務>/pre`,內容依 §2 取得(不以 `git archive` 作逐字基準);只放必要之夾與檔.相依由上層之 `node_modules` 解析,不須建目錄連結(結案清 `./tmp/` 前依全域暫存檔規則先確認無目錄連結).
2. **新版才有之匯出,以替身提供**(拋「未實作」),常數照新值;**不為「以檔名列舉而判存在」之檔建替身**——列舉某前綴檔名之案會因替身存在而假綠,應令其載入即失敗.
3. **新增之具名匯出,測試以命名空間匯入取得**(`import * as X from …` 後以 `X.name` 取用):舊碼無該匯出時,具名匯入使整檔載入失敗(`SyntaxError`),所有紅都成「載入失敗」,看不出各行為之差;改用命名空間匯入後,舊碼之各案以斷言失敗呈現(實例:某旗標之等號寫法,舊碼離開碼 0 而非 2;字串之種子 ≢ 數字之種子).鏡像根可只疊「純新增匯出、無行為改變」之新版檔(如設定之旗標表),使期望值可取得.**被測之新模組整檔為新增者**,改於案內動態匯入(`await import(…)`):靜態匯入使修前版整檔載入失敗、0 passing／0 failing,無從逐案統計.
4. **載入即失敗**(匯入不存在之模組)之測試檔會使整批 `mocha` 中止 ⇒ 各檔分別跑,並區分——**紅(斷言失敗)**、**載入失敗**、**行為保持而綠**、**逾時(懸置,§6)**、**鏡像所致之假紅**,報告分列(實例:新測試 33 案 = 32 紅 + 1 行為保持,另一檔載入失敗;另一輪 46 passing / 39 failing,failing 皆為行為之差).**逐案核對紅燈是否為產品行為之差**:依檔案系統讀相依之案(依賴閉包、檔案存在檢查)於鏡像根下可能因鏡像缺該相依而假紅(實例:鏡像缺某相依套件之資料夾,閉包類之案假紅),此類另列,不計入修前紅.
5. 複本置於 `./tmp/` 下時,依相對路徑組字串之案(任務書內之程式夾路徑)須先正規化,否則路徑長度與內容隨複本位置而變.
6. 紅燈要確認有摘要行(`N passing`／`N failing`)且各案可逐案統計,見 skill[role-coder-for-test] §6.3 第 1 點.

## 5. 副本之收尾

為驗證建之暫存副本(含相依):自工作樹複製(§2 法 1),相依以其 lockfile 精確安裝,不建目錄連結;結束前以不跟進連結之方式確認副本內無連結,再刪除並回驗(全域暫存檔規則;細節見 skill[role-command-windows] §6).

## 6. 修前版之副作用、懸置與耗盡記憶體

新測試之輸入在修前版上未必只得「斷言失敗」;以下三種先處理,才把新測試疊上修前版(先紅後綠、變異批次皆然):

1. **退回預設而起真實外部呼叫**:修前版對無效輸入可能退回預設之執行檔(PATH 上之外部 CLI)或官方端點,修前紅與變異批次因此起真實子行程、送真實請求.一律在 skill[role-coder-for-test] §5.2 之守門(測試內自包含之 PATH 移除與 `fetch` 替身)下跑.
2. **同步懸置**(無窮迴圈):mocha 之逾時計時器無法中斷同步迴圈,整個行程卡住.這類輸入之案改以子行程執行並給逾時(測試工具起子行程,逾時即判該案失敗);子行程之逾時須**大於最慢之合法輸入**,否則對照組(修後版之合法輸入)假紅而中止批次.變異批次中會卡住之候選,以環境變數縮短其等待(提案端:每個卡住之候選由 15 秒縮為 5 秒),卡住型之變異以 `--bail` 於首個失敗即停.
3. **耗盡記憶體或行程崩潰**(提案端實例:`length` 為 `Infinity` 之 Proxy 使修前之 `for (i < list.length)` 不收尾,離開碼 134、無摘要行):此類輸入不列入「會在修前版跑」之測試,其判定另以變異證明.

修前紅之報告依 §4 第 4 點分列,逾時(懸置)與崩潰不併入「紅」.

# 計時器相關之測試:以事件同步,不以延時偵測

> 本檔為 SKILL.md §8 之細則.來源:2026-10-28～29 wsemi 三輪全面套用(36 組函數、約 70 個以延時同步之案)之實作與負載試驗——以延時同步之案於人為負載下失敗(例:事件迴圈阻塞 49 次、重度阻塞 18 次),改為事件同步後皆為 0.

**觸發**:測試輪詢、偵測、重試、節流、防抖、排程、逾時、等待類函數;測試內出現 `await sleep(N)`／`setTimeout(resolve, N)`／固定 `delay(N)` 後即斷言;子行程或外部程序之輸出順序以內部計時器隔開者.

**為什麼**:計時器與其回呼受 CPU 負載影響而時差不定,「等 N 毫秒後檢查」永遠含不穩因子;單獨重跑 5 次皆過不代表穩定,高負載(多套件並行測試、e2e 多開)時才現形.

## 1. 以事件同步,不以時間同步

- 被測函數提供觀察回調 `opt.onTrace`:同步呼叫、傳**凍結**之 `{ type, ... }`、`this` 為 undefined、拋錯與回傳值(含 rejection)一律忽略、未傳時不組事件物件(零成本).
- 欄位:原始值快照;**不放 Error 物件、陣列、內部可變參照**;不暴露輸出內文時只放長度;除 `type` 外之欄位名**不得為 `type`**(第三方事件種類用 `kind`／`evType`).
- 自有套件一律沿用單一實作(wsemi `getTrace`),不各自寫等價實作.
- 測試以「等第 N 個事件」為同步點(紀錄器之 `wait(pred, from, n)`),續行時再對事件內容與最終狀態斷言.

**典型錯誤形狀**:輪詢模式之測試每步 `sleep(30)` 後改狀態,高負載時取樣尚未發生就改了下一步,少一筆.

## 2. 斷言語意,不斷言次數與時刻

斷言比對之基準、略過之原因、事件順序與對應、最終狀態與上下界;呼叫次數若為規格,斷言上界與對應關係,不斷言隨真實時間比例而變之絕對值.

## 3. 時間本身是規格者用假時鐘

- 防抖之等待、節流之窗口、逾時／停滯門檻、重試間隔:以可控時間來源推進(Node 內建 `node:test` 之 `mock.timers`,含 `Date`,可在 mocha 內使用),並以觀察回調斷言事件內容與**事件之虛擬時刻**(取代 `ms < N` 之牆鐘門檻).
- 限制:①同一 ms 內多個回呼之間不讓出 microtask;②`performance.now`／`hrtime`／`setImmediate`／`process.nextTick` 不受控——以這類時鐘計時者改以事件等待並只斷言下界;③microtask 啟動之函數須先讓出(flush)再推進;④**防懸置上限(等事件之逾時)須用模組載入時保存之真實 `setTimeout`／`clearTimeout`**,否則假時鐘下失效而缺陷版整案懸置、後續案連鎖失敗;⑤真實 I/O(本機 socket、子行程、檔案)不受假時鐘控制:時間門檻類改記憶體內回應(`ReadableStream` 由測試放行每一塊)＋假時鐘,以事件為同步點再推進;同行程之本機伺服器若以被 mock 之計時器決定出資料時刻會失效,改由測試閘門決定;⑥假時鐘期間不得使用真實 undici `fetch`(其內部計時器還原後殘留並被後續假時鐘案誤清);⑦**假時鐘視窗內之 clear 對視窗前建立之真實計時器為空操作**(`mock.timers` 取代之 `clearInterval`／`clearTimeout` 只認假計時器):前一案以真實時鐘排入、於下一案假時鐘視窗內才自停之 repeat 型計時器(如防抖之偵測 interval)即漏清而永久存活,mocha 寫出報告後行程不退出且偶發——啟用假時鐘之工具函數須記下視窗內建立之假計時器,其餘轉交原生 clear;負載試驗須偵測「測完不退出」(報告寫出後逾時即判失敗並記錄撐住行程之資源與其建立堆疊).

## 4. 真實檔案監看:步進式,不用假時鐘

事件來源是作業系統(chokidar 等):做一個操作 → 等被測函數回報「已處理該操作」之事件 → 才做下一個;起始先等 `ready`;一個操作產生多個事件者(rename)等到預期之全部事件.

## 5. 子行程與外部程序

1. 輸出順序、分段與「已啟動」不以子行程內計時器隔開,改**事件閘門**:子行程輸出一段後輪詢標記檔,父行程於資料事件見到該段才建立標記檔放行下一段,順序由因果決定.
2. 就緒改等可觀察條件(子行程先輸出就緒標記、檔案已存在且確被鎖定、串流 `close`／`finish`、`exit`);條件輪詢之防懸置上限用真實計時器.
3. 驗證樹殺須孫行程 detached(Windows 下 libuv 把非 detached 之子行程放入 KILL_ON_JOB_CLOSE 之 job,只殺父亦連孫一起結束而無法分辨).
4. **無計時器之函數**(複製、合併、tree-kill 包裝):其固定等待在測試端,改等被測物事件或可觀察條件;**不必為了測試在 src 硬塞計時器或回調**.

## 6. 否定斷言之觀察窗

「已停止」「不得再量測」無事件可等,可保留短暫真實等待,但須另以「停止」事件斷言停止本身;觀察窗只能用於否定斷言(負載只使其漏抓、不使其誤判),不得用於肯定斷言.

## 7. 懸置以事件判定

子行程或 Promise 之「是否懸置」,以「已過應 settle 之點仍有事件」判定為 pending,不以牆鐘看門狗;等不到任何事件之懸置由外層逾時兜底,該上限只防懸置、不表達規格.**不得以重試掩蓋、不得只加大 timeout.**

## 8. 未傳回調時行為不變須有測試

每個加觀察回調之函數,以同一情境跑五種回調(未傳、紀錄器、拋錯、回傳 rejection、非函數),結果須相同且無未處理之 rejection;事件凍結、各 `type` 欄位固定、`this` 為 undefined、未傳時不組事件物件.

## 9. 每個改寫附變異證據

對原測試要抓之缺陷做變異,新測試須仍抓得到並**對照舊測試**:舊版抓得到者新版也須抓得到;舊版也存活者屬新版更強或等價,逐一歸因;「事件已通知但實際動作沒做」類變異需成對移除內外兩道防線才現形者,列為設計重疊.

## 10. 負載試驗:穩定與否之判準

- 以人為 CPU 壓力(壓力行程數 ≈ 邏輯核數)＋可重現之事件迴圈阻塞(每 1000ms 阻塞 400ms)＋重度阻塞(每 3000ms 阻塞 1500ms)跑同一批測試,改造前後同次數(至少 8～10 次),比較各案失敗率.
- 改造前之基準以動工前快照**先跑完**再實作與派子代理.
- 負載試驗使整機滿載,執行時須獨佔測試資源(他套件之測試排隊),結束以 PID 回驗壓力行程全數結束.
- **每次執行須自行退出**:以記錄檔之更新時間判斷,不只看行程存活——測完不退出(未關之計時器或 socket)會整段佔住獨佔資源.以 `process.getActiveResourcesInfo()` 比較「停止後計時器回到原值」時,基準須與比較在同一狀態量測(mocha 對 async 案／hook 於回傳 promise 後才建立其逾時計時器,先後量測會差 1).
- **基準偏寬時**(裕度大之案、計時器與 I/O 同時被延遲而互相抵銷之停滯／總時限門檻案)改善證據須併用:重度阻塞、測試輔助之對照實驗(持有者延遲啟動、執行緒池壅塞)、單案耗時縮短、「設計去除固定時刻假設」.

## 11. 先驗證 harness 假設

「負載下怎麼錯」是推導,實作前宜以實驗證實(例:Node 於呼叫 `close()` 當下即把 `fd` 設 null,原判「fd 關閉慢於 300ms」不成立).

## 12. 不在本章範圍:效能時限類

斷言「X 毫秒內完成」而受測者非計時器函數(如清洗、轉換之效能)者,不屬觀察回調之範圍:集中標記、獨立執行,裕度依負載試驗訂定,或改斷言複雜度與相對比較;同樣不得以重試掩蓋.

「處理量有界、不展開」之斷言可改量**本行程之 CPU 時間**(Node:`process.cpuUsage()` 之 user＋system)取代牆鐘差——行程被擱置之時間不計入,工作量失控時仍成比例增長.限制:量測區間內只等已解決之 Promise 與微任務(讓出到巨任務會把同行程他人之耗用算進來);CPU 時間含 GC 等執行緒、粒度粗,限值仍依負載試驗實測最大值訂裕度;並以「阻塞而不耗 CPU」之變異(如 `Atomics.wait`)證明新斷言不受擱置影響、而舊之牆鐘斷言會紅.

改造前三種負載皆 0 失敗者(被測計時器極短且與測試之等待同輪建立時,Node 依到期時間排序,負載下不顛倒),失敗率無從比較:改以「非缺陷之時序變異」(如延遲 1ms 改 40ms——舊測試轉紅、新測試不受影響)與單案耗時佐證.

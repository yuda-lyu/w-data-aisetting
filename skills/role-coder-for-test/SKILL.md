# 測試規範(全層級)

**觸發條件**:寫、改、審、拆、移除、重構任何測試;新增測試檔或盤查 test 目錄;產或重產 baseline;設定 `package.json` 之 test script、runner 或 port;跑測試;產製測試/樣本/示範數據.本篇整篇入 context 逐項比對後才動工.測試全綠只證明回歸未壞;宣告完成之判準見 skill[role-coder-for-validate].

## 1. 測試是規格的翻譯,不是現狀的指紋

assertion 必須是 spec 的可執行翻譯,不是[跟上次跑出來一樣]的指紋.[產 baseline → `buf.equals(baselineBuf)` → 通過]不是測試,是 regression detector——若 baseline 產出時系統已偏離 spec,偏離被凍結為真理,測試通過反而是 false negative.

1. **Reflex check**:寫每條 assertion 前自問[這條 predicate 對應 spec 哪一句?]對不上＝現狀指紋,刪或回 spec 找對應(skill[role-coder-for-spec] §4);每條 assertion 註解標明對應之 spec 句.(LLM 偏好機械安全路徑如 `buf.equals`,此 check 就是擋這條.)
2. spec 含[畫面/顯示/轉跳/卡/出現/看到/看不到/進入]等觀察字眼 → 必須有對應之 UI 斷言,純後端 trigger 才能只驗 DB;spec[N 步後 → 觀察 M] → 測試步驟數 ≥ spec 動作數,被 helper 抹平的步驟明標[未走 UI].
3. 能驗端到端不變式(外部應用實際查到的結果)就驗它,不只驗中間資料存對.
4. 寫 assertion 時發現實作把 N 種狀態併成 M 種訊息 → 依 skill[role-coder-for-spec] §3 聚合層規則處置,不改 test 將就.
5. 走到產品缺陷的步驟:依 skill[role-coder-for-spec] §3 進〈已知落差〉,該步拋帶已知缺陷標記之錯誤讓 runner 標 pending;不用放行旗標讓壞畫面通過,不寫[baseline 凍結的是現況畫面].
6. **同一規則集中為單一包裝、再套到 N 個呼叫點時**,只測包裝本身不夠:測試須列舉全部 N 個呼叫點之接線案(或逐點植入變異——把該點改回舊寫法——確認有測試轉紅);呼叫點與包裝之接縫至少一案不用替身(stub/mock)走真實路徑.why:包裝之單元測試全綠時,某個呼叫點仍用舊寫法或傳錯參數照樣通過;替身會把接縫上之錯誤一併遮掉.**典型錯誤形狀**:提案只測新包裝,把 3 個呼叫點改回舊寫法測試仍全綠,外審才指出.另:**把兩處重複之常數集合併為一個共用常數後**,原本「只改一側」之變異會同時動到兩個使用處而失去專屬性;變異須改植於各使用處(例:在各使用處之判斷各加一個排除條件),才保有「只此一側」之鑑別力.
7. **被驗之物為由源頭資料導出之視圖、截止版或子集**(如帳本之截止視圖、過濾後之子表)時,oracle 取「以同一份源頭另行建構之同一物」(例:以同一份合成資料、不同終點各建一本帳本,比對截止視圖與之逐欄逐位相同),不取另一套手寫之算式(手寫算式與實作同錯時測不到).oracle 須含:界線之案(終點恰等於某事件之邊界),以及「讀得到全期資訊之下游」之案(下游函數所見之總數、全期統計是否仍為全期).**典型錯誤形狀**:初版只在最終輸出端裁切,獨立複審才指出下游之挑選函數所見之總數仍為全期;界線案亦因變異(`≤` 改 `<`)於一般終點存活才補.
8. **斷言「已通過前一道檢查、到達下一道」須用正向證據**:以「離開碼不是 N」「輸出不含前一道之訊息」證明已越過前一道者,於失敗通道改變(各道改用同一離開碼或同一訊息格式)後即失去意義——或照綠而成假綠,或因前後兩道同碼而轉紅;改斷言**下一道之固定訊息**(或其可觀察之副作用)出現.**典型錯誤形狀**:失敗通道統一後,6 處以「離開碼不是 2」證明「已通過旗標檢查」之測試全數失效,至全套前之子集首跑才發現.

## 2. 語意斷言為主,pixel baseline 為補強層(雙向約束)

1. 語意斷言驗[特定資訊在/不在],pixel baseline 驗[整體畫面長相],抓的是不同類 regression;對有 stable visual state 的 case,baseline 是**必要補強層非 optional**.雙向約束:只有 pixel-equality 沒語意斷言不接受;modal/轉跳/UI 切換 case 只有 innerText/URL 不加 baseline 也不接受.
2. 補強層之 pixel 比對採**反鋸齒感知容差**,非 byte-exact——白話:不要逐 byte 比整張圖(`buf.equals`),改用[允許少量像素不同]的比對:pixelmatch(`includeAA:false` 自動忽略反鋸齒邊緣像素)+ `maxDiffPixels` 容差.why:SVG icon/字型邊緣之次像素 raster 跨 browser session 不決定性,byte-exact 會把[肉眼等同的反鋸齒 noise]當失敗 → 無止境 flake.**典型錯誤形狀**:icon 全面改用 SVG 後,原本的 byte-exact 比對炸出大量次像素 flake.容差只放補強層,主驗證仍語意斷言(不違反第 1 條);真 regression(icon 換/版面位移/顏色變)量級遠超 maxDiffPixels 仍被抓.同業界 Playwright `toHaveScreenshot`(maxDiffPixels/threshold).
3. 產 baseline 前,從 spec 自己列[每張預期看到什麼]清單;產實際 baseline → 比對 → 不吻合修系統/修 spec,不是改 baseline 將就;不把預期清單丟給使用者 review(skill[role-coder-for-spec] §2).
4. 定點重產(既有之單案例重產)須先取得授權,且只產受影響者;無差別重產＝把 bug 凍結為真理.已審過的圖被重產等於換掉真理,即使內容看起來一樣.全量執行之全量趟(首選單趟收集:`E2E_COLLECT=1` 比對加 `--accept` 採用;次選重產趟)由該專案之主責 agent(或主控)自行發動,不必逐次請示——寫出或收集不等於採用:採用(`--accept`,或保留重產趟之寫出)須經審差異(逐張分類;CHANGED 以改前改後並排圖目視裁定),並於回報中逐張列出採用之變更供使用者事後檢視(可否決,否決即還原).只取數字之全套只跑比對,不重產.細節見 skill[role-coder-for-test-e2e] §7.9,§7.11.
5. 比對失敗之證據(capture/baseline/diff 三聯組)落專案根 `./testPending/`(§4),永不覆蓋、不自動刪——偶發 flake 的當次證據常在隔天才分析.

## 3. 測試分層與檔名前綴:`e2e-` / `api-` / `unit-`

測試檔一律以前綴標明層級,**同一層 `test/` 目錄內以前綴分類,不開 `e2e/` `api/` `unit/` 子目錄**(子目錄只給資產與工具,見 §4):

| 前綴 | 層級 | 判準 | 典型 runner |
|---|---|---|---|
| `e2e-` | 端對端 | 真瀏覽器 + 真鍵盤滑鼠,act/assert 走 user-facing 路徑 | Playwright(mocha 逐檔或直跑) |
| `api-` | 介面 | 直打 HTTP/RPC 端點,不經 UI | mocha / jest |
| `unit-` | 單元 | 純函式,元件掛載(jsdom),不起 server | jest / mocha |

- 檔名 `e2e-xxx` 但 act 用 `page.evaluate` / `vm.method()` → 名實不符,**正名為 `api-` 或 `unit-`,或重寫成真 e2e**(skill[role-coder-for-test-e2e] 有 L1-L6 操作層級表).
- UI 無法自然觸發者(fail-closed、後端並發序列化)→ 下沉 `api-`/`unit-`,不在 e2e 硬造.
- 共用層與輔助工具(setup 模組、runner、產生器)不帶 `.test.` 中綴且放 `test/tools/`(§4),避免被 runner 當測試檔抓取.
- 專案若無某層(如純前端函式庫無後端)則該前綴不出現,不需硬造.

## 4. 目錄配置:什麼放哪,誰負責清

| 路徑 | 放什麼 | 規則 |
|---|---|---|
| `test/*.test.mjs` | 測試檔 | 一律 `.test.mjs`,依 §3 前綴分層;不開 `e2e/` `api/` `unit/` 子目錄 |
| `test/tools/*.mjs` | 輔助測試與配套工具:setup 共用層、逐檔隔離 runner、baseline 產生器 | 一律 `.mjs`,不帶 `.test.` 中綴;同一 helper 只定義一次,測試檔內第二份近似實作＝補丁堆積 |
| `test/pics/<flow>/` | e2e 標準圖(baseline) | 入版控;spec 或規範另有指定路徑者從其指定 |
| `test/_tmp/<案名>/` | 測試中之臨時/中繼檔(暫時 settings、fixture 副本、合成 log、資料庫快照) | gitignore;各測試自建專用資料夾,由該測試檔之 `after` 或 setup 之 cleanup 刪除,測完即刪,不殘留 |
| `./testPending/` | pixel 比對失敗之三聯組證據 | gitignore;ms 時間戳、永不覆蓋、**不自動刪**(人工清理) |
| `./tmp/` | AI 代理暫存區(全域規範之暫存檔規則) | **測試程式禁用**——隨時會被整個清除,測試途中被刪即假失敗.**典型錯誤形狀**:暫時 settings 與 golden 產生器寫在 `./tmp/`,隨一次清理佚失 |

### 4.1 測試不得改寫版控內之檔

**觸發**:測試建出「含模組層常數根(如 `ROOT = process.cwd()`)之專案物件」,或呼叫會自動整理、歸檔、產報告、更新狀態檔之流程(輪末鉤子、文件整理);新增整合案之前盤查既有測試.

**why**:把專案之各資料夾改到暫存夾**並不改變該常數根**;該流程於所屬檔案逾上限時,會改寫根下**版控內**之文件(經驗、回饋、狀態類).「本庫 `git status` 乾淨」不能證明沒有此問題——平時靜默,只在檔案逾上限時才出手.**典型錯誤形狀**:8 檔 40 案於文件逾上限時改寫版控之文件;事後新增之整合案又成為第九個觸發者.

1. **測試須明關該流程**(設定項或注入參數),不依賴暫存夾之改向.
2. **守門兩層**:①靜態:含「建構該物件之呼叫」與「該流程入口字樣」之測試檔,須含關閉設定,否則失敗;②動態:同一次執行內,每個測試前後比對該根下版控夾之大小與修改時間——檔案頂層之 `afterEach` 只記錄、`after` 才失敗並列出測試與檔名,以免首個違規中斷其餘測試.動態守門之訊息須註明「全套執行期間人工編輯該夾之檔亦會觸發」,以免把肇因誤指向當時正在跑之測試.
3. **查觸發者全集**:於隔離複本把被整理之檔補至逾上限,對寫檔函數加呼叫紀錄,以 mocha 根層級掛鉤記當前測試名,跑全套,得觸發者全集;不以「本庫乾淨」為證.

## 5. 執行:`package.json`、mocha 與 port

- 請勿使用`.mocharc.json`,此會造成套件與專案批次處理機制無法統一,無法自動化調整與擴充,請勿自行創建使用.

- 若agent想用mocha運行指定測試檔,請自行編寫指令執行.

- `package.json`內本來就該放全部單元測試的指令,不是為了agent方便執行多種測試指令而被視為指令庫.**自有套件**(函式庫、元件、工具類)之`package.json`內scripts一律僅提供test,也就是只提供`npm test`快速指令,變更會造成套件與專案批次處理機制無法統一,請勿自行擴充調改.**自有計畫/專案**(系統、網站等應用)不在「僅提供test」之列,既有之serve/build/lint/deploy等指令照留;但測試類指令同樣只有test,不為agent方便增設變體(要跑單層或單檔依上條自行編寫).

- `package.json`內,若有要使用mocha,scripts給予值請依照有無parallel兩種情形,限定使用其對應指令:
**有parallel**:`mocha --parallel \"test/*.test.mjs\" --timeout 180000`
**無parallel**:`mocha --no-parallel \"test/*.test.mjs\" --timeout 180000`

- 啟動伺服器要開 port:基準埠 ≥ 8000、寫死、禁止隨機.e2e 之實際埠由 w-package-tools-e2e 之 `reserveE2ePorts` 依占用自動位移(順序固定,仍非隨機;見 skill[role-coder-for-test-e2e]).非 e2e 測試之監聽埠要與他套件錯開,或用作業系統配發(`listen(0)`),不要依賴 8080、8091 等常用埠,否則多套件同跑時會撞.

- **用到全機單一資源之測試**(Word／Excel 等 Office COM、桌面滑鼠鍵盤、螢幕截圖、固定之系統服務):`mocha --parallel` 下這類測試**一律集中於同一測試檔依序執行**,不因[只跑幾秒]留在別檔——兩檔同時驅動同一資源會互相關掉或搶走對方之實例,現形為偶發之內容錯誤而非明顯衝突.以全域計數檢查殘留(行程數、暫存檔數)時,只認本測試建立者(記 PID 或專屬前綴),他行程可能正以同名前綴產生檔案.驅動 Office 者之實例隔離案組與看門狗另見 skill[role-coder-for-office-com] §7.
- **跑可能顯示桌面 UI 之版本前先起可見視窗看門狗**(尤其是修前版本之紅測:舊版可能跳出[檔案使用中]等對話框而卡住):看門狗於測試期間偵測新出現之可見視窗並記錄、結束之;強制結束開著文件之 Office 程序後,清除其因此加入之停用項目並回驗,否則該檔之後每次開啟都跳訊息框.
- `--grep` 過濾掉 outer `it` 時,nested `before` 會在 DB 未 setup 前執行(徵狀「找不到 user / 30s timeout」是 artifact 非 production bug):`--grep` 涵蓋 outer 至少一個 case、或 nested 自己 setup、或 outer 改 `before`.

- **盤點各測試檔之案數**(如核對 README 之測試表):`mocha --dry-run --reporter json --reporter-option output=<檔>` 不實跑即得全部案,每案帶所屬檔 `file`,依 `file` 分組計數(實測 mocha 12.0.3);與 README 測試表逐檔對照,可一併查出案數過時、缺列之檔(非本輪所致者只報告,不順手補).

- 預估超過 2 分鐘之測試執行(全跑,長鏈)依全域規範之長任務規則,先調用 skill[role-setup-scheduler-for-session]:背景指令一律明給 `timeout`,超過 115 分鐘者 detached 執行.

### 5.1 跑他套件(複本、沙箱、發布包解開之目錄)之測試

**觸發**:在某專案之樹下,對另一個套件之複本(沙箱、`npm pack` 解開之目錄)跑其測試,或審查此類作法.**命中即讀 [references/sandbox-run.md](references/sandbox-run.md)**(守門模組全文與實測).

**why**:套件之測試常於載入時以行程之工作目錄為專案根而讀設定檔;裸名匯入、git、eslint 皆向上層目錄尋找——在上層專案之樹下即讀到上層專案之內容(可能含機密),且無任何訊息.**典型錯誤形狀**:自上層專案之目錄以 `node <複本>/node_modules/mocha/bin/mocha.js …` 起測,測試於載入時去解析上層專案之設定檔(兩次,幸皆解析失敗、未印內容);沙箱未自建 `node_modules`,裸名匯入向上解析到上層專案之 `node_modules`(版本不同而測試照過).

1. 動手前先查該套件之測試如何定位設定檔與專案根(讀其設定載入處與測試夾具).
2. **一律以該複本之根為工作目錄**:`npm --prefix <根> test`(實測 script 之 cwd 即 `<根>`),或以包裝程式設定工作目錄與其專案根變數;**不自上層專案之目錄直接起 runner**.派工時任務書須明寫此條(全域 §2.1〈任務書必寫〉).
3. 沙箱位於另一個專案之樹下時:先在沙箱**自建** `node_modules`,放相依套件之發布包複本(不建目錄連結);不用 git;eslint 明指該套件之設定(`-c <設定檔>`).
4. **要證明沒有向上解析**:以 `NODE_OPTIONS=--import=<守門模組>` 加 `module.registerHooks` 掛解析守門,凡解析到沙箱之外即拋錯(寫法與實測見 references;ESM 與 CJS 皆擋).
5. 於**發布包解開之目錄**跑全套:`npm pack` 之發布包不含 `.gitignore`,依賴它之測試於此配置必敗,驗證步驟須寫明哪些測試因此排除;安裝相依產生之 `package-lock.json` 視 npm 版本可能含倉庫位址,跑「發布內容不含內網位址」類之測試前先檢查並刪除.每輪之步驟(pack → 解開 → 複製 lockfile → `npm ci` → 移除真實外部 CLI 之 PATH 並驗證 → 限制平行度)、新版冷卻期之 `ETARGET`,以及解開目錄可兼作變異之鏡像根,見 references §3 第 5 點.

### 5.2 會起外部程式或送外部請求之測試(外部 CLI、付費 API)

**觸發**:被測物依名稱自 PATH 起外部程式、或對外部端點送請求(外部 AI CLI、付費 API、寄信);跑其修前版(先紅後綠、變異之鏡像根);改動這類選項之判定.

**why**:被測物對無效輸入之處置,在修前版或變異上可能是「退回預設」——對外部 CLI 為 PATH 上之預設執行檔,對 REST 為官方端點——修前紅與變異批次因此起真實子行程、送真實請求(計費、資料外送).反過來,把真實 CLI 自 PATH 移除後,需要它之測試改為略過,其紅燈被掩蓋.

1. **守門寫在測試內、自包含**:`before` 把 PATH 換成移除真實 CLI 所在資料夾者,並以 `where`／`which` 驗證已找不到,`after` 還原;全域 `fetch` 換為記錄用替身.**不以「PATH 上有真實 CLI 即拋錯」守門**——開發機之 PATH 本就有真實 CLI,拋錯式守門使整檔在使用者自己之機器上失敗,且依賴外部包裝腳本.
2. **移除後被掩蓋之測試**:需「真實 CLI＋本機假服務」之 `api-` 測試會 `this.skip()` 而 pending.改動某選項之判定時,Grep 測試目錄內以真實 CLI 驗該選項之 `api-` 測試(`this.skip()` 搭 `--version` 類煙霧呼叫者),於真實 PATH 下單獨跑過;並依 skill[role-coder-for-validate] Step 3 第 5 點比對 pending 名單.**典型錯誤形狀**:兩輪全套皆在移除真實 CLI 之 PATH 下跑,某 `api-` 案始終 pending,至發布前之真實 PATH 全套才紅 1 案.
3. **哨兵法**判斷「真實 PATH 下跑全套是否安全」:以同名之記錄用假執行檔(Windows 為 `.cmd`;每被啟動即附加一行至測試暫存檔)置於 PATH 最前跑一次全套,得出實際會以預設名稱啟動真實 CLI 之測試清單;清單為空或皆屬預期者,真實 PATH 之全套才不會意外起外部呼叫.
4. 「提前判定應使外部程式一次都不被啟動」之斷言(零次啟動),見 §10 第 1 點.

### 5.3 測試時取得外部執行檔、資料或 CDN 函式庫

**觸發**:測試(或被測物於測試中)於執行時取得外部資源——內附執行檔之首次取得(`ensureBins` 一類,含經依賴套件取得者)、下載檔案或資料、測試開啟之頁面自 CDN 載入函式庫;或寫、改這類測試之時限與共用工具.

**why**:`mocha --parallel` 之 worker 是各自獨立之程序,同一程序內之共用(單例、快取之 Promise)跨不過去——各 worker 各自下載同一份、互搶頻寬,一起變慢.使用端之內附執行檔快取常位於 `node_modules/<依賴>/` 之下,依賴一升版即清空,於是「首次取得」恰好發生在連動後之跟跑測試裡.mocha 每案之時限(常為 180 秒)又短於下載函式自身之預算(重試、停滯偵測、每檔上限),下載仍在進行就被判逾時.CDN 則於網路不穩時整批轉紅,與被測程式無關.**典型錯誤形狀**:依賴升版使快取清空,平行之 8 個測試檔各自下載同一份 400 MB 之瀏覽器,全部超過 180 秒而逾時;下載其實在 3 分多鐘後完成.

1. **取得集中於一個共用工具**(`test/tools/`):各測試檔經它取得,不在各檔各自呼叫;被測物會「隱式」取得者(未給執行檔路徑時自行取得),在呼叫被測物之前先經共用工具取一次,使其命中快取.
2. **該處之時限對齊下載之預算**(例:下載函式之最多嘗試次數 × 每檔上限,另加解壓),以 `this.timeout(…)` 寫在取得之 `before`,不沿用全域之 180 秒;其後之案只用已備妥之路徑.
3. **跨程序只下載一次**:取得函式須保證多個程序同時呼叫時只有一個下載、其餘等候後讀快取(鎖檔＋逾時＋過期鎖之接手);下載函式未提供此保證者,於共用工具內以鎖檔補上,不可讓各 worker 各自下載.**確認實際執行的是帶鎖之那一份**:依賴套件之發布檔(UMD 之 `dist`)常把它所用之函式庫版本一起打包,使用端升級自己之依賴對經該 `dist` 之取得無效(`npm ls` 顯示 deduped 亦會誤導)——改經其原始碼入口(`src/…`)或待該依賴以新版重建發布;以事件或下載次數驗證,**全綠不證明只下載一次**(本機網速快時,各自下載也會全綠).
4. **不靠 `--require` 之全域前置**:mocha 之 `mochaGlobalSetup` 雖於平行模式只在主程序跑一次、且不受 `--timeout` 約束(實測 mocha 12.0.3),但批次工具與單檔執行常直接起 mocha 而不帶 `--require`,且 `scripts.test` 須維持 §5 之固定寫法 ⇒ 以 1～3 使任何起法皆成立.
5. **測試不連 CDN**:測試開啟之頁面以路由攔截,把外部網址導到本地副本(套件內附之檔、`node_modules` 內之檔,或首次下載後快取於不入版控之資料夾並校驗),**未列入對照表之外部網址一律拋錯**(使新增之外部依賴在測試中現形);不為此把前端依賴加回 `package.json` 之 dependencies.JS 專案優先用自有套件 `w-package-tools-e2e` 之 `createCdnLocal`(清單＋sha256 校驗＋內容定址快取＋跨程序鎖＋頁面與 Node 端 `fetch` 導向＋表外拋錯),不各自重寫;自寫或審查時須涵蓋:①對照表之鍵與請求網址一律先正規化(WHATWG URL)再比對,原字串比對會被前後空白、大小寫、預設埠繞過;②本機回送位址(開發伺服器、HMR 之 WebSocket)須放行,否則頁面載不進;③路由攔不到者(放行之本機位址回 3xx 導向外部、使用端後註冊之 `route.continue()` 繞過處理器)另以 `request` 事件記為違規,使用端自己之路由改用 `route.fallback()`;④違規以「有無」斷言,筆數受預載與重試影響,不當斷言.
6. **驗收**:清空該快取(模擬依賴升版)後以 `npm test`(平行)跑一次全套,全綠且只下載一次(以進度回調或下載次數計數斷言);另以單檔執行一次,確認不依賴其他檔先跑.

## 6. 測試/樣本數據

### 6.1 連結、引用、外部參考必須真實可驗證,不可捏造

**觸發**:產製任何測試/樣本/示範數據,其欄位含 URL、外部參考文獻、報告編號/序號,或關聯到內部既有資料時.

**背景**:LLM 自由生成領域內容時天然會捏造[看似合理]的具體引用——假 URL,拿 `google.com/search?q=` 當參考連結,虛構報告編號(如自編 `SKB TR-XX-XX` 配自擬標題),同一個佔位 query 配不同假標題.這類數據交付業主/行政單位驗收時**一點即知為假 → 直接扣分甚至減價驗收**.這是捏造[看似真實的具體內容]在數據層的變體.

**鐵則**:
1. **連結須真實可連通**:不用 `google.com/search` 當參考連結;不捏造 URL 或報告編號.產出前 `curl -sI`(或 `-o /dev/null -w %{http_code}`)驗 HTTP 200.
2. **引用真實既有物**:內部關聯優先參照系統內**確實存在**的項目(真實節點/需求編號+名稱,由資料本身或關聯圖推導);外部參考只用**已驗證存在**之真實文獻——可沿用同專案其他模組已驗證之參考集(如既有真實模組之法規/報告 URL),不另憑空生.
3. **具體標識查不到就不給**:報告編號、序號、標題、DOI、法規條號等只能用真實查得者;查不到 → 欄位可空則留空,或改用泛稱,絕不自編.
4. **寧缺勿假**:欄位允許空值(如 `necessary:'n'`)時,無真實對應就留空,遠優於填假資料.
5. **委派子代理產內容必明文禁捏造**:子代理自由生成領域內容最易捏造連結/引用,派工 prompt 須明訂[只用可驗證之真實來源,禁 google query 當連結,禁自編報告編號],並要求可追溯來源;收回後逐欄查有無假 URL/假編號才接受.

**交付前自問**:[這個連結/引用,業主點下去或去查證,會成立嗎?]不確定＝不可交.

### 6.2 合成之測試資料:各欄之值須逐筆相異

**觸發**:自行產生測試用之資料(合成之帳本、資料表、陣列、樣本檔),而被測之功能會依索引或鍵搬移、過濾、排序、重新編號、合併,或處理[每筆多個值]之欄時;或測試以重算核對統計量(計數、p 值、超額、排名),或測輸出文字內之數量時(第 6 點).

1. **每一欄之值逐筆相異**,且看值即知它來自哪一筆、哪一個位置(例:第 i 筆之第 k 個值取 `i * 10 + k`,或由 i 經固定之雜湊產生);不得整欄填同一個值(尤其 0、空字串、同一個時間戳).
2. **每筆多值之欄**(每筆 k 個值攤平存放者),同一筆之 k 個值亦須互異——否則[以每筆 1 個值處理]之錯測不到.
3. **筆數與各維之大小取不相等之數**(例:筆數 7、每筆 3 值),避免誤用另一維之長度時恰好不出錯;分段之欄(起訖索引)取段長不一、含 0 長之段.
4. **鑑別力之自檢**:寫完測試後,對[取值之索引]植入一項變異(如 `a[keep[i]]` 改為 `a[i]`、每筆之寬度由 k 改為 1),相關測試須轉紅;仍綠者先改資料,不是補斷言.
5. 沿用既有之合成資料產生器時,先看其各欄是否符合上三點;不符者於本次測試內另給逐筆相異之內容,不因[沿用既有]而放過.
6. **統計量之鑑別前提**:以重算核對統計量(計數、p 值、超額、排名)之測試,先列出[正確之基準]與[易誤用之基準](例:對該段之觀測值 vs 對全段之觀測值;含端點 vs 不含;分母含自身 vs 不含).兩者在該合成資料下得同一結果時,基準取錯測不到.作法:①調整資料或亂數種子,使至少一處兩者不同(必要時用兩組種子);②**於測試內另加一條斷言驗此前提**(兩種基準之結果至少一處不同;不成立即令測試失敗,訊息提示換種子或資料)——日後改動資料、筆數或種子時,鑑別力才不會靜默消失;③逐項變異有存活者,先查是否缺此前提,不是先補斷言.同形:**輸出文字內之數量**(相位數、筆數、期數)須取自被說明之結果自身之欄位,不取設定;夾具之實算值恰等於設定值時(手寫恰 7 項、設定預設亦 7),取設定與取實算同值、改前改後皆綠——須自建「實算 ≠ 設定」之夾具,並以修前紅驗其鑑別力.

**why**:整欄同值時,搬錯位置、複製錯長度、重新編號後未對應,輸出與正確者逐位相同;斷言寫得再多、變異做得再全,資料本身分不出對錯.**典型錯誤形狀**:功能把資料依成員切半並重新編號,其中[每筆 3 個值]之欄被以每筆 1 個值複製;合成資料該欄全為 0,新測試與 26 處變異皆未抓到,複審者改用逐筆相異之資料才發現.另一形狀(第 6 點):分段之 p 應對該段之觀測值計數,變異改為對全段之觀測值計數而存活——合成資料下兩者之計數恰同;換種子並加「至少一處兩種基準之計數不同」之斷言後才轉紅.又一形狀:看板與摘要寫設定之 7 個相位,快速模式實算只有 2 個;既有夾具之相位數恰為 7,改前改後皆綠,自建實算 2 個之夾具後修前紅 15 案.

### 6.3 敵意輸入、選配選項與身分欄位之測試

**觸發**:測試以已撤銷之 Proxy、拋錯之存取器等「讀取即拋錯」之值為輸入;測試選配選項之「未給」判定或界線類選項;測試主鍵、id 等身分欄位之判定.

1. **斷言之實際值可能不可讀時,一律 `assert.ok(<條件>, <固定訊息>)`**,訊息不內插該值;不用 `assert.equal`／`deepStrictEqual` 比對它——失敗時斷言程式與 mocha 報告器會 `util.inspect` 該值而拋錯,輸出截斷、**無摘要行(`N passing`／`N failing`)而離開碼可為 0**.修前紅之階段須確認摘要行存在;變異腳本把「通過數 + 失敗數 = 0」判為未判定,不判為殺死或存活.**組案名或訊息之輔助函數亦同**:以 `JSON.stringify(v)`、`String(v)` 等為案例標籤者,遇已撤銷之 Proxy 會自己拋 `TypeError`,使整案以崩潰而非斷言失敗呈現(提案端首版 10 案同因紅);標籤函數須 try/catch 回固定字串.
2. **選配選項之「未給」判定須含假值之案**(`''`、`0`、`false`、`[]`、`{}`、`null`),否則以真假值判斷之錯誤實作全綠;**界線類選項**(起點、上限、範圍)須有與相鄰選項並用之案.
3. **身分欄位(主鍵、id)類缺陷之測試資料,須並列「與既有列同值」與「無同值列」兩組**:前者顯出跳過／覆寫／誤刪,後者顯出缺欄或補值;只測其一,另一種形狀之缺陷漏網.

**why**:**典型錯誤形狀**:敵意輸入之測試以 `assert.equal(evs[0].data, null)` 斷言,修前之 `data` 為已撤銷之 Proxy,mocha 於組失敗訊息時崩潰、無摘要而以 0 結束,變異跑器誤判為存活;另一形狀:繼承之主鍵於無同值列時寫入無 id 欄之列,有同值列時 `save` 覆寫、`del` 刪除該列——只測前者者看不到誤刪.

## 8. 計時器相關之測試:以事件同步,不以延時偵測

**觸發**:測試輪詢、偵測、重試、節流、防抖、排程、逾時、等待類函數;測試內出現 `await sleep(N)`/`setTimeout(resolve, N)`/固定 `delay(N)` 後即斷言;子行程輸出順序以內部計時器隔開者.**命中即讀 [references/timer-tests.md](references/timer-tests.md) 全文**.

**why**:計時器與其回呼受 CPU 負載影響而時差不定,「等 N 毫秒後檢查」永遠含不穩因子;單獨重跑 5 次皆過不代表穩定,多套件並行或 e2e 多開之高負載下才現形.**典型錯誤形狀**:輪詢之測試每步 `sleep(30)` 後改狀態,高負載時取樣尚未發生就改了下一步,少一筆.

核心規則(細則與限制見 references):

1. **以事件同步**:被測函數提供觀察回調 `opt.onTrace`(同步、凍結之 `{ type, ... }`、拋錯忽略、未傳零成本;自有套件沿用 wsemi `getTrace`),測試以「等第 N 個事件」為同步點,再對事件內容斷言.
2. **斷言語意**,不斷言「X 毫秒內恰 N 次」;依「現在」入鍵之去重／快取測試,兩次呼叫之間須確保時鐘已前進(references §2).
3. **時間本身是規格者用假時鐘**(`node:test` 之 `mock.timers`),斷言事件之虛擬時刻;防懸置上限用真實計時器.
4. **真實檔案監看步進式**;**子行程以事件閘門與可觀察條件**;無計時器之函數改等被測物事件,不為測試改 src.
5. **否定斷言**才可用短暫觀察窗;**懸置以事件判定**;不得以重試掩蓋、不得只加大 timeout.
6. 每個加回調之函數補「未傳回調時行為不變」之五種回調案;每個改寫附**變異證據**並對照舊測試.
7. **負載試驗**為穩定之判準:CPU 壓力＋事件迴圈阻塞＋重度阻塞,改造前後同次數;基準先跑、獨佔測試資源、結束回驗壓力行程.

## 9. 含隨機性、鎖與並行之測試

**觸發**:測試隨機搜尋、最佳化、取樣、洗牌類函數;測試鎖、互斥檔、單例資源或並行寫入之函數;宣告完成前之重跑.

### 9.1 斷言不得依賴隨機搜尋之產出數、輪數或次序

**why**:隨機搜尋之產出數與輪數取決於亂數,[第一輪必給出 N 個候選]並非保證成立;單一配置下連跑多次皆過,不代表該假設成立.**典型錯誤形狀**:一案斷言[第一輪內必給出第 2 個候選,輪數為 0],擬稿者全套連跑 8 次、審查者數次皆過,另一種配置之第 1 次全套即失敗(單獨重跑 11 次皆過);盤點後同套件另有 3 案依賴[每輪必有產出].

1. 斷言不依賴隨機搜尋、最佳化之**產出數、輪數或次序**:固定亂數來源(種子),或改寫情境使之不依賴產出數——例:以有上限之迴圈取得所需之前提,於回呼內當場記錄後才斷言;取不到前提即以明確訊息使測試失敗(不是靜默通過).
2. 不得以單純重試掩蓋;不得只放寬斷言而使原本要防之錯漏網(以變異驗證,§10).
3. 被抓到一案時,盤點同測試目錄內同形之假設(每輪必有產出、第一輪即得 N 個),不只修被抓到之一案.

### 9.2 鎖、互斥檔、單例資源之測試

除[逾時]與[殘留清除]外,須有**[另一方持有後釋放,等候者成功]**之案(以事件或可觀察條件同步,不以延時,§8).**典型錯誤形狀**:鎖之測試只有逾時與殘留清除;審查者之變異[一遇占用即拋、不等候]存活,以該變異跑兩行程並行寫入 15 回合有 7 回合出錯(提案端實測).Windows 上並行接手殘留鎖時,刪除進行中對同名路徑之操作可能回 `EPERM`／`EBUSY`,鎖之實作須與 `EEXIST` 同視為占用而重試,見 skill[role-command-windows] §4.

跨程序之鎖另審三點:①心跳刷新前先核對持有者記號仍是自己,被接手後即停,不刷新他人之鎖;②持有者紀錄暫時讀不到(寫到一半)時不取其中之 PID,也不退回以資料夾時間判為殘留而誤收活鎖;③兩方同時判定殘留時,回收者須核對所搬走者之記號與判定時相同,不同即放回.多程序之測試以真實子行程跑;**子行程要連本測試程序內之夾具伺服器時不可用 `spawnSync`**——它阻塞事件迴圈,伺服器無法回應而互等至逾時,改非同步 `spawn` 並等其結束事件.

### 9.3 交付前之重跑與另一種配置

- 全套連跑至少 5 次;易偶發之測試檔(含隨機、鎖、並行、計時者)單獨連跑至少 20 次.連跑次數是下限,不是穩定之證明.
- **於另一種配置再跑一次全套**:例如套件位於 `node_modules` 之外之發布包解開目錄(§5.1)、另一個工作目錄.目錄結構、相依解析、工作目錄、檔案是否入版控之差異,會暴露只在某配置下成立之假設(9.1 之典型錯誤形狀即於另一配置之第 1 次全套才現形).
- **全套耗時長(十數分鐘以上)時,每次改完先單跑受影響之測試檔**:釘住被改之輸出、訊息、常數之測試檔(改動前之 Grep 見 skill[role-coder-for-validate] Step 2 第 6 點)、去識別與原始碼掃描類之守門測試、「對不可信輸入不拋錯」之案;皆綠後才跑全套——全套是最後一道,不是第一個偵錯工具.**典型錯誤形狀**:複審後改字句與常數,全套 14 分鐘後才現 3 項失敗(釘住舊字串、註解含磁碟機路徑字樣觸發去識別守門、新增之遞迴對越界佔位符拋錯),三者單跑對應之測試檔數秒即可發現.
- 完成前勾選見 §7 與 skill[role-coder-for-validate] §8.

## 10. 變異驗證之判讀與對照

**觸發**:以變異(植入單點缺陷、看測試是否轉紅)驗證測試之鑑別力;變異有存活者;修改既有行為而補測試;未入版控之檔之先紅後綠.

1. **變異存活,先分[等價變異]與[測試缺口]**:兩道互為備援之檢查,拿掉任一道都被另一道擋住,兩項變異皆存活——不等於等價.須各補一個**只有它抓得到**之案(讓另一道失效、只留該道把關),補後該變異轉紅才算.**典型錯誤形狀**:兩項變異皆存活而被誤記為等價,補[只有其中一道抓得到]之案後才轉紅.
   - **宣告「等價」須附可重跑之證據**,不憑推論或「看起來一樣」:①原碼對變異碼之**隨機對拍**(大量隨機輸入,輸出差異為 0;附腳本與語料來源),有差異即為缺口;②防禦性之不可達分支(如不會被觸發之 `catch`),以各類敵意輸入實跑皆不進該分支為證;③以真實外部工具比對兩種寫法之輸出(例:以真 git 比對兩種 pattern).**典型錯誤形狀**:程式改為「繼續處理其後之參數」後,兩項存活之變異被推論為等價;以 30 萬條隨機指令對拍原碼與變異碼,各得千餘條差異(某選項之值以 `-` 起首時),實為缺口,補 5 案後轉紅.
   - **結果層等價之最佳化路徑,其退回路徑仍須有案**:批次處理與逐一處理之結果相同時,批次失敗後退回逐一之路徑原本無測試,改壞它之變異照樣存活;補「批次中途失敗而退回」之案後才可殺.
   - **提前判定與下游同一判定互為備援時,以「零次啟動」觀察**:拿掉提前判定,結果相同、只多起一次子行程,結果層測不出.改斷言外部程式一次都沒被啟動:①記號假執行檔(每被啟動即附加一字元於測試暫存檔,斷言該檔不存在;並以有效輸入為對照,證明確會啟動);②對 git 子行程設 `GIT_TRACE=<檔>`(以暫存 repo 為 `cwd`;於 repo 外執行之 git 在寫 trace 前即失敗,得不到紀錄);③兩道檢查各自之變異皆存活時,加「成對移除即紅」之變異,證明兩道確屬互為備援.
   - **新增之通用檢查使既有之檢查成為死碼時,舊檢查之變異轉為存活**(訊息逐字相同,既有測試全綠):新增通用檢查後,立即重跑與被重疊之舊檢查有關之變異;存活且無可觀察之差異(含上一點之零次啟動)者,即舊檢查已不可達——刪除舊檢查並把變異改指新檢查,不去補一個不存在之「只有舊檢查抓得到」之案.
2. **變異腳本之錨點不存在或不唯一須報失敗**,不得靜默略過:程式改動使錨點文字消失時,腳本若略過該項,全體看似通過.錨點含換行者,依被改檔之實際換行(CRLF／LF)組錨點與取代文(如檔內 `includes('\r\n')` 時把錨點之 `\n` 換成 `\r\n`),或錨點不含換行——被改檔為 CRLF 時含 `\n` 之錨點命中 0 次(由本條攔下、未靜默略過,但整批須重跑);判斷檔案換行之法見 skill[role-command-windows] §2.5.續跑或只跑部分變異之選項以**完整 id** 比對,不以前綴(`S1` 會誤含 `S10`).**每次改碼後重跑全部變異**,不只重跑存活者——錨點因改碼而消失者,只有重跑全部才現形.
3. **修改既有行為時,另以改前之測試檔重跑同一批變異**:改前測試全綠而新測試轉紅,才證明新測試補到洞;否則[新測試只是換寫法]與[新測試確實補到洞]無從分辨.
4. **未入版控之檔之先紅後綠**:無法以版本控制還原改前版,依 skill[role-coder-for-validate] Step 2 先把改前檔複製到 `./tmp/<案名>/pre/`(保持相對路徑);再以**鏡像根**(只複製檔案、不建目錄連結)覆蓋改前檔得[紅],覆蓋單點變異得各變異之結果.**已入版控之檔**之修前基準(含接續輪:工作樹已含前一輪成果)、`git archive` 之換行陷阱、新增之具名匯出須以命名空間匯入、載入失敗與斷言失敗之分列,以及**修前版會懸置、耗盡記憶體或起真實外部呼叫之輸入**(子行程加逾時、排除、守門),見 [references/pre-red-baseline.md](references/pre-red-baseline.md).
5. 新舊版輸出對拍(重構前後比對)之工具與其鑑別力驗證,見 skill[role-coder-for-validate] L3.

## 11. 原始碼掃描型測試(守門測試)

**觸發**:寫以掃描原始碼判定之測試——「console 不得輸出使用者資料」「不得用 `eval`／`alert`」「某函數只有單一實作」「某設定鍵只在一處讀取」等;審查此類測試.

**why**:掃描器本身是被信任之一方;它漏抓某種寫法時,測試照綠而守門形同不存在,且「掃描回空」與「確實沒有」看起來相同.**典型錯誤形狀**:數個套件各寫一份以正規式掃描 console 站點之測試,獨立複審指出行首註解、`.vue` 之多個 `<script>`、括號存取(`console['log']`)、解構(`const { log } = console`)皆漏抓,改為 AST 版並加盲點自測;另一例,盤點「讀取某設定鍵之處」之自寫掃描漏掉一個進入檔而綠,由複審指出.

1. **以 AST 掃描,不以正規式**:`.vue` 取全部 `<script>` 與 `<template>`(模板內之表達式亦是站點);涵蓋別名、括號存取、解構、間接執行(`Function`、字串碼之計時器).
2. **掃描器附盲點寫法自測案**:每種已知盲點寫法各放一個正例(夾具字串或夾具檔),斷言掃描器抓得到;改掃描器時這組自測先過.
3. **先對已知正例驗,再採信空結果**:對「已知有此寫法之檔」先驗掃得到,並印出掃描之檔數(為 0 或明顯偏少即範圍壞了);盤點鍵名、別名清單之掃描亦同(skill[role-coder-for-validate] §9 末列).
4. **允許之站點以各檔數釘住**(檔 → 站點數),新增或消失皆使測試失敗,不只斷言「無新增之違規」.
5. 同一掃描邏輯只實作一份,放 `test/tools/`(§4);多套件需要同一掃描時,提案抽為共用工具,不各自複製.

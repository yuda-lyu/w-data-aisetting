# update-pks:套件更新流程

把使用者的既有手動流程(ncu 查更新 → 手動改 package.json 至最新 → npm i)自動化。**套件分組定義:`wsemi` 與所有 `w-` 開頭之套件為[自有套件],其餘為[非自有套件]**。

**預設更新範圍(重要,使用者裁定 2026-07-23)**:預設**僅更新自有套件**——一律直接更至最新,含 major/破壞性更新,「是否更新」不列待決、不徵詢;**更新完再檢查**——由本技能逐套件核對舊版至新版之破壞性變更並檢查使用端(步驟 6b),須使用者裁示者列入回報(使用者 2026-11-14:「要留意自有套件更新會有破壞性更新之問題,得要更新完再檢查」)。**非自有套件預設一律不更動、僅列出**(分「非 major」與「major 跳版」兩節呈現);要更新非自有須明示參數——此設計係防範 vue 2→3、vuex 3→4、eslint 8→10 這類破壞性跳版(殷鑑:Vue 2 專案中 ncu 會建議 vue ^3.x,盲更即炸),且非自有更新本就非本技能之預設任務。

## 參數

- 無參數:僅自有套件(預設)。
- `others`:自有全部+非自有之非 major 更新。
- `major`:自有全部+非自有全部(含 major 跳版)。
- 其他文字:視為套件名單(空白分隔,可含 glob),只更新命中者(指名者含 major 也更)。

## 步驟

### 1. 前置檢查

- 確認 cwd 有 `package.json`,無則回報並終止。
- **檢查 ncu 可用性**(本技能可能被帶到其他 VM 執行,不可假設已裝):
  ```bash
  ncu --version
  ```
  成功 → 後續以 `ncu` 為指令;失敗 → 改用 `npx -y npm-check-updates`(npx 會自動下載,需網路;首次較慢屬正常)。兩者皆不可用(如無網路)→ 回報無法執行並終止。
- **檢查生效之 registry**(自有套件只發布至私有倉庫,見全域設定 §5.1):於 cwd 執行
  ```bash
  npm config get registry
  ```
  ncu 依 npm 設定之順序取 registry(專案 `.npmrc` → 使用者設定 → 預設 npmjs),**不會因查錯倉庫而報錯**。結果為 `https://registry.npmjs.org/`(或其他非私有倉庫之位址)時,自有套件會靜默查到 npmjs 上停更之舊版、看似「已是最新」——**停下並回報**:列出生效之 registry 與其來源(`npm config list` 中標示之設定檔),提示依全域設定 §5.1 於專案根目錄 `.npmrc` 設定私有倉庫(或本機使用者設定),**不得改用 npmjs 之結果繼續**。私有倉庫之位址以全域設定 §5.1 為準,本技能不寫死。
- 檢查專案根目錄是否有 `建議*修改.md`(glob):此類檔代表 `node_modules` 內有**尚未收回套件 repo 的本地 patch**,`npm i` 會將其覆蓋。有的話先列出檔名,並於最終回報提醒[哪些本地 patch 已被覆蓋,如仍需要須重套]。**不因此中止**,照常更新。

### 2. 查更新

```bash
<ncu指令> --jsonUpgraded
```

- 輸出為 JSON(`{套件名: 新版本範圍}`)。空物件 `{}` 表示全部已是最新,直接回報並結束。
- 讀 `package.json` 取各套件現行版本,組出 `套件名 現行 → 最新` 對照,並判定各套件是否 major 跳版(比對兩邊 semver 第一碼)。
- **記下每個自有套件之舊版號**(安裝前之實裝版本,讀 `node_modules/<套件>/package.json` 之 `version`;未安裝者記 package.json 之範圍):`npm i` 之後 node_modules 只剩新版,步驟 6b 須以此界定要讀之變更範圍。

### 3. 分組呈現

依定義分組列出(各組內按套件名排序),major 跳版者標註:

- **自有套件**:`wsemi` 與 `/^w-/` 命中者。
- **非自有套件(非 major,預設不更新)**:列 `現行 → 最新`,註明須參數 `others` 或指名才更新。
- **非自有套件(major 跳版,預設不更新)**:列 `現行 → 最新`,註明須參數 `major` 或指名才更新。

依參數計算實際更新名單,標明哪些將更新、哪些略過。名單為空則回報後結束(不跑 npm i)。

### 4. 更新 package.json

```bash
<ncu指令> -u --filter "<實際更新名單(空白分隔)>"
```

- 一律用顯式 `--filter` 名單(不整包 `-u`),確保預設僅自有之邏輯生效。

### 5. 安裝

```bash
npm i --no-audit --no-fund
```

- timeout 給足(600000ms);超時改 detached 背景跑再輪詢(依全域 §8.5)。

### 6. 回驗

- `npm i` exit code 為 0 且輸出無 `ERR!`。
- 逐一以 `node -e "console.log(require('./node_modules/<套件>/package.json').version)"` 抽驗本次更新的套件(至少自有套件全部),確認 node_modules 內版本 = package.json 新版本(避免[以為更新了但 node_modules 是舊的]假象)。

### 6b. 破壞性變更之核對(更新完再檢查)

只做到 6 為止會漏掉這種錯:版本號抽驗通過、測試全綠,但使用端「依舊輸出格式、舊預設值、舊錯誤語意」所寫之處理靜默失效——套件端已記下變更,使用端沒有人讀。對每個有更新之自有套件:

- a. **讀新版內之變更紀錄,取舊版至新版之間之條目**(新版之檔在 `node_modules/<套件>/`,自有套件之 `sgud/` 隨包發布):
  - README 之升版說明;
  - `sgud/rule/` 之破壞性變更紀錄(如 `rulebook_breaking*.md`);
  - **各規則條目之〈變更紀錄〉**——輸出格式、預設值、錯誤語意之改變常只記在這裡,沒進破壞性變更紀錄,只讀後者會漏;
  - CHANGELOG(若有)。
  範圍以日期界定:各版之發布時間以 `npm view <套件> time --json` 取得(私有倉庫可用;部分 npm 版本之輸出為以陣列包住之一個物件,鍵為版號,指定 `@<版號>` 仍回全部版本)。
- b. **列出受影響之對外函數、選項與輸出格式**,在使用端(專案之 src、server、測試與工具)以 Grep 找其呼叫點,以及「依舊行為所寫之處理」:依舊格式之轉換或比對、依舊錯誤語意之判斷(原回空值、現拋錯者之 `try/catch` 與判空)、依舊預設值之假設。逐處判定:不受影響/須改/已改。
- c. **須改者**依 skill[role-coder-for-validate] L0e 修使用端並補測試——測試輸入須為真實型別(如真正之日期儲存格、真正之重複主鍵),不能只有「剛好不觸發」之輸入;判定為套件缺陷者依全域設定 §5.2 提 issue。
- d. 跑專案之測試全套,結果列入回報。
- e. 變更紀錄寫得不清楚時,以 `npm pack <套件>@<舊版> --pack-destination ./tmp/<案名>/` 取得舊版,與新版之 src 比對補強;用完清除。
- 典型錯誤形狀(去識別):某次升版把試算表讀取函數對日期儲存格之讀出由序號改為 ISO 字串,只記在該規則之〈變更紀錄〉;使用端之日期轉換只認整數序號,新格式不觸發,全部日期被判為格式錯誤;測試資料皆為文字日期而全綠,約 5 週後以實際資料才發現。

### 7. 回報

- 各組更新結果(`套件名 舊 → 新`)、略過清單(含 major 跳版待決清單)。
- npm i 結果與抽驗結果。
- **〈破壞性變更核對〉**(每次必有,不得省略):各自有套件之舊版 → 新版、讀了哪些紀錄(檔名與條目)、受影響之使用端站點與處置(不受影響/已改/須裁示);無影響者寫「已核對,無影響」。
- 步驟 1 若有本地 patch 檔:提醒該等 node_modules 改動已被本次安裝覆蓋,如仍需要須重套(列出對應的 `建議*修改.md` 檔名)。
- **不自動 commit**(使用者需要時會自行說)。

## 注意事項

- Windows/git-bash 環境:一律於主任務 cwd 執行,不用 `cd` 前綴。
- 「不做相容性評估」只限非自有套件:非自有清單僅供使用者決策參考;**自有套件之相容性於步驟 6b 核對**,回歸驗證不再全交使用者事後把關(2026-11-14 調整)。
- 曾誤設計為預設連非自有非 major 一起更,經使用者糾正還原(2026-07-23):本技能之本旨即「更新自有套件」,非自有只看不動。
